## Introduction

[Inside vLLM: 서버 시작부터 KV cache까지 소스 코드 톺아보기](https://blog.liam.kim/posts/2026/10/Inside-vLLM/)에서 vLLM v0.32.0의 서버 초기화, request 처리, KV cache를 소스 코드로 따라갔다. 이번에는 같은 문제를 푸는 다른 serving engine인 SGLang을 본다. 기준은 2026년 10월의 SGLang [v0.5.22](https://github.com/sgl-project/sglang/tree/v0.5.22)다.

두 엔진은 겉으로 비슷하다. 둘 다 OpenAI 호환 HTTP API를 내놓고, continuous batching, chunked prefill, prefix caching, CUDA graph, speculative decoding을 지원한다. 그런데 코드를 열어 보면 출발점이 다르다. vLLM은 PagedAttention, 즉 KV cache를 고정 크기 block으로 나눠 메모리 낭비를 줄이는 데서 출발했다. SGLang은 RadixAttention, 즉 여러 request가 공유하는 prompt 앞부분(prefix)의 KV를 tree에 남겨 두고 자동으로 재사용하는 데서 출발했다([Zheng et al., 2023](https://arxiv.org/abs/2312.07104)). 이 차이가 KV cache 자료구조뿐 아니라 scheduler와 process 구조에도 이어진다.

이 글은 vLLM 글을 읽지 않아도 따라올 수 있게 SGLang만으로 설명한다. 다만 절마다 "vLLM과 다른 점"을 따로 두어, 같은 문제를 두 엔진이 어떻게 다르게 풀었는지 짚는다. 순서는 이렇다.

1. 큰 그림: SGLang 서버를 이루는 세 process와 한 step의 모양
2. Radix Tree: SGLang의 근간인 prefix tree가 동작하는 원리
3. 서버 초기화: `sglang serve` 한 줄이 process와 KV cache를 준비하는 순서
4. request 처리: chat request 하나가 token이 되어 돌아오는 경로
5. KV cache 메모리와 batch: 위 과정을 받치는 자료구조와, 여러 종류의 attention을 섞은 model에서 그 자료구조가 바뀌는 방식

## 큰 그림

LLM은 token을 하나씩 만든다. prompt 전체를 한 번에 계산해 KV를 채우는 단계를 prefill, 그 뒤로 token을 하나씩 만드는 단계를 decode라고 한다. serving engine은 여러 request의 이 두 단계를 GPU forward 한 번에 묶어 계산한다. SGLang은 이 묶음을 batch라고 부르고, scheduler가 loop를 돌 때마다 batch를 하나 골라 forward를 한 번 한다.

### SGLang 서버는 세 process로 나뉜다

SGLang 서버는 아래 그림처럼 세 process로 나뉜다. 그림은 GPU 하나(tensor parallel 1, data parallel 1)를 쓰는 기본 구성이다.

- **Main process**는 HTTP와 tokenize를 맡는다.
    - **FastAPI app**: HTTP request를 받아 OpenAI 형식을 검증하고, 응답을 JSON이나 SSE(Server-Sent Events, HTTP 연결 하나로 event를 조금씩 보내는 방식)로 돌려준다.
    - **TokenizerManager**: chat template을 적용하고 prompt를 token ID로 바꾼다. request마다 상태 객체([`ReqState`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L261))를 두고, 결과가 오면 기다리는 HTTP handler를 깨운다.
- **Scheduler process**는 GPU를 돌린다. GPU rank마다 하나씩 뜬다.
    - **Scheduler**: 대기 중인 request(`waiting_queue`)와 decode 중인 request(`running_batch`)를 보고 다음 batch를 고른다.
    - **Tree cache**: 이미 계산한 prefix의 KV 위치를 radix tree로 들고 있다. 이 글의 중심이다.
    - **Memory pools**: request별 token 위치표(`ReqToTokenPool`)와 KV를 실제로 담는 pool이다.
    - **TpModelWorker, ModelRunner**: batch를 GPU 입력으로 바꿔 forward와 sampling을 실행한다.
- **Detokenizer process**는 scheduler가 만든 token ID를 text로 바꿔 main process로 보낸다.

세 process는 [ZeroMQ](https://zeromq.org/)(ZMQ, broker 없이 process끼리 소켓으로 직접 메시지를 주고받는 library)로 연결된다. 방향은 한쪽으로만 돈다. TokenizerManager가 scheduler로 request를 보내고, scheduler가 detokenizer로 token ID를 보내고, detokenizer가 TokenizerManager로 text를 보낸다. 소켓은 모두 PUSH와 PULL의 짝이다.

#### vLLM과 다른 점: detokenizer가 별도 process다

vLLM은 두 process다. API server process가 HTTP, tokenize, detokenize를 모두 맡고, EngineCore process가 scheduler와 GPU를 맡는다. 결과는 EngineCore에서 API server로 바로 돌아간다. SGLang은 detokenize를 세 번째 process로 뺐고, 결과가 고리를 한 바퀴 돌아 main process로 온다.

코드나 문서에서 이렇게 나눈 이유를 적은 곳은 찾지 못했다. 추측하자면, main process의 event loop는 HTTP와 tokenize를 함께 처리하므로 detokenize의 CPU 시간까지 지면 응답이 밀린다. 실제로 SGLang에는 tokenizer와 detokenizer process 수를 따로 늘리는 옵션(`tokenizer_worker_num`, `detokenizer_worker_num`)이 있다. 각 단계를 독립적으로 늘리려는 설계로 보인다.

한 가지 더 다르다. stop string 검사가 어디서 일어나는지다. vLLM은 API server에서 detokenize하면서 stop string을 찾는다. SGLang은 scheduler가 직접 찾는다. 이 차이는 [request 처리 7번](#7-종료-판정과-출력-stop-string은-scheduler가-찾는다)에서 다룬다.

### 한 loop의 모양

scheduler process는 아래 네 일을 반복한다. 코드로는 [`event_loop_normal()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L1940-L1972)이 가장 읽기 쉽다.

```python
self.ingest_requests()                    # ZMQ로 들어온 request를 waiting_queue에 넣는다
plan = self.get_next_batch_to_run(...)    # 이번에 돌릴 batch를 고른다
result = self.run_batch(batch)            # GPU forward와 sampling
self.process_batch_result(batch, result)  # 결과 기록, 종료 판정, detokenizer로 전송
```

기본으로 쓰는 loop는 이것을 조금 비튼 [`event_loop_overlap()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L1975)이다. GPU가 batch N을 계산하는 동안 CPU가 batch N+1을 고르고, batch N의 결과는 한 loop 늦게 처리한다. [request 처리 6번](#6-forward와-overlap-scheduling-cpu-작업을-gpu-뒤에-숨긴다)에서 자세히 본다.

batch를 고르는 규칙에서 vLLM과 크게 갈린다. SGLang은 기본 설정에서 prefill batch(SGLang 용어로 EXTEND)와 decode batch를 따로 돌린다. 새로 prefill할 request가 있으면 그것을 먼저 돌리고, 없으면 decode를 돌린다. vLLM V1은 phase 구분 없이 한 step에 prefill 조각과 decode token을 섞는다. 이 차이도 [request 처리 4번](#4-다음-batch-고르기-prefill을-먼저-돌린다)에서 다룬다.

## Radix Tree: SGLang의 근간

SGLang을 이해하려면 radix tree부터 봐야 한다. scheduler가 request를 받으면 가장 먼저 tree에서 prefix를 찾고, request가 끝나면 그 KV를 tree에 넣고, 메모리가 모자라면 tree에서 지운다. KV cache를 관리하는 일 대부분이 이 tree를 거친다.

### 왜 prefix tree인가

LLM 요청에는 앞부분이 같은 경우가 많다. 같은 system prompt를 쓰는 chat, 이전 대화를 다시 담아 보내는 멀티턴, 같은 문서에 질문만 바꾸는 RAG, 같은 few-shot 예시를 쓰는 평가, tool 결과를 붙여 다시 부르는 agent가 그렇다. attention의 KV는 그 token과 앞 token들에만 의존하므로, 앞부분 token이 같으면 KV도 같다. 이미 계산한 KV를 버리지 않고 남겨 두면 다음 request는 다른 부분만 prefill하면 된다.

문제는 "남겨 둔 KV 중 어느 것이 이 request의 앞부분과 같은가"를 빨리 찾는 일이다. 남겨 둔 token 열이 수천 개라면 하나씩 비교할 수 없다. SGLang 논문은 이 일을 radix tree로 풀었고, 이 방식을 RadixAttention이라고 불렀다. 논문은 KV cache를 request가 끝나면 버리는 임시 상태가 아니라, request 사이에서 재사용하는 cache로 보자고 제안한다([Zheng et al., 2023](https://arxiv.org/abs/2312.07104), [LMSYS 블로그](https://lmsys.org/blog/2024-01-17-sglang/)).

### radix tree는 압축한 trie다

trie는 문자열 집합을 저장하는 tree다. 각 edge가 글자 하나이고, root에서 내려가며 읽은 글자들이 그 node까지의 문자열이 된다. 앞부분이 같은 문자열은 같은 경로를 공유하므로, 어떤 문자열의 가장 긴 공통 prefix는 root에서 한 글자씩 따라 내려가다가 더 갈 수 없는 곳에서 멈추면 찾을 수 있다. 비교 횟수는 저장된 문자열 수가 아니라 찾는 문자열 길이에 비례한다.

radix tree는 trie에서 가지가 갈라지지 않는 구간을 하나의 node로 합친 것이다. "S0 S1 S2 S3 a0 a1"을 trie로 저장하면 node가 6개지만, radix tree는 갈라지는 곳이 없으므로 node 하나에 6 token을 담는다. 나중에 "S0 S1 S2 S3 b0 b1 b2"가 들어와 S3 다음에서 갈라지면, 그때 node를 둘로 쪼갠다(split). 이 글의 예시에서 S0-S3은 여러 request가 공유하는 system prompt token이고, a0 a1과 b0 b1 b2는 request마다 다른 질문 token이다. SGLang에서 글자는 token ID이고, node에는 token 열과 함께 그 token들의 KV가 놓인 위치가 붙는다.

### TreeNode: token 열과 KV 위치를 함께 들고 있다

v0.5.22에서 실제 서버가 쓰는 tree는 [`UnifiedRadixCache`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_radix_cache.py#L175)이고, tree 연산의 핵심은 기본으로 [Rust 구현](https://github.com/sgl-project/sglang/tree/v0.5.22/rust/sglang-radix-tree)이 맡는다. Python으로 쓴 [`RadixCache`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/radix_cache.py#L281)는 기본 경로에서 쓰이지 않는다. 다만 동작 원리는 같고 코드가 훨씬 짧다. 그래서 이 절의 링크와 코드 조각은 모두 기본 경로에서 실제로 도는 Rust 코드에서 가져온다. 코드 조각은 설명에 필요한 줄만 남기고 줄였다. 둘의 차이는 절 끝에서 정리한다.

표에 앞서 용어 두 개를 정해 두자. KV pool은 모든 request의 KV를 담는 큰 GPU tensor다. slot은 그 안에서 token 하나의 KV가 들어가는 자리이고, 번호로 찾는다. 자세한 구조는 [KV cache 메모리 1번](#1-두-단계-pool-req_to_token과-kv-pool)에서 본다.

Rust의 [`Node`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/node.rs#L159-L209) 중 이 절에 필요한 필드는 아래와 같다.

| 필드 | 담는 것 |
| --- | --- |
| `key` | 이 node가 맡은 token 열 |
| `values` | component별 값([`ValueState`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/node.rs#L715-L720)). full attention component의 `value`가 그 token들의 KV가 놓인 KV pool slot 번호이고, GPU tensor다 |
| `children` | 자식 node. 자식 key의 첫 page를 key로 쓴다. `page_size`가 1이면 첫 token이다 |
| `parent` | 부모 node |
| `lock_ref` | 이 node를 쓰고 있는 request 수. component마다 `values` 안에서 따로 센다. 0이 아니면 지우지 않는다 |
| `last_access_counter` | 마지막으로 match되거나 insert된 순서. 시각이 아니라 단조 증가하는 counter이고, LRU eviction의 기준이다 |

Python `RadixCache`의 [`TreeNode`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/radix_cache.py#L250-L278)도 같은 역할의 필드를 가진다. 다만 `value`가 하나뿐이고, 접근 순서를 시각(`last_access_time`)으로 센다.

node에 KV 자체가 들어 있지 않다는 점이 중요하다. `value`는 slot 번호 목록일 뿐이고, KV 값은 KV pool이라는 큰 tensor에 있다([KV cache 메모리 1번](#1-두-단계-pool-req_to_token과-kv-pool)). 그래서 node를 쪼개거나 합쳐도 KV를 복사하지 않는다. slot 번호 tensor만 잘라서 나눠 가진다.

`children`의 key는 자식 node가 시작하는 첫 token이다([`ChildMap`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/node.rs#L137)). 한 node 아래 자식들은 첫 token이 서로 다르므로, 다음에 어느 자식으로 내려갈지 dictionary 조회 한 번으로 정해진다. LoRA adapter나 `cache_salt`가 있으면 그 값도 key에 섞여서, 같은 token 열이라도 namespace가 다르면 다른 가지가 된다. `ChildMap`의 key가 (namespace, 첫 page)의 쌍이기 때문이다([`Node.children`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/node.rs#L163-L169)).

### 예시로 따라가기: match, insert, lock, evict

A는 질문 a0 a1을, B는 질문 b0 b1 b2를 붙였고, C는 A의 대화에 c0을 이어 붙였다. request는 실행 중에 자기가 match한 경로를 잠그고(lock), 끝나면 계산한 token을 tree에 넣는다(checkpoint). 예시를 단순하게 하려고 생성한 답변 token은 그리지 않는다. slot 0은 나중에 CUDA graph padding이 쓰도록 비워 두므로([KV cache 메모리 7번](#7-padding이-남는-곳-cuda-graph)) 1번부터 쓴다.

아래는 그림의 동작을 함수별로 본다. match(③⑤), insert(②④), lock(③⑤), evict(⑥) 순서다.

#### match_prefix(): 따라 내려가다 node 안에서 멈추면 쪼갠다

[`match_prefix()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L1254-L1282)는 request의 token 열을 root에서부터 따라 내려간다. 실제 loop는 [`match_prefix_helper_()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L1324)에 있다. 아래는 그 loop를 줄인 것이다.

```rust
while offset < aligned_key_len {
    // 다음 page(page_size 1이면 token 하나)로 자식을 고른다
    let Some(child_id) = self.arena.child_on_page_in_namespace(
        node_id, namespace, key.page_at(offset, self.page_size),
    ) else { break };
    let child = self.arena.node(child_id);
    let prefix_len = key.match_len(offset, &child.key, self.page_size);
    if prefix_len < child.key.atom_len() {        // node 중간에서 어긋났다
        let (split_node_id, _) = self.split_node_(child_id, prefix_len);
        value.push(self.arena.node(split_node_id).device_value(FULL).shallow_clone());
        update_best_if_valid(/* ... */);
        break;
    }
    value.push(child.device_value(FULL).shallow_clone()); // node 전체가 맞았다
    node_id = child_id;
    update_best_if_valid(/* ... */);
    offset += prefix_len;
}
```

`update_best_if_valid()`는 "이 node에서 match를 끝내도 되는가"를 확인한다. full attention만 쓰는 model에서는 언제나 통과한다. 여러 종류의 attention을 섞은 model에서 하는 일은 [KV cache 메모리 8번](#8-여러-종류의-attention-종류별-pool-위에-tree-하나를-둔다)에서 본다.

loop 한 번에 node 하나를 내려간다. 첫 token으로 자식을 고르고, 그 자식의 token 열과 몇 개가 같은지 센다. 다 같으면 다음 node로, 중간에서 어긋나면 그 자리에서 멈춘다. 지나온 node의 `value`를 이어 붙이면 재사용할 KV slot 목록이 된다. 지나간 node마다 `last_access_counter`도 갱신한다.

중간에서 멈출 때 [`split_node_()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L2129-L2239)가 node를 둘로 나눈다. 앞부분은 새 부모 node가 되고, 뒷부분은 원래 node에 남아 그 자식이 된다. 그림 ③에서 "S0 S1 S2 S3 a0 a1" node가 "S0-S3"과 "a0 a1"로 나뉜 것이 이 동작이다. 이렇게 쪼개 두면 B는 정확히 4 token 경계까지 재사용할 수 있고, 다음 request는 쪼개진 경계를 그대로 쓴다. 이때 `value`도 같은 위치에서 잘리지만, slot 번호 tensor를 나눌 뿐 KV는 그대로다.

match는 탐색만 하지 않고 tree 모양을 바꿀 수 있다는 점이 특이하다. Rust의 match loop가 어긋난 자리에서 [`split_node_()`를 바로 부른다](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L1418-L1422). Python `RadixCache`의 [docstring](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/radix_cache.py#L365-L379)도 "This method may mutate internal structure by splitting an existing node"라고 적어 둔다.

request 하나가 재사용할 수 있는 prefix는 최대 `입력 길이 - 1`이다([`_compute_max_prefix_len()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L1696-L1698)). prompt 전체가 tree에 있어도 마지막 token 하나는 다시 계산한다. 다음 token을 sampling하려면 마지막 위치의 logits가 있어야 하기 때문이다. 코드 주석은 logprob 계산을 이유로 든다.

#### checkpoint()와 insert(): 계산한 KV를 tree에 넘긴다

request가 끝나면 [`release_kv_cache()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/common.py#L378)가 `UnifiedRadixCache`의 [`checkpoint()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_radix_cache.py#L1075-L1080)를 부른다. checkpoint는 request가 계산한 token과 그 KV slot을 Rust의 [`insert()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L1634)로 tree에 넣는다. prompt뿐 아니라 생성한 token도 들어간다. 그래서 다음 턴의 request는 이전 턴의 답변까지 재사용할 수 있다.

insert는 match와 같은 방식으로 내려가다가, 더 맞는 자식이 없는 곳에 남은 token으로 새 leaf를 붙인다. 그림 ④에서 b0 b1 b2 leaf가 붙은 것이 이것이다. 이때부터 그 slot들의 주인은 request가 아니라 tree다. request가 끝나도 slot은 free list로 돌아가지 않고, tree가 지우기 전까지 KV가 남는다.

두 request가 같은 prefix를 동시에 계산하는 경우도 있다. 둘 다 tree에 없는 같은 prompt를 거의 동시에 받으면, 둘 다 같은 내용의 KV를 서로 다른 slot에 계산한다. 나중에 insert하는 쪽은 tree에 이미 그 token이 있음을 알게 되고, 자기 slot 중 겹치는 부분을 바로 반납한다. Rust `insert()`는 이미 tree에 있던 길이를 [`InsertResult.prefix_len`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L199-L205)으로 돌려주고, 호출한 쪽이 그만큼의 slot을 반납한다. tree에는 한 벌만 남는다.

chunked prefill로 prompt를 나눠 계산할 때도 조각마다 checkpoint가 불린다([`checkpoint_kv_cache()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/common.py#L253-L262)). 그래서 긴 prompt를 절반만 계산했어도, 그 절반은 다른 request가 이미 재사용할 수 있다.

#### lock_ref: 쓰고 있는 경로는 지우지 않는다

tree의 KV는 언제든 지워질 수 있는 cache다. 그런데 어떤 request가 그 KV를 attention에서 읽는 중이라면 지우면 안 된다. 그래서 request는 match한 마지막 node를 잡는다. [`inc_lock_ref()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L1029-L1051)는 component마다 lock을 잡게 하고, full attention component는 그 node에서 [root까지 올라가며](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/components/full.rs#L277-L338) 모든 node의 `lock_ref`를 1씩 올린다. 아래는 그 loop를 줄인 것이다.

```rust
let mut cur = node_id;
loop {
    let node = tree_core.arena.node_mut(cur);
    if node.is_root() { break; }
    let parent = node.parent();
    if node.device_lock_ref(FULL) == 0 {           // 0에서 1이 되는 node
        let len = node.device_value_len(FULL);
        tree_core.dec_evictable_size(FULL, len);   // 지울 수 있는 크기에서 빼고
        tree_core.inc_protected_size(FULL, len);   // 보호된 크기에 더한다
    }
    node.inc_device_lock_ref(FULL);
    tree_core.evictable_device_leaves.discard(cur);
    cur = parent;
}
```

경로 전체를 잠그는 이유는 KV가 경로를 따라 이어져 있기 때문이다. C가 a-node를 읽으려면 그 앞의 S-node도 있어야 한다. `lock_ref`가 0에서 1이 되는 순간 그 node의 token 수가 "지울 수 있는 크기"(evictable size)에서 "보호된 크기"(protected size)로 옮겨진다. scheduler는 이 두 숫자로 지금 얼마나 비울 수 있는지 안다. request가 끝나면 [`dec_lock_ref()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L1127)가 반대로 내린다.

#### evict(): lock 없는 leaf부터 LRU로 지운다

KV pool에 빈 slot이 모자라면, 빈 slot을 나눠 주는 allocator([KV cache 메모리 2번](#2-allocator-빈-slot-목록은-gpu-tensor다))가 [`evict_from_tree_cache()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/common.py#L265)를 거쳐 tree에 필요한 token 수만큼 비우라고 요청한다. `UnifiedRadixCache`는 Rust의 [`evict_device_start()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/components/full.rs#L139-L150)로 후보를 모으고, [`evict_device_next_node()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/components/full.rs#L152-L192)로 지울 leaf를 하나씩 고른 뒤, [`evict_device_leaf()`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_tree_core.rs#L2592-L2634)로 slot을 반납하고 node를 지운다. 아래는 앞의 두 함수를 줄인 것이다.

```rust
// evict_device_start(): lock_ref가 0인 leaf를 우선순위 heap에 넣는다
heap.extend(evictable_device_leaves.iter()
    .map(|id| Reverse((strategy.get_priority(arena.node(id)), id))));

// evict_device_next_node(): 한 번 부를 때마다 leaf 하나를 고른다
if let Some(parent) = evict_device_cursor          // 직전에 지운 leaf의 부모가
    && evictable_device_leaves.contains(parent)    // 자식 없는 leaf가 됐으면
{
    heap.push(Reverse((strategy.get_priority(arena.node(parent)), parent)));
}
while let Some(Reverse((_, x))) = heap.pop() {
    if !evictable_device_leaves.contains(x) { continue; }
    evict_device_cursor = arena.node(x).try_parent();
    return Some(x);   // 호출한 쪽이 evict_device_leaf(x)로 slot을 반납한다
}
```

지우는 대상은 leaf뿐이다. 중간 node를 지우면 그 아래 가지의 KV가 앞부분을 잃어 쓸모없어지기 때문이다. leaf를 지운 뒤 부모가 자식 없는 leaf가 되면, 부모도 후보로 heap에 넣는다. 그래서 tree는 바깥 가지부터 안쪽으로 줄어든다. 공유가 많은 앞부분(system prompt 같은 것)은 가장 늦게 지워진다.

SWA와 Mamba component는 heap 대신 component별 LRU 이중 연결 리스트([`unified_lru_list.rs`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_lru_list.rs))를 따로 들고 있다. 이것은 [KV cache 메모리 8번](#8-여러-종류의-attention-종류별-pool-위에-tree-하나를-둔다)의 component별 eviction에 쓰인다.

우선순위는 eviction 정책이 정한다. 기본은 [`"lru"`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/memory.py#L24-L42)로, `last_access_counter`가 가장 작은 leaf부터 지운다([`LruStrategy`](https://github.com/sgl-project/sglang/blob/v0.5.22/rust/sglang-radix-tree/src/unified_lru_list.rs#L417-L424)). `--radix-eviction-policy`로 LFU, SLRU, priority, TLRU를 고를 수 있다. TLRU는 대화에서 tail TTFT에 영향을 주지 않는 부분부터 지우는 정책이다(help 문구가 [arXiv:2510.15152](https://arxiv.org/abs/2510.15152)를 인용한다).

#### page_size: token 하나 단위로 공유한다

tree가 몇 token 단위로 나뉘는지는 `page_size`가 정한다. NVIDIA GPU에서 기본값은 [1](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/overrides.py#L1304-L1326)이다. 그래서 split은 어느 token 사이에서든 일어날 수 있고, prefix는 token 하나 단위로 공유된다. `page_size`를 키우면 key를 page 크기의 배수로 [잘라서](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_radix_cache.py#L1148-L1150) 비교하고, 꽉 차지 않은 마지막 page는 tree에 넣지 않는다. FlashMLA처럼 page 크기를 요구하는 attention backend를 쓰면 `page_size`가 64 같은 값으로 강제된다.

### vLLM과 다른 점: hash table 대신 tree

vLLM도 prefix caching을 기본으로 켠다. 하지만 자료구조가 다르다. vLLM은 prompt를 16 token block으로 자르고, block마다 "앞 block의 hash + 이 block의 token"으로 hash를 만든다. 그리고 hash에서 block으로 가는 표를 조회한다. 같은 hash는 처음부터 그 block까지 token이 모두 같다는 뜻이다.

두 방식의 차이는 아래와 같다.

| | vLLM (block hash) | SGLang (radix tree, page_size 1) |
| --- | --- | --- |
| 공유 단위 | 꽉 찬 16 token block | token 하나 |
| 찾는 방법 | block마다 hash 계산 후 표 조회 | root에서 token을 따라 tree를 내려감 |
| 꽉 차지 않은 끝부분 | hash가 없어 공유 안 됨 | 공유됨 |
| 지우는 순서 | free block queue 순서(LRU) | lock 없는 leaf 중 LRU, 바깥 가지부터 |
| 공유 중임을 표시 | block마다 `ref_cnt` | 경로 전체의 `lock_ref` |
| 자료구조가 아는 것 | 개별 block | prefix 사이의 관계(누가 누구의 앞부분인가) |

마지막 줄이 가장 큰 차이다. hash table은 "이 block이 있는가"만 답한다. tree는 어떤 request들이 앞부분을 공유하는지, 그 공유가 얼마나 긴지까지 구조로 들고 있다. SGLang scheduler는 이 정보로 waiting queue를 정렬할 수 있다. 예를 들어 LPM(longest prefix match) 정책은 tree에서 가장 많이 맞는 request를 먼저 돌려, 공유 prefix가 지워지기 전에 재사용하게 한다([request 처리 3번](#3-waiting-queue와-정책-기본은-fcfs다)). 다만 v0.5.22의 기본 정책은 FCFS라 이 기능은 직접 켜야 한다.

tree에도 비용이 있다. hash 조회는 block마다 O(1)이지만, tree 탐색은 node를 하나씩 따라 내려가야 하고, split은 tree 모양을 바꾼다. Python으로 짜면 node마다 객체를 거치는 비용이 붙는다. SGLang이 tree 핵심을 Rust로 옮긴 것도 이 CPU 비용 때문으로 보인다. 반대로 vLLM의 block 방식은 page 단위 attention kernel과 자연스럽게 맞는다. SGLang도 `page_size`를 키우면 공유 단위가 page가 되어 vLLM과 비슷해진다. tree에 넣거나 찾기 전에 key를 page 크기의 배수로 [자르기](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_radix_cache.py#L1148-L1150) 때문이다. split은 page 경계에서만 일어나고, 꽉 차지 않은 마지막 page는 tree에 들어가지 않으며, allocator도 page 단위로 나눠 준다. 비슷해지는 것은 공유 단위와 메모리 단위뿐이다. 자료구조는 여전히 tree라서 prefix 사이의 관계를 알고, LPM 같은 scheduling과 leaf부터 지우는 eviction은 그대로다.

### UnifiedRadixCache: 실제로 도는 tree

앞에서 본 `RadixCache`는 원리를 보여 주는 구현이다. v0.5.22 기본 서버는 [`default_radix_cache_factory()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/registry.py#L83-L146)에서 대부분의 경우 [`create_unified_radix_cache()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/registry.py#L149)를 거쳐 `UnifiedRadixCache`를 만든다. 동작은 같지만 두 가지가 다르다.

- tree 연산 핵심을 [기본으로 Rust 구현](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/environ.py#L688)이 맡는다. Python 구현은 fallback이다.
- node에 component를 붙일 수 있다. full attention의 KV뿐 아니라 sliding window attention(SWA)의 KV나 Mamba 같은 state space model의 state도 같은 tree에서 관리한다. hybrid model마다 따로 있던 cache 구현을 이 하나로 모으는 중이라고 [`mem_cache/README.md`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/README.md)가 적고 있다. 이 component 방식은 KV 메모리 구조를 본 뒤 [KV cache 메모리 8번](#8-여러-종류의-attention-종류별-pool-위에-tree-하나를-둔다)에서 자세히 본다.

### 1. Entry: `sglang serve`에서 `ServerArgs`까지

`sglang serve`는 [`sglang.cli.main:main`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/pyproject.toml#L216)으로 시작한다. LLM backend는 결국 [`launch_server.run_server()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/launch_server.py#L20-L65)를 호출한다. 예전 방식인 `python -m sglang.launch_server`도 아직 동작하지만 deprecation 경고를 낸다.

CLI 인자는 [`ServerArgs`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/server_args.py#L230)에 담긴다. v0.5.22의 `ServerArgs`는 field를 주제별 파일(`srt/arg_groups/fields/`)로 나눠 정의하고, 비어 있는 값은 [`resolve_once()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/server_args.py#L243)가 부르는 resolution pipeline이 채운다. 예전 버전처럼 `__post_init__()` 하나에 모든 기본값 로직이 있지 않으니, 오래된 글을 볼 때 주의해야 한다.

이 처리 방식이 vLLM과 다르다. vLLM은 CLI 인자를 받자마자 `ModelConfig`, `CacheConfig`, `SchedulerConfig` 같은 sub-config로 나누고, 각 config가 자기 `__post_init__()`에서 자기 규칙을 검사한다. 즉 설정의 주인 기준으로 나눈다. SGLang은 CLI 인자를 평평한 `ServerArgs` 하나에 그대로 받는다. `fields/` 폴더의 파일 분리는 정의만 나눈 것이다. 그 다음 정해진 순서의 hook들이 이 record 하나를 돌며 빈 값을 채운다. [`pipeline.py`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/pipeline.py#L20)에는 `run_hook()` 호출이 83개 있다. 주제별로 나뉜 설정(`get_schedule()`, `get_exec()` 같은 [config bag](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/runtime_context.py#L1310-L1317))은 이 처리가 다 끝난 뒤에 만들어 공개한다. 즉 결정하는 순서 기준으로 나눈다. SGLang이 이 방식을 고른 이유를 적은 문서는 찾지 못했지만, 코드에서 보이는 이유는 세 가지다.

1. 기본값 하나가 여러 주제의 값에 함께 걸린다. 예를 들어 GLM-5.3-Flash hook은 speculative decoding을 켰고 GPU가 SM100일 때만 `linear_attn_verify_backend`를 [정한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/glm5_next_hook.py#L18-L35). 이런 규칙은 어느 sub-config에도 깔끔하게 속하지 않으므로, 무엇을 먼저 정하는지를 순서로 드러낸다.
2. 기본값의 출처가 남는다. hook은 값을 직접 덮어쓰지 않고 [`declare_resolution()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/overrides.py#L110-L135)으로 어느 단계가 어떤 값을 정했는지 쌓는다. 사용자의 원래 입력(`_raw_input`)도 따로 남긴다.
3. 확장하기 쉽다. model 제공자는 override를 등록하고, plugin은 [허용된 hook](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/resolution_hooks.py#L1-L14)을 이름으로 바꿔 끼운다.

대가도 있다. 최종 값은 pipeline을 끝까지 돌려야 알 수 있고, 코드를 읽으려면 hook 순서를 알아야 한다. hook이 idempotent(멱등성)하지 않아서 `resolve_once()`는 한 번만 돈다. vLLM 방식은 config 하나만 봐도 규칙을 알 수 있지만, 여러 주제에 걸친 규칙은 결국 `VllmConfig.__post_init__()`에 모인다.

`run_server()`는 그 다음 서버 모드를 고른다. 기본은 HTTP 서버인 [`http_server.launch_server()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/http_server.py#L2901)다. 다른 경로도 있다.

- `SGLANG_RUST_SERVER=1`: Rust로 쓴 HTTP 서버가 scheduler process 안에서 돈다. 이때 Python의 HTTP 서버, TokenizerManager, DetokenizerManager는 아예 뜨지 않는다([`rust_server/server.py`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/rust_server/server.py#L1-L8)). 기본값은 꺼져 있다.
- `--grpc-port`: HTTP 서버와 함께 gRPC 서버를 띄운다.
- [`sgl-model-gateway`](https://github.com/sgl-project/sglang/tree/v0.5.22/sgl-model-gateway): 여러 SGLang instance 앞에 두는 별도 router 프로젝트다.

이 글은 기본 HTTP 경로만 따라간다.

### 2. 기본값: GPU 메모리로 정한다

SGLang은 사용자가 정하지 않은 값 중 여럿을 GPU 메모리 크기로 정한다. 가장 중요한 두 값은 `chunked_prefill_size`와 decode CUDA graph의 최대 batch 크기다. `chunked_prefill_size`는 prefill batch 하나에 넣을 최대 token 수다. 이보다 긴 prompt는 여러 batch에 나눠 계산한다. CUDA graph는 forward 한 번의 kernel들을 기록해 두고 통째로 재생하는 기능이다. 자세한 것은 4번에서 본다.

[`handle_gpu_memory_settings()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/memory_hook.py#L47)가 이 일을 하고, tensor parallel 크기가 4 미만일 때 [표](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/memory_hook.py#L90-L170)는 아래와 같다.

| GPU 메모리 | `chunked_prefill_size` | decode CUDA graph 최대 batch |
| --- | --- | --- |
| 20GB 미만 | 2048 | 8 |
| 20-35GB | 4096 | 48 |
| 35-60GB | 4096 | 32 |
| 60-90GB (H100, A100 80GB) | 8192 | 256 |
| 90-160GB (H200) | 8192 | 256 |
| 160GB 이상 (B200 등) | 16384 | 512 |

그 밖의 기본값은 이렇다.

- `mem_fraction_static`: GPU 메모리 중 weight와 KV pool이 쓸 비율이다. 고정값이 아니라 [식으로 계산한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/memory_hook.py#L296-L328). activation과 CUDA graph가 쓸 메모리(`reserved_mem`)를 `chunked_prefill_size`와 CUDA graph batch 크기로 추정하고, `(GPU 메모리 - reserved_mem) / GPU 메모리`로 정한다.
- `schedule_policy`: [`"fcfs"`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/schedule.py#L82-L98)다.
- `max_prefill_tokens`: [16384](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/schedule.py#L67-L77)다.
- `max_running_requests`: 동시에 decode할 최대 request 수다. 여기서는 정하지 않고, KV pool 크기가 정해진 뒤 [그 크기로 계산한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/kv_cache_configurator.py#L2800-L2813).

코드 주석 하나가 이 표가 왜 중요한지 보여 준다. RTX 5090 같은 32GB GPU에서 예전 상한은 batch 32 이상에서 CUDA graph를 못 쓰게 했고, 주석은 이것이 "collapsed high-concurrency throughput vs vLLM"했다고 적는다. 그래서 20-35GB 구간의 상한을 48로 올렸다.

#### vLLM과 다른 점: 기본값이 메모리 예산까지 정한다

vLLM도 GPU 메모리로 기본값을 고른다. 다만 vLLM은 진입점(`vllm serve`인지 `LLM` 클래스인지)도 함께 보고, 고르는 값은 주로 `max_num_batched_tokens`다. SGLang에는 진입점별 구분이 없다. 대신 SGLang은 이 값들로 activation 메모리를 추정해 KV pool에 줄 메모리 비율(`mem_fraction_static`)까지 정한다. vLLM에서는 같은 일을 다음 4번처럼 실제 profiling으로 한다.

### 3. Process launch: 세 process와 ZMQ 고리

HTTP 서버 경로는 [`Engine._launch_subprocesses()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/engine.py#L1121)로 process를 띄운다. 순서는 이렇다.

1. [`_launch_scheduler_processes()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/engine.py#L889): GPU rank마다 `mp.Process`를 하나씩 띄운다. target은 [`run_scheduler_process()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L6076)이고, process마다 `mp.Pipe`를 하나 준다.
2. [`_launch_detokenizer_subprocesses()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/engine.py#L1035): detokenizer process를 띄운다. target은 [`run_detokenizer_process()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/detokenizer_manager.py#L539)다.
3. [`init_tokenizer_manager()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/engine.py#L191): main process 안에 TokenizerManager를 만든다.
4. [`_wait_for_scheduler_ready()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/engine.py#L1982): 각 scheduler가 pipe로 READY를 보낼 때까지 기다린다.

소켓 주소는 [`PortArgs`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/server_args.py#L719)가 정한다. 기본은 TCP port가 아니라 임시 파일 경로를 쓰는 `ipc://` 주소다. 같은 호스트의 process끼리 통신하므로 Unix domain socket으로 충분하다. 연결은 앞의 큰 그림대로 고리 모양이다.

| 방향 | 보내는 쪽 | 받는 쪽 |
| --- | --- | --- |
| TokenizerManager → Scheduler | [PUSH](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L668) | PULL |
| Scheduler → Detokenizer | PUSH | [PULL](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/detokenizer_manager.py#L126) |
| Detokenizer → TokenizerManager | [PUSH](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/detokenizer_manager.py#L133) | [PULL](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L664) |

READY 대기는 무작정 막히지 않는다. `_wait_for_scheduler_ready()`는 pipe를 5초씩 poll하면서 scheduler process가 살아 있는지 확인한다. 그래서 scheduler가 model load 중 OOM으로 죽으면 main process가 영원히 기다리지 않고 바로 실패한다. detokenizer는 READY를 보내지 않는다. 대신 watchdog이 살아 있는지 감시한다.

#### vLLM과 다른 점: handshake가 단순하다

vLLM은 EngineCore process를 띄운 뒤 ZMQ로 HELLO와 READY를 주고받고, 그 사이에 소켓 주소를 교환한다. SGLang은 소켓 주소를 `PortArgs`로 미리 정해 두고 자식 process에 인자로 넘긴다. READY는 ZMQ가 아니라 `mp.Pipe`로 받는다. READY 메시지에는 KV pool이 담을 수 있는 최대 token 수(`max_total_num_tokens`, 다음 4번에서 계산한다)와 최대 입력 길이가 들어 있고, main process는 이 값을 TokenizerManager에 넘겨 입력 길이 검사에 쓴다.

이 차이는 상대 process의 주소를 시작 전에 알 수 있느냐에서 나온다. vLLM의 EngineCore는 API server의 자식 process가 아닐 수도 있다. data parallel(DP)을 쓰면 다른 노드에서 엔진만 headless(frontend 없이)로 뜨고, API server를 여러 개 띄우기도 한다([`_perform_handshakes()` docstring](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1250-L1278)). 이런 상대에게는 process 인자로 주소를 넘길 수 없다. 그래서 엔진이 HELLO로 먼저 알리고, frontend가 그 답으로 ZMQ 주소와 DP 설정을 [보낸다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L1475-L1490). SGLang은 주소를 교환하지 않고 계산한다. 한 노드에서는 모든 process를 main process가 직접 띄우므로 인자와 Pipe로 충분하다.

여러 노드에서도 SGLang은 handshake를 하지 않는다. 노드마다 같은 명령에 `--nnodes`, `--node-rank`, `--dist-init-addr`만 맞춰 띄운다([multi-node 문서](https://github.com/sgl-project/sglang/blob/v0.5.22/docs/docs/references/multi_node_deployment/multi_node.mdx)). 각 노드는 자기 GPU의 scheduler만 띄우고 Pipe로 READY를 기다린다. HTTP 서버와 TokenizerManager는 node rank 0에만 [있다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/engine.py#L1228-L1230). TokenizerManager는 TP rank 0 scheduler에만 request를 보내고, 그 scheduler가 다른 TP rank에 request를 [broadcast한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler_components/request_receiver.py#L80-L101). DP attention처럼 노드를 넘는 ZMQ 주소가 필요하면, 모든 노드가 `dist_init_addr`와 고정 offset으로 같은 port를 [계산한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/server_args.py#L803-L830). 노드 사이의 준비는 scheduler가 `torch.distributed`를 초기화할 때 모든 rank가 모여야 끝나므로 따로 확인하지 않는다.

대가는 배치의 유연성이다. 모든 노드를 같은 인자로 함께 띄워야 하고, vLLM처럼 엔진만 따로 원격에 붙이는 구성은 이 경로로 할 수 없다.

### 4. Scheduler startup: model load, KV pool, tree cache, CUDA graph

scheduler process 안에서는 [`Scheduler.__init__()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L460)이 준비를 맡는다. 핵심은 [`init_model_worker()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L1098)다.

1. `TpModelWorker`와 `ModelRunner`를 만든다. [`ModelRunner`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/model_runner.py#L695)는 분산 환경을 초기화하면서 model load 전 GPU 여유 메모리를 기록하고, weight를 GPU에 올린다.
2. [`init_memory_pools()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L1068)가 KV pool 크기를 정하고 pool을 할당한다.
3. attention backend를 초기화한다.
4. [`init_cuda_graphs()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/model_runner.py#L1156)가 CUDA graph를 capture한다.

KV pool 크기는 [`_profile_available_bytes()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/kv_cache_configurator.py#L2671-L2719)가 정한다. 이름에 profile이 들어 있지만 forward를 돌려 보지는 않는다. 계산은 이렇다.

```python
slack_gb = pre_model_load_memory * (1 - get_schedule().mem_fraction_static)
rest_memory = available_gpu_memory - slack_gb - mm_reservation_gb
```

아래 그림은 이 계산을 메모리 막대로 보여 준다.

`pre_model_load_memory`는 model을 올리기 전의 여유 메모리, `available_gpu_memory`는 weight를 올린 뒤의 여유 메모리다. 즉 2번에서 정한 비율만큼을 activation과 CUDA graph 몫으로 남기고, 나머지를 KV pool에 준다. 이 byte 수를 token 하나의 KV 크기(`cell_size`, layer 수 * KV head 수 * head 크기 * 2 * dtype 크기)로 나눈 값이 KV pool이 담을 수 있는 token 수(`max_total_num_tokens`)다. 그 다음 [`build_kv_cache()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/kv_cache_builder.py#L248)가 세 가지를 만든다.

- `req_to_token_pool`: request별 token 위치표([`ReqToTokenPool`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/memory_pool.py#L374))
- `token_to_kv_pool_allocator`: 빈 KV slot을 나눠 주는 allocator
- `tree_cache`: 앞에서 본 radix tree. `--disable-radix-cache`를 주지 않으면 [켜져 있다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/memory.py#L64-L69)

CUDA graph는 decode와 prefill 둘 다 capture한다. [CUDA graph](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)는 forward 한 번에 실행되는 kernel들을 기록해 두고 통째로 재생하는 기능이다. kernel을 하나씩 launch하는 CPU 비용이 사라지므로, kernel이 짧은 decode에서 효과가 크다. decode용 batch 크기 목록은 [`generate_decode_cuda_graph_batch_sizes()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/cuda_graph_hook.py#L462-L479)가 `[1, 2, 4, 8, 12]`, 16부터 256까지 8 간격, 그 뒤로 16과 32 간격으로 만든다. prefill은 CUDA에서 BCG(breakable CUDA graph)가 [기본](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/cuda_graph_config.py#L119-L122)이다.

준비가 끝나면 `run_scheduler_process()`가 pipe로 READY를 보내고 event loop에 들어간다. loop는 [`_dispatch_event_loop_once()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L5984)가 고른다. `--disable-overlap-schedule`을 주지 않으면 [`enable_overlap`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L495-L497)이 참이고, `event_loop_overlap()`이 돈다.

#### vLLM과 다른 점: KV cache 크기를 profiling하지 않는다

vLLM은 최대 크기의 dummy batch로 forward를 실제로 한 번 돌려 activation 최고치를 재고, CUDA graph 메모리도 추정한 뒤, 남은 메모리를 KV cache에 준다. SGLang은 dummy forward 없이 `mem_fraction_static`이라는 비율 하나로 정한다. 그 비율은 2번에서 chunked prefill 크기와 CUDA graph batch 크기로 추정한 값이다.

장단점이 있다. SGLang 방식은 시작이 빠르고 결과가 예측 가능하다. 대신 추정이 틀리면 OOM이 나거나 메모리가 남는다. 그래서 OOM이 나면 `--mem-fraction-static`을 낮추라는 것이 SGLang의 흔한 처방이다. `memory_hook.py`의 docstring도 "in the future, we can do better estimation by ... do a dummy run"이라고 이 한계를 인정한다. CUDA graph를 capture한 뒤 실제 여유 메모리를 재서 KV pool 크기를 다시 맞추는 기능도 있지만, v0.5.22에서는 [기본으로 꺼져 있다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/environ.py#L589)(`SGLANG_ENABLE_POST_CAPTURE_KV_SIZING`).

### 5. HTTP serving: READY 뒤에 listen하고, warmup으로 확인한다

scheduler가 모두 READY를 보내면 [`_setup_and_run_http_server()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/http_server.py#L2624)가 FastAPI [`app`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/http_server.py#L481)으로 Uvicorn을 띄운다. 소켓은 이때 처음 열린다.

FastAPI의 lifespan은 서버가 요청을 받기 시작할 때 warmup thread를 하나 띄운다. [`_execute_server_warmup()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/http_server.py#L2287)은 `/model_info`가 응답할 때까지 기다린 뒤, 자기 자신에게 `/generate` request(8 token 생성, temperature 0)를 보낸다. 이 request가 성공하면 상태를 `ServerStatus.Up`으로 바꾸고 "The server is fired up and ready to roll!"을 log에 남긴다. 실패하면 process tree 전체를 죽인다. 그 전까지 `/health`는 503을 돌려준다.

#### vLLM과 다른 점: 소켓을 여는 시점이 반대다

vLLM은 엔진을 준비하기 전에 소켓을 먼저 bind해 port를 잡고, 엔진이 READY가 된 뒤 listen한다. port 충돌을 무거운 초기화 전에 발견하려는 것이다. SGLang은 엔진이 다 준비된 뒤에 소켓을 만든다. 그래서 port가 이미 쓰이고 있으면 model load와 CUDA graph capture를 다 마친 뒤에야 실패한다. 대신 SGLang은 warmup request로 전체 경로(HTTP → tokenize → scheduler → GPU → detokenize)를 한 번 실제로 돌려 본 뒤에 healthy로 바뀐다. load balancer가 `/health`를 보고 traffic을 보낸다면, 첫 사용자 request가 초기화 비용을 지지 않는다.

### 1. HTTP POST와 tokenize: event loop 밖에서 한다

[`/v1/chat/completions` route](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/http_server.py#L1803)는 `OpenAIServingChat`의 `handle_request()`를 부른다. 이 함수는 chat template 적용과 tokenize를 asyncio event loop 밖의 thread에서 [실행한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/entrypoints/openai/serving_base.py#L92-L96).

```python
# Convert off-loop: jinja render + full-prompt tokenization blocks
# the loop on long prompts, and the rust tokenizer releases the GIL.
adapted_request, processed_request = await loop.run_in_executor(
    None, self._convert_to_internal_request, request, raw_request
)
```

긴 prompt를 tokenize하는 동안 event loop가 막히면 다른 request의 SSE 응답까지 멈춘다. Rust로 쓴 tokenizer는 실행 중 GIL을 놓으므로, thread로 빼면 실제로 병렬로 돈다. 결과는 token ID를 담은 `GenerateReqInput`이고, TokenizerManager의 [`generate_request()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L896)로 넘어간다. 이미 token ID가 있으므로 [`_tokenize_one_request()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L1097-L1119)는 tokenize를 건너뛴다.

### 2. ZMQ 전송: pickle로 scheduler에 보낸다

TokenizerManager는 `TokenizedGenerateReqInput`을 PUSH 소켓으로 scheduler에 보낸다. 직렬화는 기본으로 pickle이다([`SGLANG_USE_PICKLE_IPC=True`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/environ.py#L361)). msgspec 기반의 더 빠른 경로도 있지만 opt-in이다. 보낸 뒤에는 `rid_to_state[rid]`에 `ReqState`를 두고, 그 안의 `asyncio.Event`를 기다린다. detokenizer에서 결과가 오면 [`handle_loop()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L2463)가 해당 `ReqState`에 결과를 붙이고 event를 깨운다.

### 3. waiting queue와 정책: 기본은 FCFS다

scheduler의 [`ingest_requests()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L2098)는 ZMQ 소켓에서 non-blocking으로 request를 모두 꺼낸다. [`handle_generate_request()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L2820)가 `Req`를 만들고, [`_add_request_to_queue()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L3353)가 `waiting_queue`에 넣는다. structured output request는 grammar를 compile하는 동안 별도 queue에서 기다린다.

waiting queue를 어떤 순서로 볼지는 [`SchedulePolicy`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L186)가 정한다. v0.5.22의 기본값은 `fcfs`로, 도착 순서를 그대로 쓴다. `--schedule-policy`로 고를 수 있는 정책 중 cache를 보는 것은 아래 둘이다.

- `lpm`(longest prefix match): request마다 tree에서 match 길이를 재고, 긴 것부터 [정렬한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L437). 같은 prefix를 공유하는 request를 몰아서 돌리므로, 그 prefix가 지워지기 전에 재사용된다.
- `dfs-weight`: tree를 깊이 우선으로 돌며 가지마다 대기 request 수로 가중치를 매기고, 그 순서로 돌린다. 논문이 제안한 cache-aware scheduling이다.

LPM은 같은 batch에 들어갈 request끼리 prefix가 겹치는 경우도 처리한다. 아직 tree에 없는 같은 prefix를 가진 request가 여럿 오면, 하나만 먼저 돌리고 나머지는 잠시 미룬다. 먼저 돈 request가 tree에 prefix를 넣으면 나머지가 그것을 재사용한다. 이를 위해 batch 안의 request만 담는 가상의 tree를 따로 쓴다.

과부하일 때 request를 거절하는 기능도 있다. `--max-queued-requests`를 주면 scheduler의 waiting queue가 그 수를 넘을 때 [`_abort_on_queued_limit()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L3425)이 "The request queue is full." 메시지와 HTTP 503으로 request를 끝낸다. 기본값은 `None`이라, 설정하지 않으면 거절하지 않는다.

#### vLLM과 다른 점: cache를 보고 순서를 바꿀 수 있다

vLLM의 waiting queue는 FCFS나 priority 순서다. prefix cache는 request가 들어갈 차례가 된 뒤에 확인한다. SGLang은 tree가 prefix 사이의 관계를 알기 때문에, 순서 자체를 cache hit가 커지도록 바꿀 수 있다. 다만 LPM은 긴 prefix를 가진 request를 계속 앞으로 당기므로, 짧은 prefix의 request가 오래 기다릴 수 있다. v0.5.22가 FCFS를 기본으로 둔 것도 이런 공정성 문제 때문으로 보인다. 코드에서 그 이유를 적은 곳은 찾지 못했다. 또한 waiting queue가 128개를 넘으면 match와 정렬 비용 자체가 커지므로, LPM을 켜도 그동안은 [FCFS로 돌린다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L300-L311).

#### vLLM과 다른 점: 거절은 scheduler가 한다

vLLM도 `--max-num-queued-reqs`로 503을 돌려준다. 기본값이 없어서 기본으로는 거절하지 않는 것도 같다. 다른 점은 위치다. vLLM은 API server가 request를 EngineCore로 보내기 전에 거절한다. SGLang은 request가 scheduler process까지 간 뒤에 거절한다. priority scheduling을 켜면 SGLang은 새 request를 거절하는 대신 queue에 있는 우선순위 낮은 request를 내보낼 수도 있다. waiting queue의 내용을 아는 scheduler에서 결정하니 가능한 일이다.

### 4. 다음 batch 고르기: prefill을 먼저 돌린다

[`get_next_batch_to_run()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L3766)은 먼저 [`get_new_batch_prefill()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L3927)로 waiting queue에서 prefill batch를 만들어 본다. 만들어지면 그것을 돌리고, 없을 때만 [`update_running_batch()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L4335)로 decode batch를 돌린다([코드](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L3870-L3882)).

```python
if new_batch is not None:
    # Run prefill first if possible
    ret = new_batch
else:
    # Run decode (skip for prefill-only batches)
    if not running_batch.is_empty() and not running_batch.is_prefill_only:
        decode_batch = self.update_running_batch(running_batch)
```

그래서 한 forward는 기본적으로 prefill(EXTEND) 아니면 decode(DECODE)다. prefill batch가 끝나면 그 request들은 `running_batch`에 합쳐지고, 다음부터 decode batch에 함께 들어간다. batch의 종류는 [`ForwardMode`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/forward_batch_info.py#L196)로 표시한다. EXTEND와 DECODE 말고도 둘을 섞은 MIXED, speculative decoding 검증용 TARGET_VERIFY 등이 있다.

#### vLLM과 다른 점: phase를 나눈다

vLLM V1 scheduler에는 prefill phase와 decode phase가 없다. step마다 request별로 "이번에 계산할 token 수"만 정하고, prefill 조각과 decode token을 한 forward에 섞는다. SGLang은 기본으로 두 phase를 나누고, prefill을 우선한다. 아래 그림은 A와 B가 decode 중일 때 C가 들어오면 두 엔진이 각각 어떤 forward를 만드는지 보여 준다.

차이는 decode 중인 request가 받는 영향에서 드러난다. SGLang에서 새 request가 오면 decode 중인 request들은 prefill batch가 도는 동안 한 forward를 쉰다. 긴 prompt가 연달아 오면 이 쉬는 시간이 쌓여 TPOT(token 사이 간격)가 튄다. chunked prefill이 prefill batch 크기를 `chunked_prefill_size`로 제한해 이 시간을 줄인다. vLLM 방식은 decode가 쉬지 않는 대신, decode token과 prefill token이 한 forward 안에서 같은 kernel을 쓰게 된다.

SGLang도 섞을 수 있다. `--enable-mixed-chunk`를 주면 [`mix_with_running()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L3143)이 prefill batch에 decode 중인 request를 합쳐 MIXED batch를 만든다. 기본값은 꺼져 있고, logprob을 요청한 request나 beam search가 있으면 섞지 않는다.

### 5. PrefillAdder: decode가 쓸 자리를 미리 떼어 둔다

prefill batch에 어떤 request를 몇 token 넣을지는 [`PrefillAdder`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L581)가 정한다. waiting queue를 정책 순서대로 보며 [`add_one_req()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L1336)로 하나씩 넣는데, 한도는 세 가지다.

- `rem_chunk_tokens`: 이번 batch에 넣을 수 있는 prefill token 수. `chunked_prefill_size`에서 시작한다. prompt가 남은 한도보다 길면 잘라서 앞부분만 넣고, 그 request를 `chunked_req`로 기억했다가 다음 batch에서 이어 넣는다.
- `rem_input_tokens`: 한 batch의 입력 token 수 상한. `max_prefill_tokens`에서 시작한다.
- `rem_total_tokens`: KV pool의 남은 자리. 빈 slot에 지울 수 있는 tree 크기를 더하고, 아래의 예약분을 뺀 값이다.

세 번째가 SGLang의 특징이다. 새 request를 받기 전에, 지금 decode 중인 request들이 앞으로 쓸 KV 자리를 [미리 빼 둔다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L641-L650).

```python
def _get_running_request_total_token_offset(self, req: Req) -> int:
    ratio = 1.0 if req.sampling_params.ignore_eos else self.new_token_ratio
    return min(req.sampling_params.max_new_tokens - len(req.output_ids),
               CLIP_MAX_NEW_TOKENS) * ratio
```

request마다 "남은 최대 생성 token 수 * `new_token_ratio`"만큼을 예약한다. `max_new_tokens`를 끝까지 쓰는 request는 드물기 때문에 비율을 곱한다. 남은 수는 [4096에서 자른다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L83-L87). 이 비율은 [`NewTokenRatioTracker`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler_components/new_token_ratio_tracker.py#L14)가 관리한다. 시작값, 하한, 줄어드는 속도는 [환경 변수 기본값](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/environ.py#L594-L596)으로 정한다. 시작값은 0.7이고, 하한은 시작값의 0.14배인 약 0.1이다. decode step마다 같은 폭으로 줄어, 600 step 뒤에 하한에 닿는다. 메모리가 넉넉하게 남는 동안에는 점점 덜 보수적으로 request를 받는 것이다.

추정이 틀려 decode 도중 KV 자리가 모자라면 retract가 일어난다. [`check_decode_mem()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L3279)이 실패하면 [`retract_decode()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L3298)가 running batch에서 request 몇 개를 골라 KV를 놓게 하고 waiting queue로 돌려보낸다. 그리고 `new_token_ratio`를 실제 생성량에 맞춰 높인다. 이후 request 받기가 다시 보수적으로 바뀐다. log에는 "KV cache pool is full. Retract requests."가 남는다. 돌려보낸 request는 나중에 다시 prefill한다. 다만 그 KV가 tree에 남아 있으면 match로 상당 부분을 건너뛴다.

#### vLLM과 다른 점: 예측해서 받고, 틀리면 retract한다

vLLM은 미래를 예약하지 않는다. step마다 이번에 필요한 KV block만 할당하고, 모자라면 그때 running request 하나를 preempt해 처음부터 다시 계산하게 한다. SGLang은 받을 때 미래 사용량을 추정해 예약하고, 추정이 틀렸을 때만 retract한다. 둘 다 결국 "KV를 놓고 다시 계산"으로 수습하지만, SGLang은 그런 일이 드물도록 입구에서 조절한다. 그 대가로 추정이 보수적인 동안에는 실제로 쓸 수 있는 메모리보다 적게 request를 받는다.

### 6. Forward와 overlap scheduling: CPU 작업을 GPU 뒤에 숨긴다

[`run_batch()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L4490)는 `TpModelWorker.forward_batch_generation()`을 부른다. 여기서 `ScheduleBatch`가 [`ForwardBatch.init_new()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/forward_batch_info.py#L937)로 GPU 입력이 되고, [`ModelRunner.forward()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/model_runner.py#L1786)와 [`sample()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/model_runner.py#L2061)가 실행된다. decode batch는 batch 크기가 capture한 크기 안이면 [CUDA graph를 재생한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/model_runner.py#L1964-L1969).

기본 loop인 `event_loop_overlap()`은 이 forward를 CPU 작업과 겹친다. GPU는 kernel을 queue에 쌓아 두고 순서대로 실행하므로, CPU는 forward를 launch만 하고 바로 다음 일을 할 수 있다. 문제는 다음 decode batch의 입력이 이번 batch에서 sampling한 token이라는 점이다. CPU가 그 token 값을 받으려면 GPU가 끝날 때까지 기다려야 한다.

<Figure
  src="/assets/images/post/2026-10-31-Inside-sglang/07-overlap-light.svg"
  darkSrc="/assets/images/post/2026-10-31-Inside-sglang/07-overlap-dark.svg"
  caption="normal loop와 overlap loop. overlap loop는 batch N의 결과를 한 loop 늦게 처리하고, 다음 decode 입력은 GPU 안에서 가져온다."
/>

SGLang은 이 문제를 [`FutureMap`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/overlap_utils.py#L255)으로 푼다. forward가 sampling한 token은 GPU의 `output_tokens_buf`에서 그 request의 `req_to_token` 행 번호(`req_pool_indices`) 위치에 쓰인다. 다음 decode batch의 입력은 CPU가 값을 몰라도 GPU에서 [바로 모은다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/overlap_utils.py#L118).

```python
batch.input_ids = future_map.output_tokens_buf[batch.req_pool_indices]
```

그래서 loop는 이렇게 돈다. batch N+1을 고르고 launch한 뒤에 batch N의 결과를 처리한다([`pop_and_process()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L1981-L1984)). 결과를 CPU로 복사하는 일은 별도 CUDA stream(`copy_stream`)에서 한다. CPU 쪽 scheduling, 종료 판정, detokenizer 전송이 모두 GPU forward 뒤에 숨는다.

결과를 한 loop 늦게 처리하므로, request가 끝났는지도 한 loop 늦게 안다. 그 사이에 끝난 request의 token이 하나 더 계산될 수 있다. scheduler는 이번 forward에서 `max_new_tokens`에 닿을 request를 미리 계산해 다음 batch에서 빼는 식으로 이 낭비를 줄인다. structured output은 다음 token의 허용 목록(grammar bitmask)이 이전 token에 달려 있으므로, sampling을 이전 결과 처리 뒤로 미룬다.

#### vLLM과 다른 점: 같은 생각, 다른 시기

vLLM의 async scheduling도 같은 문제를 같은 방향으로 푼다. step N이 도는 동안 step N+1을 schedule하고, 아직 모르는 token 자리는 placeholder로 둔다. 차이는 시기다. SGLang은 v0.4(2024년 12월)에서 이 방식을 "zero-overhead batch scheduler"로 기본으로 켰다([LMSYS 블로그](https://lmsys.org/blog/2024-12-04-sglang-v0-4/)). vLLM에서 async scheduling이 기본값이 된 것은 2025년 가을 이후다.

### 7. 종료 판정과 출력: stop string은 scheduler가 찾는다

batch 결과는 [`process_batch_result_decode()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler_components/batch_result_processor.py#L942) 같은 함수가 처리한다. request마다 새 token을 `output_ids`에 붙이고 [`Req.update_finish_state()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L1913)로 끝났는지 본다. 검사 순서는 vocab 범위, stop string, stop token과 EOS, `max_new_tokens`, grammar 종료다.

stop string 검사는 [`_check_str_based_finish()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L1829)가 한다. 이 함수는 출력의 끝 몇 token을 scheduler 안의 tokenizer로 decode해 stop string이 있는지 찾는다. 그래서 scheduler process도 tokenizer를 들고 있다.

그 다음 [`stream_output()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler_components/output_streamer.py#L119)이 batch 전체의 새 token과 종료 이유를 `BatchTokenIDOutput` 하나로 묶어 detokenizer로 보낸다. [`DetokenizerManager`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/detokenizer_manager.py#L103)는 request마다 [`DecodeStatus`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/detokenizer_manager.py#L76)에 offset을 두고 incremental detokenize를 한다. token 하나가 완성된 글자가 아닐 수 있으므로(예: UTF-8 한 글자가 token 두 개로 나뉜 경우), 앞 몇 token을 함께 decode한 뒤 새로 늘어난 text만 내보낸다. 끝난 request는 출력 끝의 stop string을 잘라 낸다. 결과 `BatchStrOutput`은 TokenizerManager로 가고, streaming이면 SSE chunk가 된다.

#### vLLM과 다른 점: 종료 판정이 모두 GPU 쪽 process에 있다

vLLM은 stop token과 길이 제한은 EngineCore가, stop string은 API server의 detokenizer가 본다. stop string으로 끝나면 API server가 EngineCore에 abort를 보내 KV를 정리하게 한다. SGLang은 모든 종료 판정을 scheduler가 한다. 그래서 종료와 KV 반납이 같은 자리에서 일어나고, 별도의 abort 왕복이 없다. 대신 stop string이 있는 request가 많으면 scheduler의 CPU가 decode 비용을 진다. overlap loop가 이 CPU 시간을 GPU 뒤에 숨긴다.

### 8. 종료와 abort: KV를 tree에 넘기고 lock을 푼다

끝난 request는 [`release_kv_cache()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/common.py#L378-L417)를 거친다. 하는 일은 이렇다.

1. `tree_cache.checkpoint()`로 계산을 마친 token과 KV slot을 tree에 넣는다. 이 slot들은 이제 tree의 것이다.
2. tree에 넣지 않은 나머지 slot(예: 꽉 차지 않은 마지막 page, speculative decoding이 미리 잡아 둔 slot)을 반납한다.
3. request가 잡고 있던 tree 경로의 lock을 푼다.
4. `req_to_token_pool`의 request 행을 반납한다.

client가 연결을 끊으면 abort가 일어난다. streaming 응답에는 연결이 끊긴 뒤 request가 아직 살아 있으면 abort를 보내는 background task가 [붙어 있다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L2425). TokenizerManager의 [`abort_request()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/tokenizer_manager.py#L2240)가 scheduler로 `AbortReq`를 보내고, scheduler는 waiting queue에 있으면 바로 빼고, 실행 중이면 종료로 표시해 위 경로로 정리한다.

## KV cache 메모리와 batch

앞에서 tree의 node가 KV slot 번호를 들고 있다고 했다. 이 파트는 그 slot이 어디에 있고, request와 attention kernel이 그것을 어떻게 찾는지 본다.

### 1. 두 단계 pool: req_to_token과 KV pool

SGLang의 KV 메모리는 두 단계로 나뉜다. request마다 token 위치표가 한 행씩 있고, 그 표가 KV pool의 slot을 가리킨다. 그림은 앞의 radix tree 예시를 조금 바꿔, B가 끝나기 전에 C가 들어와 둘이 함께 decode하는 순간을 그린다. B는 S0-S3을, C는 S0-S3 a0 a1을 tree에서 재사용하므로 두 행이 slot 1-4를 함께 가리킨다.

<Figure
  src="/assets/images/post/2026-10-31-Inside-sglang/05-two-level-pool-light.svg"
  darkSrc="/assets/images/post/2026-10-31-Inside-sglang/05-two-level-pool-dark.svg"
  caption="B와 C가 함께 decode하는 순간의 두 단계 pool. 두 request의 행이 slot 1-4를 함께 가리킨다."
/>

- **KV pool**([`MHATokenToKVPool`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/memory_pool.py#L2198)): layer마다 K tensor 하나와 V tensor 하나다. 기본 layout에서 shape은 `(slot 수 + page_size, KV head 수, head 크기)`다. slot 하나가 token 하나의 KV를 담는다. slot 0은 CUDA graph padding이 쓰는 자리로 비워 둔다.
- **ReqToTokenPool**([`ReqToTokenPool`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/memory_pool.py#L374)): `req_to_token`이라는 GPU int32 tensor 하나다. shape은 `(최대 request 수 + 1, 최대 context 길이)`이고, `req_to_token[행, 위치]`가 그 request의 그 위치 token의 KV slot 번호다. 행 0은 padding용이다.

request는 시작할 때 행 하나를 받는다. prefill은 [`prepare_for_extend()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L2730)에서 tree가 match한 slot을 행 앞쪽에 쓰고, 새로 할당한 slot을 그 뒤에 쓴다. decode는 [`prepare_for_decode()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L3563)에서 request마다 slot 하나를 받아 `req_to_token[행, seq_len]`에 쓴다. 이번 forward가 새 KV를 쓸 slot 목록이 `out_cache_loc`이다.

attention backend는 `req_to_token`을 직접 읽는다. `ForwardBatch`에는 batch의 행 번호(`req_pool_indices`)와 길이(`seq_lens`, prefill이면 `extend_prefix_lens`, `extend_seq_lens`도)가 들어 있고, backend는 이것으로 request마다 KV slot 목록을 만든다. 예를 들어 FlashAttention backend는 `req_to_token`에서 page_size 간격으로 slot을 뽑아 page table을 만든다. `page_size`가 1이면 slot 번호가 그대로 page 번호다([코드](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/layers/attention/flashattention_backend.py#L773-L782)).

기본 attention backend는 [`get_default_attn_backend()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/model_override_base.py#L268)가 GPU에 따라 고른다. Hopper(H100, H200)는 [`fa3`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/model_override_base.py#L296-L302)다. 주석은 FlashInfer 0.6.1의 Hopper 성능 저하를 이유로 든다. Blackwell은 `trtllm_mha`, 그 밖에는 FlashInfer가 있으면 FlashInfer, 없으면 Triton이다.

#### vLLM과 다른 점: block table 대신 token 단위 위치표

vLLM은 request마다 block ID 목록(block table)을 두고, token 위치를 `block_table[pos // 16] * 16 + pos % 16`으로 바꾼다. step마다 새 token이 쓸 위치 목록(`slot_mapping`)도 따로 만든다. SGLang은 page_size 1에서 token 위치마다 slot 번호를 바로 적는다. SGLang의 `out_cache_loc`이 vLLM의 `slot_mapping`에 해당하고, `req_to_token`이 block table을 대신한다.

token 단위 표는 tree의 token 단위 공유와 짝을 이룬다. tree가 어느 token에서든 split할 수 있으려면, request의 KV 위치도 token 단위로 적혀 있어야 한다. 대신 표가 크다. 최대 request 수 * 최대 context 길이만큼 int32를 미리 잡는다. vLLM의 block table은 같은 정보를 16분의 1 크기로 담는다.

### 2. allocator: 빈 slot 목록은 GPU tensor다

빈 slot은 [`TokenToKVPoolAllocator`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocator/token.py#L28)가 관리한다. 목록은 Python 자료구조가 아니라 GPU의 int64 tensor다.

```python
self.free_pages = torch.arange(1, self.size + 1, dtype=torch.int64, device=self.device)
```

할당은 앞에서 [잘라 내고](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocator/token.py#L61-L62), 반납은 뒤에 이어 붙인다. 할당한 slot 번호가 처음부터 GPU tensor이므로, `out_cache_loc`과 `req_to_token`을 채울 때 slot 번호를 CPU에서 GPU로 옮기지 않아도 된다. 빈 slot이 모자라면 allocator가 tree에 evict를 요청한다. `page_size`가 1보다 크면 [`PagedTokenToKVPoolAllocator`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocator/paged.py#L136)를 쓰고, decode에서 request가 page 경계를 넘을 때만 새 page를 받는다.

이 구조에서 메모리 낭비라는 의미의 fragmentation(조각화)은 거의 없다. `page_size`가 1이면 slot 하나가 token 하나이므로, 덜 찬 block에 남는 빈 칸(내부 fragmentation)이 없다. 빈 slot이 메모리 곳곳에 흩어져도 할당에는 문제가 없다(외부 fragmentation). attention이 `req_to_token` 표로 slot을 하나씩 찾아가므로, request의 slot이 연속일 필요가 없기 때문이다.

대신 흩어짐은 성능 비용으로 나타날 수 있다. 반납된 slot은 free list 끝에 그대로 [붙고](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocator/token.py#L65-L75), 정렬은 PD disaggregation 모드에서만 [한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/kv_cache_configurator.py#L887). 그래서 서버가 오래 돌면 한 request의 KV가 KV pool 여기저기 흩어지고, attention kernel은 떨어진 위치를 token마다 따로 읽는다. 이 때문에 얼마나 느려지는지는 측정 근거를 찾지 못했다. FlashMLA처럼 큰 page를 요구하는 backend가 `page_size`를 64 같은 값으로 강제하는 것도 이런 접근 효율 때문으로 보인다.

<Figure
  src="/assets/images/post/2026-10-31-Inside-sglang/13-free-list-light.svg"
  darkSrc="/assets/images/post/2026-10-31-Inside-sglang/13-free-list-dark.svg"
  caption="free list가 흩어지는 과정. 반납된 slot이 정렬 없이 뒤에 붙어, 다음 request가 떨어진 slot을 받는다."
/>

#### vLLM과 다른 점: 재사용 순서를 allocator가 아니라 tree가 정한다

vLLM의 free block queue는 직접 만든 이중 연결 리스트다. prefix cache로 쓸 수 있는 block도 이 queue 뒤쪽에 들어가고, 할당은 앞에서 꺼내므로 queue 순서가 곧 LRU eviction이다. 그래서 cache hit가 나면 queue 중간의 block을 O(1)에 빼야 한다. SGLang의 free list에는 정말 빈 slot만 있다. cache로 남은 slot은 tree가 들고 있고, 지울 순서는 tree의 eviction heap이 정한다. free list와 cache를 분리했으니 free list는 단순한 tensor로 충분하다.

### 3. chunked prefill: 조각마다 tree에 넣는다

prompt가 `chunked_prefill_size`보다 길면 `PrefillAdder`가 앞부분만 batch에 넣고 그 request를 [`chunked_req`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/scheduler.py#L1336)로 기억한다. 다음 prefill batch는 [`add_chunked_req()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_policy.py#L1092)로 이 request를 가장 먼저 이어 넣는다.

조각 하나가 끝날 때마다 `checkpoint_kv_cache()`가 그때까지 계산한 부분을 tree에 넣고, request는 tree의 새 끝 node를 lock한다. request는 `req_to_token` 행을 그대로 유지한다. 효과는 두 가지다. 같은 문서를 가진 다른 request가 조각 계산 도중에 들어와도 이미 끝난 조각을 재사용할 수 있다. 그리고 조각 사이에 메모리가 모자라도 이미 계산한 앞부분은 lock 덕분에 지워지지 않는다.

#### vLLM과 다른 점: 조각만 담은 batch를 돌린다

chunked prefill이 기본으로 prefill batch에만 적용된다는 점은 vLLM과 다르다. vLLM은 chunked prefill의 조각을 decode token과 같은 step에 넣는다. SGLang은 기본으로 조각만 담은 EXTEND batch를 돌리고, 그동안 decode는 쉰다.

### 4. 멀티턴 대화: session 없이 tree가 재사용한다

멀티턴 대화에서 두 번째 턴은 서버 입장에서 새 request다. client가 이전 대화를 `messages`에 다시 담아 보내면, main process가 전체를 다시 token화하고 scheduler가 tree에서 match한다. 첫 번째 턴의 prompt와 답변은 끝날 때 checkpoint로 tree에 들어갔으므로 대부분 맞는다. 새로 prefill하는 것은 처음으로 token이 어긋나는 곳부터다.

다시 계산하는 부분이 생기는 경우는 세 가지다.

- 마지막 token: tree에는 KV를 계산한 token까지만([`kv_committed_len`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/managers/schedule_batch.py#L1491-L1503)) 들어간다. 마지막으로 sampling한 token은 다음 forward에 들어가야 KV가 생기므로, 첫 번째 턴이 그 전에 끝나면 이 token은 두 번째 턴에서 계산하는 것으로 보인다.
- token이 달라지는 경우: 답변을 text로 바꿨다가 다시 token화하면 생성할 때와 다른 token이 나올 수 있다. chat template이 턴 끝에 특수 token을 넣기도 한다. 그 지점부터는 다시 계산한다.
- eviction: 턴 사이에 다른 request가 많이 들어와 메모리가 모자라면, 오래 안 쓴 가지부터 지워진다.

명시적인 session도 있다. `--enable-streaming-session`을 켜면 [`StreamingSession`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/session/streaming_session.py#L52)이 첫 턴의 `req_to_token` 행과 tree lock을 붙잡아 두고, 다음 턴은 tree match 없이 그 행을 이어서 쓴다. 턴 사이에 eviction으로 KV를 잃지 않는다는 보장이 생긴다. 기본은 꺼져 있다.

#### vLLM과 다른 점: 덜 찬 block을 버리지 않는다

`page_size`가 1이므로 vLLM과 달리 꽉 차지 않은 block을 버리지 않는다. vLLM은 첫 번째 턴 끝의 최대 15 token을 다시 계산하지만, SGLang에서 다시 계산하는 끝부분은 많아야 몇 token이다.

### 5. speculative decoding: draft도 같은 slot 번호를 쓴다

speculative decoding은 작은 draft model이 token 몇 개를 먼저 추측하고, 본 model이 한 forward로 검증하는 기법이다. SGLang의 대표 경로는 EAGLE이다. draft worker는 본 model과 [`req_to_token_pool`을 공유하고](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/kv_cache_configurator.py#L710), allocator도 같은 것을 쓴다. draft model의 KV는 별도의 KV pool tensor에 있지만, 같은 slot 번호로 찾는다.

decode마다 draft token을 위한 자리를 [두 step 분량만큼 미리 잡는다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocation_sizing.py#L64-L70). overlap loop에서 결과가 한 step 늦게 오므로 여유를 하나 더 두는 것이다. 검증에서 틀린 draft token의 slot은 매 step 반납하지 않는다. 다음 step이 그 자리를 덮어쓰고, request가 끝날 때 남은 초과분을 [한꺼번에 반납한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/common.py#L378-L417). tree에는 검증을 통과한 token만 들어간다.

#### vLLM과 다른 점: 거의 같다

vLLM도 draft의 KV를 본 model과 같은 pool에 두고, 틀린 draft의 KV를 덮어쓴다. 이 부분은 두 엔진이 거의 같다.

### 6. HiCache와 PD disaggregation: KV가 GPU 밖으로 나갈 때

**HiCache**(hierarchical cache)는 radix tree를 GPU 메모리 밖으로 늘린다. GPU 메모리(L1) 아래에 host 메모리(L2)를 두고, 필요하면 file, Mooncake, 3FS 같은 storage(L3)까지 둔다. `--enable-hierarchical-cache`로 켜고, 기본은 꺼져 있다. 동작은 SGLang 팀의 [HiCache 글](https://www.sglang.io/blog/hicache)이 그림과 함께 잘 설명하므로, 여기서는 v0.5.22 기본값과 함께 요점만 정리한다.

- tree가 KV의 위치를 안다. match가 L1에 있는 node에 닿으면 그대로 쓰고, L2에 있으면 GPU로 올리고, L3에 있으면 host로 읽은 뒤 GPU로 올린다.
- GPU에서 host로 언제 복사할지는 write policy가 정한다. 기본값은 KV가 cache에 들어올 때 바로 복사하는 [`write_through`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/memory.py#L118-L124)다. 자주 맞는 prefix만 복사하는 `write_through_selective`와, GPU에서 지울 때 복사하는 `write_back`도 있다.
- host에서 GPU로 올릴 때는 layer 하나씩 올린다. 그래서 GPU는 layer 0을 계산하는 동안 다음 layer의 KV를 받는다. 이 복사는 기본으로 전용 GPU kernel이 한다(`--hicache-io-backend kernel`).
- L3 읽기가 제때 끝나지 않을 때의 처리는 prefetch policy가 정한다. 기본값은 정해진 시간까지만 기다리는 [`timeout`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/memory.py#L167-L174)이다. 끝난 부분만 쓰고 나머지를 다시 계산하는 `best_effort`, 끝까지 기다리는 `wait_complete`도 있다.
- L3는 기본으로 붙지 않는다(`--hicache-storage-backend`의 기본값은 `None`). host의 KV는 L3 입출력에 맞게 page 단위로 모아 두는 [`page_first`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/memory.py#L132-L144) layout이 기본이다.

같은 글은 DeepSeek-V4-Flash 멀티턴 benchmark에서 L3까지 붙이면 실효 입력 처리량이 GPU만 쓸 때의 15.5배가 된다고 보고한다. 이 처리량에는 cache에서 읽은 token도 포함되므로, 계산 자체가 15.5배 빨라졌다는 뜻은 아니다.

**PD disaggregation**은 prefill과 decode를 서로 다른 instance에서 돌린다. prefill은 계산량이 많고 decode는 메모리 대역폭을 많이 써서, 나누면 각각에 맞게 GPU를 쓸 수 있다. SGLang은 [`disaggregation/`](https://github.com/sgl-project/sglang/tree/v0.5.22/python/sglang/srt/disaggregation)에 prefill 서버와 decode 서버의 queue를 따로 둔다. decode 서버는 request가 오면 KV slot을 먼저 할당하고, bootstrap 서버로 prefill 서버와 주소를 교환한 뒤, prefill 서버가 그 slot으로 KV를 직접 보낸다. 전송 backend는 기본이 [Mooncake](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/disagg.py#L65-L71)이고, NIXL 등을 고를 수 있다.

#### vLLM과 다른 점: plugin 대신 별도 event loop를 쓴다

vLLM은 같은 일을 KV connector라는 plugin 인터페이스로 한다. scheduler는 connector에 "원격에서 받을 수 있는 token 수"를 묻고, 전송은 connector가 맡는다. SGLang은 disaggregation을 scheduler의 별도 event loop와 queue로 구현했다. 확장 지점의 모양이 다르다.

### 7. padding이 남는 곳: CUDA graph

decode batch는 CUDA graph로 재생한다. graph는 capture한 batch 크기로만 재생할 수 있으므로, 실제 batch 크기를 capture한 크기 중 가장 가까운 큰 값으로 [올린다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/model_executor/runner/base_cuda_graph_runner.py#L162-L170). batch 13이면 16짜리 graph를 쓰고 3개를 padding한다. padding 자리는 `req_to_token`의 행 0과 KV pool의 slot 0을 가리키므로, 실제 request의 KV를 건드리지 않는다. 앞에서 행 0과 slot 0을 비워 둔 이유가 이것이다.

#### vLLM과 다른 점: request 수로 padding한다

vLLM도 같은 방식으로 batch 끝에만 padding한다. 다만 vLLM은 prefill과 decode가 섞인 step의 token 수를 기준으로 맞추고, SGLang은 decode batch의 request 수를 기준으로 맞춘다. 한 forward가 decode만 담는 SGLang에서는 request 수가 곧 token 수다.

### 8. 여러 종류의 attention: 종류별 pool 위에 tree 하나를 둔다

SGLang은 attention 종류가 섞인 model을 두 층으로 다룬다. 아래 층은 종류별로 따로 둔 물리적인 pool이고, 위 층은 그 pool들을 함께 가리키는 radix tree 하나다. tree node에는 종류별 데이터(component)를 붙인다. 앞에서 본 KV pool, `req_to_token`, allocator가 이 절의 재료다.

이런 구조가 필요한 이유는 종류마다 남겨야 할 것이 다르기 때문이다. full attention은 모든 token의 KV, sliding window attention(SWA, 최근 window 크기만큼의 token만 보는 attention)은 마지막 window 안의 KV, Mamba 같은 state space layer는 마지막 위치의 state 하나만 있으면 된다. 2026년의 주요 open model은 대부분 이런 layer를 섞는다. 긴 context에서 KV cache와 attention 비용을 줄이려고, full attention layer는 일부만 남기고 나머지를 더 가벼운 layer로 바꾸기 때문이다. SGLang v0.5.22가 지원하는 model은 크게 두 부류다.

- SWA를 섞는 model: Gemma 4, MiMo-V2-Flash, DeepSeek-V4.1 등이다. DeepSeek-V4.1은 config를 읽을 때 architecture 이름이 DeepSeek-V4와 같은 것으로 [바뀌어](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/configs/deepseek_v41.py#L36-L39) 같은 경로를 탄다. SGLang은 이 architecture들을 [목록](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/configs/model_config.py#L2536-L2563)으로 들고 있다가 hybrid SWA 메모리를 켠다.
- state를 쓰는 layer를 섞는 model: Qwen 3.8 계열은 Gated DeltaNet이라는 linear attention을, Kimi K3와 GLM-5.3-Flash는 Kimi Delta Attention(KDA) 방식의 linear attention을, Nemotron-H 계열은 Mamba2를 full attention과 섞는다. 코드에서 Qwen 3.8은 `Qwen4Exp`, GLM-5.3-Flash는 `Glm5Next`라는 이름으로 들어 있다. GLM-5.3-Flash는 이름과 달리 DSA 하나만 쓰는 GLM-5.2·GLM-5.3과 다른 구조의 model이다. 이런 layer는 token마다 KV를 쌓지 않고 request마다 고정 크기 state 하나를 들고 간다. SGLang은 이것들을 [하나의 조건](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/kv_cache_builder.py#L154-L165)으로 묶어 같은 Mamba 경로로 다룬다. 이 글에서도 Mamba 계열이라고 부른다.

아래 그림은 세 종류를 모두 가진 model을 가정한다. 위쪽은 tree node 세 개와 그 node에 붙은 종류별 데이터이고, 아래쪽은 종류별 pool이다.

#### 아래 층: 종류별 pool을 layer_id로 고른다

SWA를 섞은 model은 [`SWAKVPool`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/swa_memory_pool.py#L21)을 쓴다. 이 pool은 full attention layer용 pool과 SWA layer용 pool을 [따로 들고 있고](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/swa_memory_pool.py#L84-L95), 두 pool의 token 수가 다르다. SWA pool의 크기는 `--swa-full-tokens-ratio`로 정하고, 기본값은 full pool의 [0.8배](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/schedule.py#L146-L159)다. 각 layer가 어느 pool을 쓰는지는 [`layers_mapping`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/swa_memory_pool.py#L106-L111)이 정한다.

request의 위치표인 `req_to_token`은 하나뿐이고, full pool의 slot 번호만 담는다. SWA layer는 [`full_to_swa_index_mapping`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocator/swa.py#L100-L111)으로 full slot 번호를 SWA slot 번호로 바꿔 읽는다. 예를 들어 FlashAttention backend는 forward마다 page table을 한 번 변환해 SWA layer용 page table을 [따로 만든다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/layers/attention/flashattention_backend.py#L1243-L1250). allocator([`SWATokenToKVPoolAllocator`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocator/swa.py#L34))도 두 pool의 free list를 따로 관리하고, 할당할 때 이 변환표를 함께 채운다. 실행 중인 request가 window 밖으로 밀어낸 SWA slot은 request가 끝나기 전에도 [반납한다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_cache/components/swa.py#L1005-L1024).

Mamba를 섞은 model은 state를 [`MambaPool`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/memory_pool.py#L503)에 둔다. 이 pool의 단위는 token이 아니라 request다. 여기서 Mamba slot은 token 하나의 자리가 아니라 request 하나의 state 자리다. allocator 주석도 "slots are per request, not per token"이라고 적는다([`MambaSlotAllocator`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/allocator/mamba.py#L30-L33)). request 행과 Mamba slot의 대응은 [`HybridReqToTokenPool`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/memory_pool.py#L1369)이 관리한다. Mamba pool과 KV pool의 메모리 비율은 `--mamba-full-memory-ratio`로 정하고, 기본값은 [0.9](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/fields/schedule.py#L214-L221)다.

#### 위 층: tree node마다 종류별 데이터를 붙인다

[`create_unified_radix_cache()`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/registry.py#L165-L170)는 model을 보고 tree에 붙일 component를 정한다. FULL은 항상 붙고, SWA를 섞었으면 SWA를, state space layer를 섞었으면 MAMBA를 붙인다. node는 component마다 데이터를 따로 가진다. FULL은 full pool slot 번호, SWA는 SWA pool slot 번호, MAMBA는 그 node 위치의 state가 저장된 slot 번호다. component마다 lock 수와 "지울 수 있는 크기"도 따로 센다.

components README는 설계 목표를 이렇게 적는다([`components/README.md`](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_cache/components/README.md)). "Zero special-casing in the main tree — The tree operates purely on keys (logical). All physical resource management (allocation, freeing, copy-on-write) is handled by components through hooks." tree는 token 열만 알고, 메모리를 할당하고 반납하는 일은 component가 hook으로 맡는다. 새 종류의 cache를 지원하려면 component 하나만 더하면 된다.

이 설계의 배경은 LMSYS의 [Unified Radix Cache 글](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/)(2026년 8월)이 잘 설명한다. 예전에는 hybrid model의 조합마다 cache class를 따로 만들었다. 글은 이것이 "a combinatorial class matrix"를 만들고, match, insert, lock, eviction 로직을 class마다 중복시켰다고 적는다. 그래서 prefix가 같은지(tree 구조)와 그 prefix를 실제로 다시 쓸 수 있는지(component별 validator)를 나눴다는 것이 글의 요지다. 다만 그 글을 쓸 때는 unified tree가 `SGLANG_ENABLE_UNIFIED_RADIX_TREE=1`로 켜는 opt-in이었고, Rust core도 실험 단계라 full attention의 GPU 계층만 지원했다. v0.5.22에서는 이 환경 변수가 ["The unified radix tree is the default tree cache now"](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/environ.py#L2033-L2035)라는 안내와 함께 deprecated되었고, Rust core가 기본이며 SWA와 Mamba component도 Rust 쪽에 [들어 있다](https://github.com/sgl-project/sglang/tree/v0.5.22/rust/sglang-radix-tree/src/components). 글의 benchmark도 그때의 구현으로 잰 것이다.

match는 component마다 validator를 하나씩 받는다. tree를 따라 내려가면서 node마다 모든 validator에 묻고, 모두 "여기서 끝나도 된다"고 답하는 가장 깊은 node에서 match를 끝낸다.

- FULL: KV가 있으면 언제나 된다.
- SWA: hit 끝 바로 앞의 window 크기만큼 SWA KV가 이어져 있어야 [된다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_cache/components/swa.py#L349-L372). SWA KV가 지워진 node(tombstone)를 만나면 센 길이를 0으로 되돌린다. 그림의 node 2까지는 4 token뿐이라 안 되고, node 3에서 8 token이 되어 통과한다.
- MAMBA: 그 node에 state가 저장되어 있어야 [된다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/mem_cache/unified_cache/components/mamba.py#L147-L158). Mamba state는 마지막 위치 하나만 의미가 있으므로, 중간 위치에서 이어 계산하려면 그 위치의 state가 따로 저장되어 있어야 한다. match가 끝나면 그 state를 request의 새 slot으로 복사해(copy-on-write) 이어 계산한다.

Mamba state는 매 token마다 저장할 수 없으므로, 언제 저장할지가 문제다. SGLang은 정해진 간격의 위치에서만 state를 저장해 tree에 남긴다. 간격은 model config의 Mamba chunk 크기(없으면 64)와 page 크기 중 큰 값에서 [정해진다](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/overrides.py#L1844-L1870). 저장 방식은 `--mamba-radix-cache-strategy`로 고르고, 기본값 `auto`는 model과 overlap scheduling 지원 여부를 보고 정한다.

eviction은 component마다 우선순위가 있고, 높은 쪽을 지우면 낮은 쪽도 함께 지워진다. 중간 node에서는 FULL이 가장 높고, 그 다음이 SWA, MAMBA 순이다. 그래서 중간 node의 SWA KV만 지우면 FULL KV는 남고 SWA 자리는 tombstone이 된다. 그 node는 full attention에는 여전히 쓸모 있지만, SWA validator는 그 node를 지나면 길이를 다시 센다. leaf에서는 모든 component를 함께 지우고 node를 없앤다.

#### vLLM과 다른 점: group으로 나누는가, component를 붙이는가

vLLM은 layer를 종류별 KV cache group으로 나눈다. group마다 manager와 block table이 따로 있고, prefix cache도 group마다 따로 hash를 매긴다. 메모리는 반대로 하나다. 모든 group이 page size를 맞추고, 같은 block ID 공간과 같은 bytes를 함께 쓴다. prefix hit는 group마다 따로 찾은 뒤, 모든 group이 동의할 때까지 길이를 줄여 맞춘다([Inside vLLM](https://blog.liam.kim/posts/2026/10/Inside-vLLM/#8-여러-종류의-attention-kv-cache-group과-타입별-manager)).

SGLang은 그 반대다. 메모리는 종류별 pool로 나누고, 논리 구조는 하나의 tree로 모은다. prefix hit도 tree를 한 번 내려가면서 모든 component에 묻는다.

| | vLLM | SGLang |
| --- | --- | --- |
| 물리 메모리 | 하나의 block pool, group들이 같은 bytes를 나눠 씀 | 종류별 pool (full, SWA, Mamba) |
| 종류별 메모리 비율 | 정하지 않음. block ID를 필요한 group이 가져감 | 미리 정함 (`swa_full_tokens_ratio`, `mamba_full_memory_ratio`) |
| 종류별 규칙의 위치 | group별 `SingleTypeKVCacheManager` | tree node의 component와 hook |
| request의 KV 위치 | group별 block table | `req_to_token` 하나 + full→SWA 변환표 |
| prefix hit | group별로 찾고 fixed-point loop로 맞춤 | tree를 한 번 내려가며 모든 validator가 동의하는 곳 |
| 일부 종류만 지움 | group별 block hash가 따로 지워짐 | tombstone (FULL은 남고 SWA만 지움) |

어느 쪽에도 대가가 있다. vLLM은 종류별 비율을 정할 필요가 없어서 workload가 바뀌어도 메모리가 남지 않는다. 대신 모든 group의 page size를 맞추느라 block 크기를 키우거나 padding해야 한다. SGLang은 종류마다 pool 모양을 자유롭게 고를 수 있고, 같은 token 열에 대한 종류별 상태를 한 node에서 본다. 대신 SWA와 full의 비율을 미리 정해야 하고, 비율이 workload와 맞지 않으면 한쪽 pool이 먼저 찬다. SGLang에는 하나의 메모리를 종류별 pool이 동적으로 나눠 쓰는 `--enable-unified-memory` 옵션도 있지만, v0.5.22에서는 기본으로 꺼져 있다.

같은 model이라도 두 엔진이 잡는 메모리가 다를 수 있다. Gemma 2, Gemma 3, Gemma 3n은 SGLang v0.5.22에서 hybrid SWA 메모리를 쓰지 않는다. [override](https://github.com/sgl-project/sglang/blob/v0.5.22/python/sglang/srt/arg_groups/model_overrides/gemma2_gemma3.py#L15-L26)가 "not yet supported"라는 경고와 함께 끈다. 그래서 이 model들은 모든 layer에 full attention만큼 KV를 잡는다. Gemma 4는 hybrid SWA 목록에 들어 있어 SWA pool을 따로 쓴다. 반면 vLLM은 hybrid manager 설계 문서에서 Gemma 3를 예시로 들고, sliding window layer의 KV를 window만큼만 잡는다. 그래서 Gemma 3를 띄우면 vLLM이 같은 GPU에 더 많은 token을 담는다.

## 정리: vLLM과 SGLang의 차이

| 주제 | vLLM v0.32.0 | SGLang v0.5.22 |
| --- | --- | --- |
| 출발점 | PagedAttention: block으로 메모리 낭비 줄이기 | RadixAttention: prefix KV 재사용 |
| process | API server, EngineCore (2개) | main, scheduler, detokenizer (3개, ZMQ 고리) |
| 소켓 open | 엔진 준비 전 bind, 준비 후 listen | 엔진 준비 후 생성, warmup 뒤 healthy |
| KV cache 크기 | dummy forward로 profiling | `mem_fraction_static` 비율로 추정 |
| prefix cache | 16 token block hash 표 | token 단위 radix tree |
| 공유 표시와 eviction | block `ref_cnt`, free queue 순서 LRU | 경로 `lock_ref`, leaf heap LRU |
| request의 KV 위치 | block table + `slot_mapping` | `req_to_token` + `out_cache_loc` |
| waiting queue 순서 | FCFS, priority | 기본 FCFS. LPM, DFS-weight로 cache-aware 가능 |
| batch 구성 | prefill과 decode를 한 step에 섞음 | 기본으로 EXTEND 우선, DECODE 따로 |
| 메모리 부족 대응 | step마다 할당, 모자라면 preempt | `new_token_ratio`로 예약, 틀리면 retract |
| CPU와 GPU 겹치기 | async scheduling (v0.32.0부터 기본) | overlap loop (v0.4부터 기본) |
| stop string | API server의 detokenizer | scheduler |
| PD disaggregation | KV connector plugin | 전용 queue와 transfer backend |
| 여러 종류의 attention | 종류별 group과 manager, 메모리는 하나 | 종류별 pool, tree node의 component |

## 마치며

이 글은 SGLang v0.5.22에서 `sglang serve` 한 줄이 세 process를 띄우고, chat request 하나가 token이 되어 돌아오기까지를 따라갔다. 그리고 그 아래의 radix tree와 두 단계 KV pool을 봤다.

한 문장으로 줄이면, SGLang은 KV cache를 "request가 쓰고 버리는 메모리"가 아니라 "request 사이에서 재사용하는 cache"로 다룬다. radix tree가 그 cache를 token 단위로 관리하고, scheduler는 tree를 보고 request를 받고, 정렬하고, 내보낸다. vLLM이 block 단위 메모리 관리 위에 prefix caching을 얹었다면, SGLang은 prefix tree 위에 메모리 관리를 얹었다.

어느 쪽이 나은지는 workload가 정한다. system prompt, few-shot 예시, 멀티턴 대화, agent loop처럼 prefix 공유가 많고 그 공유가 block 경계와 맞지 않는 경우에는 SGLang의 tree가 유리하다. decode 지연이 일정해야 하는 서비스라면 prefill과 decode를 한 step에 섞는 vLLM의 기본 방식이 유리할 수 있다. SGLang에서 같은 효과를 원한다면 `--enable-mixed-chunk`와 `chunked_prefill_size`를 먼저 조정해 보면 된다.

다음 글에서는 vLLM 글에서 예고한 대로 GPU 여러 개를 쓸 때의 NCCL 초기화와, FlashInfer 같은 attention backend가 이 글의 `req_to_token`과 vLLM의 block table을 어떻게 받아들이는지 볼 예정이다.
