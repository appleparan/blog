## Introduction

예전에 [Inside vLLM: Anatomy of a High-Throughput LLM Inference System](https://www.aleksagordic.com/blog/vllm)을 읽고는 '아, 그렇구나' 하고 넘어간 적이 있다. 그런데 막상 누군가에게 설명하려니 말이 제대로 나오지 않았다. 예전에 비슷한 내용을 [코드](https://github.com/appleparan/nano-vllm-rs)를 통해서도 공부하고 작동원리를 이해했다고 생각했지만, 정작 내가 설명할 때는 기억도 잘 나지 않고, 코드도 다 안뜯어봐서 디테일도 없었고 많이 부끄러웠다.

이럴 때 가장 좋은 방법은 역시 직접 글로 정리해 보는 것이다. 코드를 따라가며 이해한 내용을 내 방식대로 풀어 쓰다 보면, 적어도 쉽게 잊어버리지는 않는다.

게다가 위 글은 2025년 가을의 글이고, 그사이 vLLM에는 큰 변화가 많았다. V0 engine이 완전히 제거되어 V1만 남았고, async scheduling이 기본으로 켜졌으며, Model Runner V2가 모든 model의 기본 실행 경로가 되었다. Python API server를 대신할 Rust frontend도 실험 기능으로 들어왔다. 따라서 이번에는 2026년 10월, vLLM v0.32.0을 기준으로 내부 아키텍처를 다시 살펴보려 한다.

이번 글은 설명을 요약하는 대신, vLLM 소스 코드를 직접 열어 보며 따라간다.

## 큰 그림

LLM은 token을 하나씩 만든다. request(요청)는 이 token 생성을 묶은 단위다. prompt를 받아 output token을 끝까지 만들어 내는 일 전체가 request 하나다. vLLM은 이 request를 한꺼번에 처리하지 않고 step으로 다시 쪼갠다. step은 GPU forward 한 번이고, step 한 번에 각 request는 자기 token을 몇 개씩만 계산한다. 그래서 request 하나는 여러 step에 걸쳐 끝나고, step 하나에는 여러 request의 token이 함께 들어간다.

코드를 따라가기 전에 이 관계와, 이것을 돌리는 전체 구조부터 보고 가자.

### step: LLM request를 쪼개는 단위

그 전에 vLLM이 request를 어떻게 처리하는지부터 알아야 한다. vLLM 구조를 이해하는 출발점은 LLM request 하나를 여러 step으로 쪼갠다는 점이다. vLLM은 request 단위가 아니라 step이라는 시간 단위로 일한다. request를 하나씩 끝까지 처리하지 않고, step을 돌리면서 step 한 번에 살아 있는 request 전부를 한꺼번에 조금씩 진행시킨다. prefill 중인 request는 prompt token을 한 조각 더 계산하고, decode 중인 request는 다음 token을 하나 더 만든다.

풀어 쓰면 이렇다.

1. **Step은 엔진의 기본 실행 단위다.** CPU의 clock과 비슷하게 엔진의 실행 주기를 나타내며, 이하 모든 step은 이 단위를 의미한다.
2. **매 step마다 엔진은 처리할 request와 token을 선택한다.** 선택된 token들을 하나의 GPU forward pass로 처리하고, request마다 다음 token을 하나씩 생성한다.
3. **하나의 request는 여러 step에 걸쳐 처리된다.** 먼저 입력 token들을 처리하는 prefill을 수행하고, 이후 매 step에서 decode를 반복하며 출력 token을 생성한다.
4. **한 step에는 여러 request가 함께 처리될 수 있다.** 수백 개의 request가 하나의 batch에 포함될 수 있으며, 긴 request 하나가 GPU를 독점하지 않고 다른 request들과 연산 자원을 공유한다.

### vLLM 컴포넌트

이 step을 돌리는 vLLM 서버는 아래 그림처럼 두 프로세스와 GPU로 나뉜다. 그림은 API server 하나와 EngineCore 하나를 쓰는 uni executor 구성이다.

/>

그림의 상자를 위에서부터 차례로 보면 이렇다.

- **API server 프로세스**는 HTTP request를 엔진 request로, 엔진 출력을 HTTP 응답으로 바꾼다.
    - **FastAPI app**: FastAPI router가 HTTP request를 받는다. chat template과 tokenizer로 prompt를 token ID로 바꿔 AsyncLLM에 넘기고, 돌아온 결과를 JSON이나 SSE로 응답한다.
    - **AsyncLLM**: EngineCore를 호출하는 engine client다. request를 ZMQ로 EngineCore에 보내고, 돌아온 출력을 FastAPI app에 넘긴다.
    - 지금은 Python 구현이다. Rust frontend로 전환하는 작업이 진행 중이지만 아직 빠진 기능이 있어서, 이 글은 Python frontend로 설명한다.
- **EngineCore 프로세스**는 busy loop를 돌며 ZMQ로 받은 request를 Scheduler에 넣고, step을 실행하고, 결과를 AsyncLLM으로 보낸다.
    - **Scheduler**: 대기 중인 request와 실행 중인 request를 보고, token budget과 priority에 따라 이번 step에 request마다 계산할 token 수를 정한다. 안에 있는 KV cache manager가 KV cache block을 request에 할당하고, 끝난 request의 block을 회수한다.
    - **Executor · Worker · ModelRunner**: Scheduler가 정한 일을 GPU에서 실행한다. Executor는 EngineCore가 worker를 호출하는 창구이고, GPU가 하나면 같은 프로세스 안의 [`UniProcExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/uniproc_executor.py#L51)가 쓰인다. Worker는 GPU 장치를 초기화하고 model을 load한다. ModelRunner는 이번 step의 token을 한 줄로 묶어 batch를 만들고 forward와 sampling을 실행한다.
- **GPU**는 프로세스 밖의 장치다. ModelRunner가 보낸 forward와 sampling을 계산하고 token ID를 돌려준다.

그림의 주황색 STEP LOOP가 앞서 말한 step이다. 한 step을 조금 더 자세히 보면 세 단계다.

1. scheduler가 지금 살아 있는 request들을 보고, 이번 step에 계산할 token을 고른다. 한 번에 쓸 수 있는 token 수(token budget)와 KV cache 자리가 한도다.
2. worker가 고른 token들을 GPU에서 forward 한 번으로 계산하고, request마다 다음 token을 하나씩 뽑는다(sampling).
    - 이때의 batch는 request별로 길이를 맞춰 padding한 [request 수 x 길이] 격자가 아니다. request마다 길이가 다른 token 조각을 그대로 한 줄로 이어 붙인 것이다. 예를 들어 A의 prefill 512개, B의 prefill 10개, C의 decode 1개면 523개짜리 token 줄 하나가 forward에 들어간다.
    - 각 request의 조각이 어디서 시작하고 끝나는지, 그 request의 지난 KV cache가 어느 block에 있는지는 따로 넘겨주므로 attention은 request를 섞지 않는다. sampling도 request마다 자기 조각의 마지막 위치에서 한다.
3. scheduler가 뽑힌 token을 각 request에 기록하고, 끝난 request는 내보낸다.

prefill은 보통 한 step에 끝나지만, prompt가 길면 token budget에 맞춰 여러 step에 나눠서 한다(chunked prefill). 그래서 한 step의 batch에는 prefill 중인 request와 decode 중인 request가 섞여 있고, 위 예시의 A, B, C가 바로 그 모습이다.

step마다 나온 token ID는 frontend로 돌아간다. streaming request면 그때그때 SSE event가 되고, non-streaming request면 완료된 뒤에 최종 JSON으로 만들어진다.

이후 글은 두 부분으로 나뉜다. 서버 초기화에서는 이 그림의 상자들이 만들어지는 순서를 따라가고, request 처리에서는 화살표를 따라간다.

### 1. Server mode selection: `vllm serve`에서 `run_server()`까지

`vllm serve`를 실행하면 [`vllm/entrypoints/cli/main.py`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/main.py)가 subcommand를 찾아 [`vllm/entrypoints/cli/serve.py`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/serve.py)의 `ServeSubcommand.cmd()`를 호출한다. 이 함수가 옵션을 보고 서버를 어떤 모드로 띄울지 정한다. 외부 load balancer나 multi-port 같은 특수한 옵션을 주지 않으면, 지금 프로세스에서 API server 하나가 [`run_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L165-L177)로 올라온다.

```python
# Single API server (this process).
args.api_server_count = None
uvloop.run(run_server(args))
```

다른 모드는 아래 세 가지다.

- [`run_dp_supervisor()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/dp_supervisor.py#L562): `--data-parallel-multi-port-external-lb`를 주면 쓰인다. `DPSupervisor`가 이 노드의 DP rank마다 vLLM 서버 프로세스를 하나씩 띄우고, 각 서버는 자기 port로 request를 받는다.
- [`run_headless()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/serve.py#L181): `--headless`를 주면 쓰인다. API server 없이 EngineCore만 띄우고, request는 다른 노드의 frontend에서 받는다. 주로 vLLM을 여러 노드에 띄울 때 worker 노드에서 쓴다.
- [`run_multi_api_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/serve.py#L269): API server가 둘 이상이거나 Rust frontend를 쓰면 쓰인다. DP(data parallelism)를 켜고 API server 수를 따로 정하지 않으면 그 기본값이 DP 크기가 되므로, 이 경로로 온다.

Rust frontend는 Python API server를 대신할 수 있는 실험 기능이다(`VLLM_USE_RUST_FRONTEND=1`). 처음 제안한 RFC는 당분간 Python frontend를 대체하지 않는다고 밝혔다([RFC #40846](https://github.com/vllm-project/vllm/issues/40846), [Roadmap #44280](https://github.com/vllm-project/vllm/issues/44280)). 이 글은 기본 경로인 [`run_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L165-L177)만 따라간다.

#### 설계 결정: API server와 EngineCore를 따로 늘린다

API server 수와 EngineCore 수는 따로 정한다. API server를 늘리면(예: `--api-server-count 2`) tokenize와 응답 직렬화 같은 frontend의 CPU 작업을 여러 프로세스가 나눠 지고, engine은 하나를 공유한다. data parallelism은 반대로 engine과 model replica를 늘린다. 이 글은 둘 다 하나인 구성만 다룬다. 이 구조는 [#17546](https://github.com/vllm-project/vllm/pull/17546)에서 들어왔다. 이 PR은 `--api-server-count` 옵션을 추가했고, DP와 함께 쓰면 API server와 EngineCore가 ZMQ로 all-to-all 연결되게 했다. PR의 benchmark는 DP 크기를 키울 때 성능, 특히 TTFT가 이전보다 잘 확장되는 것을 보여 준다.

### 2. Socket bind: listen 전의 port 선점

API server 하나로 띄우는 [`run_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L165-L177)는 두 함수를 차례로 호출한다. [`setup_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L378)가 소켓을 만들어 주소에 bind하고, [`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)가 엔진 client를 만든 뒤 HTTP 서버를 띄운다.

[`setup_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L378)는 vLLM 버전과 기본값이 아닌 인자를 log로 남기고, tool parser와 reasoning parser plugin을 load하고, 인자를 검증한다. 그 다음 소켓을 만들어 bind한다. 기본은 [`create_server_socket()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L335)이 만드는 TCP 소켓이다. `--uds`로 경로를 주면 [`create_server_unix_socket()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L353)이 Unix domain socket을 만든다. 같은 호스트의 reverse proxy가 vLLM과 통신할 때 이 방식을 쓴다.

서버 소켓은 `socket() → bind() → listen() → accept()` 순서로 열린다. [`setup_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L378)는 `bind()`까지만 한다. 그래서 엔진을 준비하는 동안 port는 잡혀 있지만, request는 아직 받지 않는다. `listen()`과 `accept()`는 뒤에 나오는 [`serve_http()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L175)에서 일어난다.

[`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)도 tool parser와 reasoning parser plugin을 import한다. API server를 여러 개 띄우면 이 함수가 새 프로세스마다 따로 시작되기 때문이다. 그 다음 [`build_async_engine_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L36)로 엔진 client인 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)을 만들고 [`build_and_serve()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L116)를 호출한다. 서버가 끝나면 엔진을 정리하고 소켓을 닫는 일도 이 함수가 한다.

엔진 초기화는 모두 [`build_async_engine_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L36) 안에서 일어난다. 이 함수가 반환되기 전에 설정 생성, EngineCore 프로세스 시작, model load와 KV cache 할당이 모두 끝난다. 3~5번이 이 과정을, 6번이 그 뒤의 [`build_and_serve()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L116)를 다룬다.

#### 설계 결정: 엔진보다 먼저 bind하는 이유

소켓을 엔진보다 먼저 bind하는 데는 이유가 있다. 코드 주석에 따르면, 엔진을 준비하기 전에 port를 잡아 두어 Ray와의 race condition을 피하려는 것이다([#8204](https://github.com/vllm-project/vllm/issues/8204)). port가 이미 쓰이고 있으면 무거운 엔진 초기화를 시작하기 전에 바로 실패하는 효과도 있다. [#8204](https://github.com/vllm-project/vllm/issues/8204)는 서버가 시작할 때 `address already in use` 오류로 bind에 실패하던 문제였다.

### 3. Engine config: CLI 인자에서 `VllmConfig`까지

3번은 [`build_async_engine_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L36)에서 시작한다. 이 단계는 CLI 인자를 엔진 전체가 공유하는 설정 객체 [`VllmConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2838)로 변환한다. 변환은 **필드 매핑**과 **기본값 결정**의 두 단계로 나뉜다. 단계를 나누는 이유는 설정값 하나를 정할 때 여러 정보를 조합해야 하기 때문이다. CLI 인자만으로는 값을 정할 수 없고, model, 하드웨어, 진입점을 함께 봐야 한다. 그래서 사용자가 정한 값은 그대로 쓰고, 정하지 않은 값만 vLLM이 이 정보들을 조합해 정한다.

첫 단계는 이름 기준의 필드 매핑이다. 값을 해석하거나 검증하지 않는다. [`AsyncEngineArgs.from_cli_args()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L1933)가 argparse `Namespace`에서 field 이름이 같은 값만 골라 [`AsyncEngineArgs`를 만든다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L53). 사용자가 정하지 않은 값은 이때 `None`이나 `"auto"`로 남는다.

둘째 단계는 기본값 결정(default resolution)이다. 비어 있는 값을 정하고, 설정 전체를 검증한다. [`build_async_engine_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L36)가 호출하는 [`build_async_engine_client_from_engine_args()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L70)가 [`create_engine_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2205)를 호출한다. 기본값을 정할 때 참고하는 정보는 값마다 다르다. 몇 가지 값을 예로 들면 아래와 같다.

[`create_engine_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2205)는 [`create_model_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L1943)로 `ModelConfig`를 먼저 만든다. [chunked prefill 지원 여부](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2987)처럼 다른 설정의 기본값이 model 정보에 달려 있기 때문이다. 그 뒤 [`CacheConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2265), [`ParallelConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2528), [`SchedulerConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2617) 같은 sub-config를 만들고 [`VllmConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2838) 하나로 모은다. [`__post_init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L1414)는 sub-config끼리 서로 어긋나지 않는지 검사하고, [compilation mode](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L1752) 같은 남은 값을 정한다. 이후 4번의 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)과 5번의 [EngineCore](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L115)는 모두 이 객체 하나를 받는다.


#### 설계 결정: 진입점마다 다른 batch 기본값

CUDA GPU에서 `max_num_batched_tokens`의 [기본값 표](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2900-L2952)는 아래와 같다. CPU와 TPU는 값이 따로 있다. GPU 메모리로 행을 고르고, 진입점으로 열을 고른다. 코드 주석은 H100급 GPU에 대해 "use larger offline defaults"라고 적어 두었다. 오프라인 batch 처리는 응답 지연보다 처리량이 중요하므로 한 step을 더 크게 잡는 것으로 보인다.

| GPU | `LLM` 클래스 | `vllm serve` |
| --- | --- | --- |
| 메모리 160GiB 이상 (B200 등) | 16384 | 16384 |
| 메모리 70GiB 이상, A100 제외 (H100, H200) | 16384 | 8192 |
| 그 외 | 8192 | 2048 |

[`UsageContext`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/usage/usage_lib.py#L111)는 CLI 인자가 아니다. 진입점이 코드에서 넘기는 값이다. `vllm serve`는 [`OPENAI_API_SERVER`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L39)를, `LLM` 클래스는 [`LLM_CLASS`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/llm.py#L343)를 넘긴다. 그래서 같은 인자를 줘도 진입점이 다르면 기본값이 달라질 수 있다.

A100은 메모리가 80GB여도 "그 외" 행으로 빠진다. A100에서는 `max_num_batched_tokens`를 크게 잡으면 오히려 처리량이 떨어졌기 때문이다([#17885](https://github.com/vllm-project/vllm/pull/17885)).

### 4. Engine client: `AsyncLLM` 생성과 EngineCore 연결

4번은 엔진 client를 만드는 단계다. 엔진 client는 API server가 엔진에 request를 넣고 결과를 받을 때 쓰는 객체이고, vLLM에서는 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)이다. [`VllmConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2838)가 준비되면 [`AsyncLLM.from_vllm_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L95)가 이 객체를 만든다. [`AsyncLLM.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L87)에서 하는 일은 두 가지다. request 전처리와 결과 후처리를 맡을 객체를 만들고, EngineCore 프로세스를 띄워 ZMQ로 연결한다. 먼저 만드는 객체는 아래 세 개다.

- [`renderer`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L158): tokenizer와 chat template을 가지고, 사용자가 보낸 messages를 model 입력 형식(prompt 문자열과 token ID)으로 바꾼다. 이미지 같은 multimodal 입력 처리도 맡는다.
- [`InputProcessor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L161): renderer가 만든 입력과 sampling parameter를 검증하고, EngineCore로 보낼 [`EngineCoreRequest`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/__init__.py#L109)로 묶는다.
- [`OutputProcessor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L171): EngineCore가 돌려준 token ID를 request별로 모아 detokenize하고, logprobs를 붙여 [`RequestOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/outputs.py#L129)으로 바꾼다.

그 다음 [`EngineCoreClient.make_async_mp_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L137)를 [호출한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L184). DP를 쓰지 않으면 이 함수는 [`AsyncMPClient`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1106)를 반환한다. DP를 쓰면 외부 load balancer가 있을 때 [`DPAsyncMPClient`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1419)를, 없을 때 vLLM이 직접 분산하는 [`DPLBAsyncMPClient`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1603)를 반환한다. EngineCore 프로세스는 이 client의 부모 클래스 [`MPClient.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L595)에서 생긴다.

[`MPClient.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L595)은 먼저 ZMQ 소켓 두 개를 bind한다. request를 보내는 [ROUTER 소켓](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L660-L665)과 출력을 받는 [PULL 소켓](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L667-L669)이다. 그 다음 [`launch_core_engines()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L1198)가 handshake용 소켓을 열고, [`CoreEngineProcManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L237)가 [`EngineCoreProc.run_engine_core()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L282-L283)를 target으로 새 프로세스를 시작한다. 이 함수가 EngineCore 프로세스의 진입점이고, 프로세스 안에서 일어나는 일은 5번에서 이어진다.

두 프로세스는 handshake로 연결된다. EngineCore가 HELLO를 보내면 API server가 ZMQ 소켓 주소를 돌려준다. EngineCore는 5번의 startup을 마친 뒤 READY를 보낸다. [`launch_core_engines()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L682)의 `with` 블록이 끝날 때 [`wait_for_engine_startup()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L1361)이 이 READY를 기다린다. 그래서 API server는 이 함수에서 멈춰 있고, 그동안 EngineCore 프로세스 안에서 5번이 진행된다. [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84) 생성은 5번이 끝나야 반환된다.

#### 설계 결정: EngineCore 프로세스 분리와 ZMQ

EngineCore를 별도 프로세스로 띄우는 이유는 두 가지다. API server와 엔진의 CPU 작업이 같은 자원을 두고 다투지 않게 하고, CPU 작업과 GPU 실행의 overlapping을 늘리기 위해서다. 처음에는 API server와 엔진이 같은 asyncio event loop를 썼다([RFC #6797](https://github.com/vllm-project/vllm/issues/6797)). [#6883](https://github.com/vllm-project/vllm/pull/6883)에서 API server를 별도 프로세스로 분리했고, V1의 [#9826](https://github.com/vllm-project/vllm/pull/9826)에서 EngineCore를 분리했다. 두 프로세스 사이의 통신에는 [ZeroMQ](https://zeromq.org/)(ZMQ)를 쓴다.

ZMQ는 TCP나 IPC 소켓 위에서 메시지 단위 통신을 제공하는 messaging library다. ZMQ에는 메시지를 중계하는 broker가 없어서, vLLM은 ZMQ용 서버를 따로 띄우지 않는다. API server와 EngineCore가 각자 ZMQ 라이브러리로 소켓을 만들고 서로 직접 연결한다. 메시지를 어떤 방식으로 주고받을지는 소켓 종류로 고르며, 앞에서 본 [ROUTER](https://zeromq.org/socket-api/#router-socket)와 [PULL](https://zeromq.org/socket-api/#pull-socket)이 그 예다. [#6883](https://github.com/vllm-project/vllm/pull/6883)은 gRPC와 benchmark로 비교해 ZMQ를 골랐고, 이 benchmark에서 ZMQ가 TTFT와 TPOT 모두 더 짧았다. API server 쪽은 [`zmq.asyncio`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L21) 소켓을 써서, EngineCore의 출력을 기다리는 동안에도 asyncio event loop가 다른 HTTP request를 처리한다.

이미지 같은 큰 multimodal tensor는 예외적으로 ZMQ를 거치지 않을 수 있다. [`mm_tensor_ipc`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/multimodal.py#L440)를 `"torch_shm"`으로 설정하면 tensor를 공유 메모리로 넘긴다. 이때 ZMQ 메시지에는 tensor 대신 참조만 들어간다. 기본값은 `"direct_rpc"`이고, 이 경우 tensor도 직렬화해 ZMQ로 보낸다.

### 5. EngineCore startup: model load, KV cache allocation, scheduler setup

5번은 EngineCore 프로세스가 시작해서 step loop에 들어가기까지의 과정이다. 프로세스 안에서 model을 GPU에 올리고, 남은 GPU 메모리로 KV cache를 할당하고, scheduler를 만든다. 이 셋이 갖춰지면 API server에 READY를 보내고 step loop에 들어간다.

4번에서 [`CoreEngineProcManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L237)가 target으로 넘긴 [`EngineCoreProc.run_engine_core()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1391)가 EngineCore 프로세스에서 처음 실행되는 함수다. 이 함수가 [`EngineCoreProc`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1128)를 만든다. [`EngineCoreProc.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1135)은 [`_perform_handshakes()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1250) context를 열어 HELLO를 보내고 ZMQ 주소를 받는다. 그리고 그 context 안에서 [`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)을 [호출한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1194).

[`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)은 model, KV cache, scheduler를 이 순서로 준비한다. 뒤 단계가 앞 단계의 결과를 쓰기 때문이다.

model은 [`executor_class(vllm_config)`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L144)에서 올라온다. GPU 하나로 띄우면 executor는 [`UniProcExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/uniproc_executor.py#L51)이고, 이 프로세스 안에 Worker를 하나 만든다. Worker의 [`init_device()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L436)가 CUDA device와 분산 환경을 초기화하고, GPU 전체 메모리에 `gpu_memory_utilization`을 [곱해](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L535) vLLM이 쓸 메모리 예산을 정한다. 이어서 [`load_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L587)이 model runner를 통해 weight를 GPU에 올린다. GPU를 여러 개 쓰면 [`MultiprocExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/multiproc_executor.py#L111)가 GPU마다 worker 프로세스를 따로 띄운다. worker 수는 tensor, pipeline, prefill context parallelism 크기를 곱한 [`world_size`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/parallel.py#L945-L949)다. data parallelism은 EngineCore 자체를 늘리므로, EngineCore 하나에 속한 worker 수에는 들어가지 않는다. 이후 EngineCore가 worker에 시키는 일은 모두 executor의 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)를 거친다. 이 함수는 5번 끝에서 따로 설명한다.

KV cache는 [`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)이 [호출하는](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L157) [`_initialize_kv_caches()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L261)가 준비한다. 먼저 worker에서 layer별 [`KVCacheSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L165)을 모은다. spec에는 KV cache의 shape(block 크기, KV head 수, head 크기)와 dtype, 그리고 full attention, sliding window, MLA 같은 attention 종류가 들어 있다. 이 값으로 block 하나의 byte 크기가 정해진다. 그 다음 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)로 각 Worker에서 실행되는 [`determine_available_memory()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L634)가 KV cache에 쓸 수 있는 메모리를 잰다. 측정은 두 번이다. 먼저 [`profile_run()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_model_runner.py#L6133)이 한 step의 최대 token 수로 만든 dummy 입력으로 forward를 한 번 돌려, 실행 중에 잠깐 생기는 activation 메모리의 최고치(그림의 PEAK)를 잰다. 다음으로 [`profile_cudagraph_memory()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_model_runner.py#L6333)가 CUDA graph가 차지할 메모리를 추정한다. 메모리 예산에서 weight, activation 최고치, CUDA graph 추정치를 뺀 나머지가 KV cache 몫이다. 이 크기로 block 수를 정하고, [`initialize_from_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L377)가 KV cache tensor를 할당한다.

마지막으로 [`compile_or_warm_up_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L379)이 model을 warm up하고 CUDA graph를 capture한다. 추정치로 비워 둔 자리를 실제 graph가 채운다. [CUDA graph](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)는 kernel 실행, 데이터 복사 같은 GPU 작업을 의존 관계로 이어 놓은 것이다. CUDA graph capture는 forward 한 번에 실행되는 작업을 이 graph로 기록해 두는 일이다. vLLM은 batch 크기 몇 개(`cudagraph_capture_sizes`)를 골라 각각 기록해 두고, 실행할 때는 batch를 가장 가까운 크기로 [padding해](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/cudagraph_dispatcher.py#L71) 그 graph를 통째로 재생한다. 고정 크기 몇 개에 입력을 맞추는 이런 방식을 흔히 bucketing이라고 부른다.

scheduler는 step마다 어떤 request의 token을 몇 개 계산할지 정하는 컴포넌트다. 개념은 5번 끝에서 따로 설명한다. scheduler 객체는 [`Scheduler(...)`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L174)로 만든다. 앞에서 정한 KV cache 설정을 받아 [`KVCacheManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L328)를 만든다. request에 KV block을 나눠 주려면 전체 block 수를 알아야 하므로, scheduler는 KV cache 다음에 생긴다.

[`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)이 끝나면 [`EngineCoreProc`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1128)은 ZMQ 입출력 thread를 띄운다. 그 다음 [`_perform_handshakes()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1250) context를 빠져나가면서 [READY를 보낸다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1338-L1350). 마지막으로 [`run_busy_loop()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1547)에 들어가 request를 기다린다. 이 loop가 뒤에서 볼 step loop다.

#### 설계 결정: KV cache 크기를 profiling으로 정한다

vLLM은 KV cache를 시작할 때 한 번에 할당하고, 이후에는 고정 크기 block 단위로 request에 나눠 준다. 이 block 방식은 PagedAttention 논문에서 왔다. 논문은 request마다 KV cache를 연속 공간으로 미리 잡으면 단편화와 과잉 예약으로 메모리가 낭비된다고 보고, OS의 paging처럼 KV cache를 block으로 나눠 이 낭비를 줄였다([Kwon et al., SOSP 2023](https://arxiv.org/abs/2309.06180)).

block pool을 시작할 때 한 번에 잡으므로, 그 크기를 정하려면 KV cache 말고 다른 것이 쓸 메모리를 먼저 알아야 한다. activation 최고치와 CUDA graph 메모리는 model, attention kernel, batch 크기에 따라 달라서 식으로 미리 계산하기 어렵다. 그래서 vLLM은 dummy 입력으로 실제로 한 번 돌려서 재는 방식을 택한 것으로 보인다.

#### `collective_rpc()`: EngineCore가 worker에 일을 시키는 방식

EngineCore는 worker가 몇 개인지, 같은 프로세스에 있는지 신경 쓰지 않는다. executor의 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)에 메서드 이름만 넘기면, executor가 그 메서드를 모든 worker에서 실행하고 결과를 리스트로 모아 돌려준다. 실행 방식은 executor마다 다르다. [`UniProcExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/uniproc_executor.py#L51)는 같은 프로세스에 있는 worker의 메서드를 바로 호출한다. [`MultiprocExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/multiproc_executor.py#L111)는 공유 메모리 기반 [`MessageQueue`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/multiproc_executor.py#L164)로 모든 worker 프로세스에 호출을 broadcast하고, worker별 응답 queue에서 결과를 받는다.

5번의 [`determine_available_memory()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L634), [`initialize_from_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L377), [`compile_or_warm_up_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L379)이 모두 [이 경로로](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L137-L163) worker에서 실행된다. 그래서 EngineCore 코드에는 `self.model_executor.xxx()`만 보이고, 실제 일은 worker에서 일어난다.

#### Scheduler: step마다 계산할 token을 고르는 컴포넌트

scheduler는 step마다 어떤 request의 token을 몇 개 계산할지 정한다. 기준은 두 가지다. 하나는 한 step에 계산할 수 있는 token 수(token budget)다. 3번에서 본 `max_num_batched_tokens`가 이 상한을 [정한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L137-L141). 다른 하나는 KV cache block이다. request가 새 token을 계산하려면 그 token의 KV를 저장할 block이 있어야 한다. [`KVCacheManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L328)는 GPU의 KV block 전체를 관리하는 객체로, request에 block을 [나눠 주고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L778) 끝난 request의 block을 [돌려받는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L620). block이 모자라면 scheduler는 실행 중인 request 하나를 [preempt해](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L795-L802) block을 확보한다.

step마다 실제로 어떻게 고르는지는 [request 처리의 4번](#4-schedule-step마다-계산할-token-배정)에서 다룬다.

### 6. HTTP serving: route 등록과 Uvicorn 실행

다시 2번의 [`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)로 돌아온다. [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)이 반환되면 [`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)는 [`build_and_serve()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L116)를 호출한다. 이 함수는 먼저 엔진에게 지원하는 task 목록([`SupportedTask`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/tasks.py#L43))과 `model_config`를 받아 온다. task 목록에는 `generate` 같은 생성 task와 `embed` 같은 pooling task가 들어 있다.

[`build_app()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/app.py#L19)은 FastAPI app을 만들고, [`register_api_routers()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/routers.py#L12)로 이 목록에 맞는 route만 등록한다. 예를 들어 `generate`가 있으면 `/v1/chat/completions` 같은 생성 route를 붙인다. [`init_app_state()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/app_state.py#L24)는 route가 쓸 handler를 `app.state`에 만들어 둔다. chat request를 처리하는 [`OpenAIServingChat`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L118)도 여기서 생긴다. 마지막으로 [`serve_http()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L175)를 호출한다.

[`serve_http()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L175)는 Uvicorn 설정을 만들고, `server.serve()` coroutine을 event loop에 task로 올린다. event loop가 이 task를 실행하면 Uvicorn이 시작하면서 소켓에 `listen()`을 호출한다. `accept()`는 그 뒤 연결이 들어올 때마다 일어난다. Uvicorn 서버로는 signal handler를 설치하지 않는 [`NoSignalServer`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L45)를 쓴다.

#### 설계 결정: Uvicorn의 signal handler를 끈다

[`NoSignalServer`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L45)는 SIGINT와 SIGTERM handler를 설치하지 않는다. vLLM은 종료할 때 HTTP 서버뿐 아니라 엔진도 정리해야 해서, 종료 handler를 event loop에 직접 등록한다. Uvicorn이 자기 handler를 설치하면 이 handler와 경쟁하다가 덮어쓴다. [#49668](https://github.com/vllm-project/vllm/pull/49668)이 이 문제를 고치면서 지금 구조가 되었다.

### 1. HTTP POST: FastAPI router의 request 수신

1번은 HTTP request가 vLLM 코드에 처음 들어오는 단계다. router는 request 형식을 검증하고 handler에 넘길 뿐, model을 직접 실행하지 않는다. 예를 들어 client가 다음 request를 보낸다고 하자.

```console
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"<model>","messages":[{"role":"user","content":"hi"}]}'
```

이 request는 [`create_chat_completion()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/api_router.py#L41-L80) route로 들어온다. FastAPI가 이 함수를 호출하기 전에 JSON body를 [`ChatCompletionRequest`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/protocol.py#L220)로 검증한다. 함수는 [서버 초기화 6번](#6-http-serving-route-등록과-uvicorn-실행)에서 `app.state`에 만들어 둔 [`OpenAIServingChat`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L118)을 꺼내, 그 [`create_chat_completion()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L281)을 호출한다.

chat completions만 있는 것은 아니다. model이 `generate` task를 지원하면, [서버 초기화 6번](#6-http-serving-route-등록과-uvicorn-실행)의 [`register_generate_api_routers()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/generate/api_router.py#L21)가 다른 생성 API의 route도 함께 등록한다. 모두 같은 방식으로 동작한다. FastAPI가 JSON body를 API마다 정의된 Pydantic model로 검증하고, route는 검증된 request를 그 API의 handler에 넘긴다.

handler는 API마다 다르지만, 결국 모두 2번부터의 경로를 탄다. 입력을 token ID로 바꾸고 `AsyncLLM`의 `generate()`를 호출한다. 이 글은 chat completions를 예로 따라간다.

handler가 돌려준 값에 따라 응답 형식이 갈린다. `ErrorResponse`면 오류 JSON을, `ChatCompletionResponse`면 완성된 JSON을 보낸다. 그 밖의 경우는 streaming이므로 `StreamingResponse`로 감싸 `text/event-stream`(SSE)으로 보낸다. route에 붙은 `with_cancellation` decorator는 client 연결이 끊기면 handler task를 취소한다. 이 취소가 7번의 정리로 이어진다.

#### SSE: 응답을 조금씩 보내는 방식

SSE(Server-Sent Events)는 HTTP 응답 하나를 열어 둔 채, server가 event를 하나씩 이어서 보내는 방식이다. 표준은 [HTML Living Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html)에 있다. 응답의 `Content-Type`은 `text/event-stream`이고, event 하나는 `data: ...` 줄과 빈 줄 하나로 끝난다.

```text
data: {"choices":[{"delta":{"content":"Hel"}}]}

data: {"choices":[{"delta":{"content":"lo"}}]}

data: [DONE]
```

LLM 서버가 SSE를 쓰는 이유는 token이 step마다 하나씩 나오기 때문이다. 응답을 다 만들 때까지 기다리지 않고, 만든 부분부터 client에 보낼 수 있다. 통신은 server에서 client로 한 방향뿐이다. WebSocket처럼 양방향 연결이 필요 없어서, 평범한 HTTP 위에서 그대로 동작한다. 마지막 `data: [DONE]`은 SSE 표준이 아니라 OpenAI API가 정한 종료 표시이고, vLLM도 이를 따른다.

vLLM에서는 route가 handler의 async generator를 Starlette의 [`StreamingResponse`](https://starlette.dev/responses/#streamingresponse)로 [감싼다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/api_router.py#L77-L80). generator가 `data: ...` 문자열을 하나 yield할 때마다 Starlette가 그것을 HTTP chunk로 보낸다. 이 문자열을 만드는 쪽은 6번의 `chat_completion_stream_generator()`다. 그 사이에는 [`with_sse_keep_alive()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/serve/utils/sse_keep_alive.py#L21)가 끼어 있다. 이 함수는 keep-alive 간격이 설정되어 있으면, 그 시간 동안 새 chunk가 없을 때 연결 유지용 SSE comment를 보낸다. 간격이 0 이하면 아무것도 하지 않는다.

### 2. Tokenize: chat request를 model 입력으로

2번은 chat 형식의 request를 엔진에 넘길 형태로 바꾸는 단계다. 하는 일은 세 가지다. messages를 token ID로 바꾸고, 생성할 token 수의 한도를 정하고, sampling parameter를 만든다. 이 일은 모두 API server 프로세스에서 일어나고, EngineCore는 이미 token화된 입력만 받는다.

[`OpenAIServingChat`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L118)의 [`_create_chat_completion()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L296-L415)이 실제 일을 한다. 먼저 [`render_chat_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L258-L279)가 model 이름을 확인하고, renderer의 [`render_chat()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/renderers/online_renderer.py#L224-L317)을 호출한다. 여기서 messages, system prompt, tools를 model의 chat template에 넣어 prompt 문자열을 만들고, tokenizer로 token ID로 바꾼다. 결과가 [`EngineInput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/inputs/engine.py#L266)이다. [서버 초기화 4번](#4-engine-client-asyncllm-생성과-enginecore-연결)에서 본 renderer가 바로 이 일을 한다.

생성 한도는 [`get_max_tokens()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/serve/utils/api_utils.py#L169-L205)가 정한다. 규칙의 핵심은 하나다. prompt와 생성 token을 합친 길이는 `max_model_len`을 넘을 수 없다. 그래서 prompt를 넣고 남은 공간이 상한이 되고, request나 서버 설정이 그보다 작은 값을 주면 그 값이 한도가 된다. 각 값의 정의와 관계는 2번 끝의 [생성 한도를 정하는 값들](#생성-한도를-정하는-값들)에서 자세히 다룬다.

<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/03-2-max-tokens-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/03-2-max-tokens-dark.svg"
  caption="max_model_len 안에서 max_tokens가 정해지는 방식. prompt(input_length)를 넣고 남은 공간이 생성 한도의 상한이다."
/>

코드의 변수 이름으로 쓰면 아래와 같다.

$$
\begin{aligned}
\text{model\_max\_tokens} &= \text{max\_model\_len} - \text{input\_length} \\
\text{max\_tokens} &= \min\big(\text{model\_max\_tokens},\ \text{fallback\_max\_tokens},\ \text{override\_max\_tokens},\ \text{platform\_max\_tokens}\big)
\end{aligned}
$$

sampling parameter는 [`to_sampling_params()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/protocol.py#L715)가 만든다. 이 함수는 temperature, top-p, stop 같은 request 필드로 [`SamplingParams`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/sampling_params.py#L268)를 만든다. 마지막으로 `engine_client.generate()`를 호출한다. 이 서버에서 `engine_client`는 [서버 초기화 4번](#4-engine-client-asyncllm-생성과-enginecore-연결)에서 만든 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)이다.

#### 생성 한도를 정하는 값들

아래 값은 모두 token 단위다.

- context length: model이 한 번에 다룰 수 있는 최대 token 수다. model의 HF `config.json`에 적혀 있다.
- `max_model_len`: 이 서버가 허용하는 sequence 길이의 상한이다. sequence는 prompt와 생성 token을 합친 것이다.
- `input_length`: prompt 길이(prompt_len). chat template을 적용해 token화한 prompt의 token 수다.
- `model_max_tokens`: prompt를 넣고 남은 공간, 즉 `max_model_len - input_length`다.
- `fallback_max_tokens`: request가 요청한 한도다. `max_completion_tokens`, 없으면 `max_tokens`, 그것도 없으면 model의 기본 sampling 설정 값을 쓴다.
- `override_max_tokens`: 서버 운영자가 `--override-generation-config`의 `max_new_tokens`로 건 강제 상한이다.
- `platform_max_tokens`: 외부 플랫폼 plugin을 위한 상한이다. CUDA를 포함한 기본 플랫폼에서는 [제한이 없다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/platforms/interface.py#L224-L225).

`max_tokens`는 두 단계로 정해진다. 먼저 `max_model_len`은 context length를 넘지 못한다. 사용자가 `--max-model-len`을 주면 그 값을, 주지 않으면 context length를 쓰고, context length보다 큰 값을 주면 기본적으로 [오류가 난다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/model.py#L2639-L2664).

$$
\text{max\_model\_len} = \min\big(\texttt{--max-model-len},\ \text{context length}\big)
$$

context length는 model마다 키 이름이 달라서, vLLM은 `max_position_embeddings`, `n_positions`, `max_seq_len`, `seq_length` 같은 후보 키 중 config에 있는 값의 [최솟값을 쓴다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/transformers_utils/model_arch_config_convertor.py#L394-L427). Llama나 Qwen 같은 대부분의 model은 `max_position_embeddings`다. tokenizer config에 `model_max_length`가 있으면 그 값으로 더 줄어들 수 있다.

그 다음 `max_tokens`는 `model_max_tokens`, `fallback_max_tokens`, `override_max_tokens`, `platform_max_tokens` 중 가장 작은 값이다. 값이 없는(`None`) 항은 `min`에서 빠진다. 그래서 request가 한도를 주지 않으면 `model_max_tokens`가 그대로 한도가 되고, request가 큰 값을 줘도 context 길이를 넘지는 못한다.

`max_new_tokens`는 `max_tokens`와 같은 값의 다른 이름이다. Hugging Face의 `generation_config.json`과 `--override-generation-config`는 이 값을 `max_new_tokens`라고 적고, vLLM은 읽을 때 `max_tokens`로 [매핑한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/model.py#L1883-L1888). 아래에서 HF는 `generation_config.json`의 `max_new_tokens`를, override는 `--override-generation-config`의 `max_new_tokens`를 뜻한다.

HF 파일을 어디서 읽는지는 `--generation-config` 값이 [정한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/model.py#L1824-L1837). `auto`(기본값)면 `--model`로 준 곳에서 읽는다. `--model`은 HF Hub repo id일 수도, local 폴더일 수도 있다. 폴더 경로를 주면 그 폴더에서 읽고, `vllm`이면 읽지 않는다.

이 값들은 두 가지 역할 중 하나를 맡는다. 차이는 request가 값을 줬을 때 드러난다.

- 기본값: request가 값을 주지 않았을 때만 그 자리를 채운다. request가 값을 주면 그 값이 더 커도 request 값을 쓴다.
- 강제 상한: request가 무엇을 주든 그 값을 위에서 자른다. `min`에 항상 들어간다.

`get_max_tokens()`는 세 단계로 `max_tokens`를 정한다.

1. 원하는 값(requested)을 고른다. request의 `max_completion_tokens`, `max_tokens`, 서버 기본값 순서로 보고 처음 있는 값을 쓴다. 서버 기본값은 override가 있으면 override, 없으면 HF다.
2. 강제 상한(cap)을 고른다. `--generation-config`가 폴더 경로면 서버 기본값이, 아니면 override가 [상한이 된다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L175-L181). 둘 다 없으면 상한도 없다.
3. `model_max_tokens`, requested, cap 중 가장 작은 값을 고른다. 값이 없는 항은 빠진다.

그림의 "override > HF"는 둘 다 있으면 override를 쓴다는 뜻이다.

<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/03-2-max-tokens-flow-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/03-2-max-tokens-flow-dark.svg"
  caption="get_max_tokens()가 max_tokens를 정하는 순서."
/>

예를 들어 `model_max_tokens`가 4000이고, model의 `generation_config.json`에 `max_new_tokens: 512`가 있다고 하자. 아래 표에서 열은 서버를 띄운 설정이고(`<dir>`은 `generation_config.json`이 있는 폴더 경로), 행은 client가 보낸 request 하나다. 칸의 값은 그 request에 실제로 적용되는 `max_tokens`다. 셋째 열은 `auto`에 `--override-generation-config '{"max_new_tokens": 1000}'`을 더한 설정이다.

| client request의 `max_tokens` | `--generation-config auto` | `--generation-config <dir>` | `auto` + override 1000 |
| --- | --- | --- | --- |
| 없음 | 512 | 512 | 1000 |
| 100 | 100 | 100 | 100 |
| 2000 | 2000 | 512 | 1000 |

`auto`에서 512는 기본값이라 request의 2000을 막지 않는다. 폴더 경로에서는 512가 강제 상한이라 2000이 512로 잘린다. override를 주면 1000이 강제 상한이 되고, 파일 값 위에 덮어써지므로 기본값 자리도 1000이 차지한다. `vllm`이면 파일을 읽지 않으므로 override만 적용된다.

헷갈리기 쉬운 점을 정리하면 아래와 같다.

- `input_length`는 prompt 길이(prompt_len)다. 이름에 input이 들어가지만 생성 token은 포함하지 않는다.
- `max_model_len`은 context length와 같은 값이 아니다. 둘 중 작은 값이고, 대개 사용자가 `--max-model-len`으로 줄인 값이다.
- `max_new_tokens`와 `max_tokens`는 같은 값이다. HF와 `--override-generation-config`는 앞의 이름을, vLLM 내부와 OpenAI API는 뒤의 이름을 쓴다.
- HF 파일은 local 경로를 뜻하지 않는다. `auto`면 `--model`이 가리키는 곳(HF Hub 또는 local)의 파일이다.
- `auto`에서 HF 값은 기본값일 뿐이다. request가 더 큰 값을 주면 막지 않는다.
- override는 강제 상한이면서 기본값 자리도 덮어쓴다. 그래서 request가 비어 있으면 HF 값이 아니라 override 값이 쓰인다.

### 3. ZMQ ADD: `AsyncLLM`에서 EngineCore로

3번은 request를 엔진에 등록하고, 결과를 받을 자리를 마련하는 단계다. 등록은 API server와 EngineCore 양쪽에서 일어난다.

[`AsyncLLM.generate()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L698-L809)는 먼저 [`add_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L388)를 호출한다. 여기서 [`InputProcessor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L161)가 [`EngineInput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/inputs/engine.py#L266)과 [`SamplingParams`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/sampling_params.py#L268)를 검증하고 [`EngineCoreRequest`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/__init__.py#L109)로 묶는다. 그 다음 두 줄이 순서대로 실행된다.

```python
self.output_processor.add_request(request, prompt, parent_req, index, queue)
await self.engine_core.add_request_async(request)
```

[첫 줄](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L572)은 API server 쪽에 이 request의 detokenizer, logprob 처리기, 결과 queue를 등록한다. [둘째 줄](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L575)은 EngineCore에 ADD message를 보낸다. 결과 queue를 먼저 만들어 두므로, 엔진 출력이 아무리 빨리 와도 받을 자리가 이미 있다. `generate()`는 이후 이 queue([`RequestOutputCollector`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/output_processor.py#L53))를 async generator로 읽으며 결과를 기다린다.

ADD message는 [서버 초기화 4번](#4-engine-client-asyncllm-생성과-enginecore-연결)에서 bind한 ROUTER 소켓으로 간다. [`AsyncMPClient.add_request_async()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1296)가 request를 msgspec으로 직렬화해 ZMQ로 보낸다. EngineCore 쪽에서는 입력 thread가 이 message를 받아 [`preprocess_add_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1089)로 [`Request`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L60) 객체로 바꾼다. busy loop는 이 객체를 [`_handle_client_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1674)로 넘기고, [`add_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L508)가 scheduler의 waiting queue에 넣는다.

ADD를 보내기 전에 `add_request()`는 [`check_admission()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L316-L374)으로 admission을 검사한다. 끝나지 않은 request 수가 `--max-num-queued-reqs`를, prefill 중인 prompt token 합이 `--max-num-queued-tokens`를 넘으면 request를 거절하고 HTTP 503으로 응답한다. 503은 load balancer나 client SDK가 다른 instance로 retry하게 하려는 선택이다. 다만 두 값의 [기본값은 `None`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/scheduler.py#L92-L105)이라, 설정하지 않으면 API server는 request를 거절하지 않는다. ZMQ도 막지 않는다. vLLM은 ZMQ 소켓의 [high-water mark를 0](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/utils/network_utils.py#L372-L376)(무제한)으로 두므로, ZMQ는 메시지를 버리거나 막지 않는다. 그래서 기본 설정에서 몰린 request는 EngineCore의 입력 queue를 거쳐 scheduler의 waiting queue에 쌓이고, 그만큼 TTFT가 늘어난다. 이 waiting queue를 어떻게 비우는지는 4번에서 본다.

입력 자체가 stream으로 들어오는 경우는 경로가 조금 다르다. 실시간 음성 인식 API는 오디오 조각이 도착할 때마다 [`StreamingInput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/speech_to_text/realtime/serving.py#L59-L89)을 yield한다. `add_request()`는 이런 입력을 [`_add_streaming_input_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L580-L673)로 넘긴다. 이 함수는 결과 queue를 먼저 만들어 바로 반환하고, 입력을 읽는 task를 따로 띄운다. 그 task가 입력 조각마다 request를 만들어 같은 queue로 EngineCore에 이어 붙인다. admission은 첫 조각을 보낼 때 한 번만 검사한다. 거절되면 그 오류가 queue를 통해 `generate()`로 전달된다. SSE는 출력을 조금씩 보내는 방식이라 이 경로와 관계가 없다. chat completions는 `stream: true`여도 위의 일반 경로를 탄다.

### 4. Schedule: step마다 계산할 token 배정

4번은 scheduler가 이번 step에 어떤 request의 token을 몇 개 계산할지 정하는 단계다. 기준은 [서버 초기화 5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)의 Scheduler 소제목에서 본 두 가지, token budget과 KV block 여유다. 앞의 step timeline 그림이 보여 준 "step마다 여러 request가 함께 진행된다"는 동작이 여기서 만들어진다.

EngineCore는 이 일을 queue 몇 개로 처리한다. [`run_busy_loop()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1547-L1556)는 step마다 두 가지를 반복한다. 먼저 [`_process_input_queue()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1573-L1602)가 input thread가 채운 `input_queue`를 비워, 새 request를 scheduler의 `waiting` queue에 넣는다. 그 다음 `step_fn`이 schedule, forward, 결과 처리를 한 번 실행한다. 결과는 `output_queue`로 가고, output thread가 이를 API server로 보낸다.

  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/03-4-step-queues-dark.svg"
  caption="EngineCore step 하나에서 request가 queue를 지나는 순서."

[`Scheduler.schedule()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L591)은 두 queue를 정해진 순서로 본다.

1. `running`부터 본다. 이미 실행 중인 request마다 이번 step에 계산할 token 수를 정한다. prompt를 다 계산한 request는 보통 1개(decode), prompt가 남은 request는 남은 만큼이나 budget이 허락하는 만큼(chunked prefill)이다. 그만큼의 KV block을 `allocate_slots()`로 받고, token budget에서 뺀다.
2. 그 다음 `waiting`을 앞에서부터 본다. 이번 step에 preempt가 없었고 budget이 남았을 때만 본다. 새 request는 먼저 [`get_computed_blocks()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L264)로 prefix cache에서 이미 계산된 block을 찾고, 나머지 token에 필요한 block을 `allocate_slots()`로 받는다. block을 받으면 `waiting`에서 꺼내 `running`에 넣는다. `running`의 request 수가 `max_num_seqs`에 닿으면 멈춘다.

running을 먼저 보는 이유는 이미 시작한 request를 끝까지 진행시키기 위해서다. 새 request는 남은 budget과 block 안에서만 들어온다.

배정 결과가 [`SchedulerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L232)이다. 여기에는 request별 계산할 token 수, 새로 받은 KV block, encoder 작업, structured output 정보가 들어 있다. 결국 한 step의 batch는 `{request_id: num_tokens}` 하나로 표현되고, 여기에 prefill 조각과 decode token이 섞여 들어간다.

여러 request의 token을 padding 없이 한 forward로 묶는 방법은 뒤의 [padding 없는 continuous batching](#padding-없는-continuous-batching)에서 다룬다.

#### KVCacheManager: block을 나눠 주고 돌려받는 방식

[`KVCacheManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L328)는 서버 초기화 5번에서 할당한 KV cache를 고정 크기 block 단위로 관리한다. block 하나는 기본 [16 token](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/cache.py#L72)의 KV를 담는다. 일반 attention layer에서 block 하나의 byte 크기는 `2(K, V) × block_size × num_kv_heads × head_size × dtype 크기`다.

빈 block은 [`BlockPool`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L136)의 [`free_block_queue`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L178)에 있다. 이 queue는 Python `deque`가 아니라 vLLM이 직접 만든 [이중 연결 리스트](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L246-L262)다. 중간의 block을 O(1)에 빼낼 수 있어야 하기 때문이다. 이 필요는 아래 prefix caching에서 나온다.


<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/03-4-kv-block-manager-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/03-4-kv-block-manager-dark.svg"
  caption="KVCacheManager가 KV block을 나눠 주고 돌려받는 경로. 번호는 아래 설명의 순서와 같다."
/>

[`allocate_slots()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L371)는 세 단계로 block을 나눠 준다.

1. 필요한 block 수를 계산한다. 새 token이 17개면 `ceil(17 / 16) = 2`개다.
2. `free_block_queue`에 block이 충분한지 확인한다. 모자라면 실패를 돌려준다.
3. queue 앞에서 block을 꺼내 request에 붙이고, request별 block 목록(`req_to_blocks`)에 기록한다.

실패하면 scheduler가 처리한다. running request라면 우선순위가 가장 낮은 running request를 [preempt](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L795-L802)한다. FCFS에서는 `running`의 마지막 request다. preempt된 request는 block을 모두 돌려주고, 계산한 token 수를 0으로 되돌린 채 [`waiting` 맨 앞](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L1612-L1613)으로 간다. 다시 들어오면 prompt부터 다시 계산한다(recompute). waiting request라면 이번 step에는 더 들이지 않는다.

request가 끝나거나 preempt되면 block은 `free_block_queue`로 [돌아간다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L774-L804). 돌아가는 자리는 block에 hash가 있는지에 따라 다르다. hash가 없는 block은 queue 앞에 넣어 가장 먼저 재사용한다. 코드 주석은 그 이유를 GPU locality라고 적는다. hash가 있는 block, 즉 prefix cache로 다시 쓸 수 있는 block은 queue 뒤에 넣는다. 새 block은 앞에서부터 꺼내므로, cache된 block은 가장 오래 쓰지 않은 것부터 덮어써진다(LRU).

prefix caching은 이 구조 위에서 동작한다. scheduler는 prompt를 16 token씩 잘라 block마다 hash를 계산한다. hash에는 앞 block의 hash가 들어가므로, 같은 hash는 "처음부터 그 block까지 token이 모두 같다"는 뜻이다. [`cached_block_hash_to_block`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L181)은 이 hash에서 block으로 가는 표다. 새 request가 오면 `get_computed_blocks()`가 이 표에서 가장 긴 일치를 찾는다. 찾은 block이 다른 request에서 쓰는 중이면 참조 수(`ref_cnt`)만 올린다. 이미 반납되어 `free_block_queue`에 있으면 queue 중간에서 빼내 다시 쓴다. 이것이 중간 삭제가 O(1)이어야 하는 이유다. 꽉 차지 않은 마지막 block은 hash가 없으므로 공유되지 않는다.

#### 설계 결정: prefill과 decode를 나누지 않는다

V1 scheduler에는 prefill phase와 decode phase가 따로 없다. [코드 주석](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L594)도 "There's no 'decoding phase' nor 'prefill phase' in the scheduler"라고 적어 둔다. prompt token과 생성된 token을 똑같이 "아직 계산하지 않은 token"으로 보고, 결정은 `{request_id: num_tokens}` 같은 dictionary 하나로 표현한다. V1 소개 글은 이 표현이 chunked prefill, prefix caching, speculative decoding까지 담을 만큼 일반적이라고 설명한다([vLLM V1 소개 글](https://blog.vllm.ai/2025/01/27/v1-alpha-release.html)). 앞의 step timeline 그림에서 prefill과 decode가 한 step에 섞이는 것도 이 덕분이다. V1을 다시 설계하며 정리한 [#8779](https://github.com/vllm-project/vllm/issues/8779)는 그 배경으로 "scheduling is not cheap"을 든다. 이전 scheduler는 step마다 `running` 전체를 Python으로 훑었고, 그 CPU 시간이 GPU를 놀게 했다. 표현을 하나로 줄인 것은 이 비용을 줄이는 방향과 맞닿아 있다.


#### 설계 결정: free block queue는 직접 만든 이중 연결 리스트다

`free_block_queue`는 Python `deque` 대신 vLLM이 직접 만든 이중 연결 리스트다. 이 구조는 V1에 prefix caching을 넣은 [#9972](https://github.com/vllm-project/vllm/pull/9972)에서 들어왔다. PR은 `deque`보다 나은 점을 두 가지로 든다. 중간의 block을 O(1)에 뺄 수 있고, 새 Python 객체를 만들지 않고 block 객체의 포인터만 바꾼다. 앞의 prefix caching에서 반납된 block을 queue 중간에서 다시 꺼내는 일이 바로 첫째 이유다. 같은 PR의 benchmark는 prefix cache 적중률 49%인 offline batch에서 입력 처리량이 약 1.8배(17,916에서 32,258 tok/s)로 늘었다고 보고한다.

#### 설계 결정: prefix caching은 기본으로 켠다

V1은 prefix caching을 처음부터 기본 기능으로 설계했다. [#8779](https://github.com/vllm-project/vllm/issues/8779)는 V1의 방향 중 하나로 "Prefix-caching as a first-class feature"를 들고, 그 overhead를 줄이는 것을 목표로 삼았다. v0.32.0에서도 model이 지원하면 prefix caching이 [기본으로 켜진다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L3021-L3027). 같은 system prompt나 대화 기록을 공유하는 request가 많을수록 prefill에서 아끼는 계산이 커진다.

### 5. Forward: GPU forward와 sampling

5번은 worker가 [`SchedulerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L232)대로 GPU에서 forward를 한 번 돌리고, request마다 다음 token을 뽑는 단계다.

EngineCore의 busy loop는 step마다 [`step_fn`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L242-L246)을 호출한다. 가장 단순한 [`step()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L657-L687)은 아래 순서로 한 step을 처리한다.

```python
scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
future = self.model_executor.execute_model(scheduler_output, non_block=True)
grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
model_output = future.result()
if model_output is None:
    model_output = self.model_executor.sample_tokens(grammar_output)
engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)
```

executor는 [서버 초기화 5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)에서 본 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)로 worker의 model runner를 호출한다. model runner의 [`execute_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1719-L2087)은 request 상태와 KV block table을 갱신하고, attention metadata를 준비한 뒤 forward를 실행한다. CUDA graph 모드와 batch 크기에 따라, capture해 둔 graph를 재생하거나 model을 직접 호출한다. 이어서 [`sample_tokens()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L2088-L2175)가 마지막 hidden state로 logits를 만들고, sampling parameter를 적용해 request마다 token ID를 뽑는다. 결과가 [`ModelRunnerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/outputs.py#L267)이다.

한 step 안에서 여러 request의 token을 어떻게 한 줄로 묶고, 각 token의 KV를 어디에 저장하는지는 뒤의 "실행 batch와 KV cache" 파트에서 다룬다.

#### 설계 결정: async scheduling으로 scheduling과 실행을 겹친다

async scheduling이 꺼져 있으면 EngineCore는 `step()`으로 schedule, forward, 결과 처리를 차례로 한다. GPU가 step N을 마치면 CPU가 결과를 받아 상태를 갱신하고 step N+1을 짜는데, 그동안 GPU는 다음 일을 받지 못하고 기다린다. 순서대로 할 수밖에 없었던 이유는 step N+1을 짜려면 step N에서 뽑힌 token을 알아야 하기 때문이다.

v0.32.0은 조건이 맞으면 [async scheduling을 자동으로 켠다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L1585). 이때 EngineCore는 [`step()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L657-L687) 대신 [`step_with_batch_queue()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L698)를 쓴다. 새 batch의 실행을 먼저 시작하고, 그 실행이 GPU에서 도는 동안 다음 step을 schedule한다. 앞선 batch의 결과는 queue가 차거나 더 넣을 수 없을 때 받는다. 동시에 진행하는 batch 수는 [`max_concurrent_batches`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L577)가 정한다.

이 구조는 [#19970](https://github.com/vllm-project/vllm/pull/19970)에서 들어왔다. 목표는 scheduler를 실행보다 한 step 앞서 돌게 해서, scheduling에 드는 CPU 시간을 GPU 실행 뒤에 숨기는 것이다. PR은 이 방식이 [NanoFlow](https://arxiv.org/abs/2408.12757) 논문의 접근과 비슷하다고 밝힌다. 처음에는 `--async-scheduling`으로 켜는 실험 기능이었다. [`AsyncScheduler`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/async_scheduler.py)는 이 의존성을 placeholder로 푼다. step N의 결과를 기다리지 않고 request마다 다음 token이 하나 나온다고 가정해 `num_output_placeholders`를 올려 두고 step N+1을 짠다. 실제 token ID는 GPU에 남아 있는 step N의 sampling 결과를 worker가 바로 이어 붙이고, 결과가 CPU에 도착하면 placeholder를 실제 token으로 바꾼다. EOS로 끝난 request처럼 가정이 틀린 경우에는 미리 계산한 결과를 버린다. 이 기능은 v0.14.0부터 기본으로 켜졌다.

### 6. Detokenize: token ID에서 응답까지

6번은 뽑힌 token ID를 request별 출력으로 되돌리고, text로 바꿔 client에 보내는 단계다. 이 일은 EngineCore와 API server에 나뉘어 있다.

EngineCore에서는 [`Scheduler.update_from_output()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2026)이 [`ModelRunnerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/outputs.py#L267)의 token ID와 logprob을 request별로 나누고, request 상태를 갱신한다. EOS token이나 `max_tokens`에 닿은 request는 여기서 끝난다. 결과는 client별 [`EngineCoreOutputs`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/__init__.py#L259)로 묶이고, [`_process_engine_step()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1603)이 이를 output queue에 넣는다. output thread가 queue에서 꺼내 PULL 소켓으로 보낸다.

API server에서는 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)의 background loop인 [`output_handler()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L845)가 이 출력을 받아 [`OutputProcessor.process_outputs()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/output_processor.py#L681)에 넘긴다. 여기서 request별 detokenizer가 새 token ID를 text로 바꾸고, stop string을 확인하고, [`RequestOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/outputs.py#L129)을 만들어 3번에서 등록한 queue에 넣는다. queue를 기다리던 `generate()`가 깨어나 이 값을 handler에 넘긴다.

handler는 응답 형식에 맞게 마무리한다. streaming이면 [`chat_completion_stream_generator()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L466)가 [`RequestOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/outputs.py#L129)마다 chat chunk를 만들어 `data: ...` 형식으로 보내고, 끝에 `data: [DONE]`을 보낸다. non-streaming이면 [`chat_completion_full_generator()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L935)가 generator를 끝까지 읽은 뒤 최종 text와 usage를 `ChatCompletionResponse` JSON 하나로 만든다. SSE chunk 수와 생성 token 수는 일대일이 아니다. 첫 role chunk와 마지막 usage chunk가 따로 있고, detokenizer가 문자를 다 만들 때까지 text를 미루기도 한다.

#### 설계 결정: stop string은 API server에서 판단한다

EOS token과 `max_tokens`는 EngineCore가 판단하지만, stop string은 API server의 detokenizer가 판단한다. stop string은 token ID가 아니라 text에 대한 조건이라서, text를 만드는 쪽에서 보는 것이 자연스럽다. stop string을 만나면 API server는 [`abort_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/output_processor.py#L552)로 frontend 상태를 정리하고, EngineCore에 abort를 보내 아직 실행 중인 request를 멈춘다. 이 분담은 V1 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)을 만든 [#9826](https://github.com/vllm-project/vllm/pull/9826)의 설계 메모에 "stop strings are detected in the detokenizer and we send an abort message"로 적혀 있다.

### 7. Free blocks: request 종료와 KV block 정리

7번은 끝난 request가 쓰던 자원을 돌려주는 단계다. request는 정상 완료, client 취소, 오류 중 하나로 끝나고, 어느 경우든 KV block을 반납한다.

정상 완료는 6번의 `update_from_output()`에서 바로 정리된다. abort는 [`finish_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2649)가 request를 waiting queue나 running queue에서 빼낸다. 두 경로 모두 [`_free_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2714)로 모이고, 이 함수가 결국 [`KVCacheManager.free()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L620)로 block을 돌려준다. 여기서 free는 GPU 메모리를 CUDA allocator에 돌려주는 것이 아니다. block pool에서 참조를 풀어, 다음 request가 이 block을 다시 쓸 수 있게 하는 것이다. GPU가 아직 그 block을 쓰고 있을 수 있으면, scheduler는 안전한 step까지 free를 미룬다.

client가 연결을 끊으면 1번의 cancellation이 [`AsyncLLM.generate()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L698-L809)까지 전달된다. `generate()`는 [`asyncio.CancelledError`를 받아](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L779) [`abort()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L911)를 호출하고, 이 함수가 API server의 출력 상태와 EngineCore 양쪽에서 request를 지운다. 그래서 끊긴 request가 GPU에서 계속 token을 만들지 않는다.

## 실행 batch와 KV cache

이 파트는 request 처리 4번과 5번에서 미뤄 둔 내용을 다룬다. 먼저 여러 request를 padding 없이 한 step에 묶는 방식을 보고, 이어서 scheduler가 request와 KV block을 어떻게 따로 관리하는지, 그리고 한 step의 token이 GPU에서 어떻게 한 줄로 묶이고 KV cache 주소를 찾는지를 본다. 예시의 숫자는 아래 그림과 같고, block 크기는 기본값인 16 token이다.

### padding 없는 continuous batching

continuous batching은 지금도 쓴다. 바뀐 것은 padding이다. 두 개념을 나눠서 보면 차이가 보인다.

<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/03-4-batching-compare-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/03-4-batching-compare-dark.svg"
  caption="같은 request 4개를 static batching과 vLLM의 continuous batching으로 처리할 때."

그림의 위쪽은 batch 단위로 묶는 static batching이다. A, B, C를 한 batch로 묶으면 가장 긴 A가 끝날 때까지 batch가 유지된다. 먼저 끝난 B와 C의 자리는 padding으로 채우고, 그동안 도착한 D는 batch가 끝나는 step 7까지 기다린다. 아래쪽 vLLM은 batch를 step마다 다시 짠다. B와 C는 끝난 step 바로 다음부터 빠지고, step 2에 도착한 D는 step 3부터 들어온다. 그래서 step 3에서는 A, B, C의 decode token과 D의 prefill token이 한 줄로 묶여 forward 한 번에 들어간다.

흔히 보는 continuous batching 그림은 batch 슬롯 몇 개를 고정해 두고, 슬롯이 비면 다음 request로 채우는 모습이다. vLLM에는 이런 슬롯도 없다. step마다 `running` request 중 token budget과 KV block이 허락하는 만큼의 token을 골라 한 줄로 이어 붙일 뿐이다. 그래서 step마다 들어가는 request 수와 token 수가 모두 달라진다.

- continuous batching: batch 구성을 step마다 바꾼다. Orca 논문의 iteration-level scheduling에서 왔다([Yu et al., OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/yu)).
- padding 제거: request를 `[request 수 × 최대 길이]` 격자로 맞추지 않고, token을 한 줄로 이어 붙인다. request 경계는 position과 attention metadata로 따로 넘긴다([Anatomy of vLLM](https://vllm.ai/blog/2025-09-05-anatomy-of-vllm)).

이 한 줄 배열과 block table이 실제로 어떻게 생겼는지는 아래에서 차례로 본다. padding이 완전히 사라진 것은 아니다. CUDA graph를 쓸 때는 batch 크기를 capture한 크기로 맞추느라 끝에 약간 남는다.

### request와 KV block의 자료구조

request와 KV block은 따로 관리된다. request 객체는 KV block을 직접 들고 있지 않고, KV block 쪽도 request를 가리키지 않는다. 둘은 request ID로만 이어진다. EngineCore 프로세스의 CPU 쪽에는 세 가지 자료구조가 있다.

- [`Request`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L60): scheduler가 관리하는 request 상태다. `prompt_token_ids`, 지금까지 만든 output token, 계산을 마친 token 수(`num_computed_tokens`), 상태(`status`), `sampling_params`, prefix caching용 block hash 목록(`block_hashes`)을 담는다. `waiting`, `running` queue에 들어가는 것이 이 객체다.
- [`KVCacheBlock`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L176-L200): KV block 하나의 metadata다. `block_id`, 참조 수(`ref_cnt`), block hash, 그리고 `free_block_queue`의 이중 연결 리스트용 `prev_free_block`과 `next_free_block`만 들고 있다. KV 값 자체는 들고 있지 않다.
- [`req_to_blocks`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L122-L125): request ID에서 그 request가 쓰는 `KVCacheBlock` 목록으로 가는 dictionary다. `KVCacheManager` 안에 있고, request가 끝나면 이 목록으로 block을 돌려준다.

실제 KV 값은 GPU에 있다. 서버 초기화 5번에서 layer마다 할당한 KV cache tensor를 block 단위로 나눈 것이고, `block_id`는 그 tensor 안의 block 위치다. 모든 `KVCacheBlock`은 [`BlockPool.blocks`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L172)에 미리 만들어져 있고, block 0은 [null block](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L184-L188)으로 따로 잡아 둔다. 그래서 실제로 나눠 주는 block ID는 1부터 시작한다.

worker 쪽에는 이 정보의 사본이 있다. scheduler는 step마다 [`SchedulerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L232)에 새로 받은 block ID를 실어 보내고, worker는 이를 [`BlockTables`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/block_table.py#L17)에 쌓는다. block table은 request마다 한 행이고, 행에는 그 request의 block ID가 순서대로 들어 있다. 아래 예시에서 request A의 행은 `[7, 12]`, B는 `[3]`, C는 `[9, 4]`다.

### step 안의 token packing

한 step의 batch는 request별 격자가 아니라 token 한 줄이다. 그림의 step에서 A는 decode token 1개, B는 prefill token 2개, C는 prefill 조각 3개를 계산한다. worker의 [`InputBatch`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/input_batch.py#L39-L100)는 이를 아래 배열로 만든다.

```text
input_ids        = [A16, B0, B1, C14, C15, C16, PAD, PAD]
positions        = [ 16,  0,  1,  14,  15,  16,   -,   -]
query_start_loc  = [0, 1, 3, 6]

```

`input_ids`와 `positions`는 이번 step에 계산할 token만 담는다. A는 앞의 16 token을 이미 계산했으므로 A16 하나만 들어가고, 앞 token의 KV는 KV cache에서 읽는다. `query_start_loc`은 각 request의 token이 이 줄의 어디서 시작하는지 알려 준다. A는 0, B는 1, C는 3에서 시작하고, 끝은 6이다. `seq_lens`는 request마다 KV cache까지 포함한 전체 길이다. attention kernel은 이 두 배열로 request 경계를 알고, 각 token이 자기 request의 token만 보게 한다. 그래서 padding 없이 길이가 다른 request를 한 forward에 넣을 수 있다.

### block table: token 위치에서 KV cache 주소로

forward 중에 attention layer는 각 token의 새 KV를 KV cache에 써야 한다. 어디에 쓸지는 `slot_mapping`이 알려 준다. slot은 KV cache를 token 단위로 센 주소이고, [slot mapping kernel](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/block_table.py#L341-L348)이 block table로 계산한다.

$$
\text{slot} = \text{block\_table}\big[\lfloor \text{position} / \text{block\_size} \rfloor\big] \times \text{block\_size} + (\text{position} \bmod \text{block\_size})
$$

C14는 position 14이므로 C의 첫 block(9)의 14번째 칸, `9 × 16 + 14 = 158`이다. C16은 position 16이라 첫 block을 넘어 둘째 block(4)의 0번째 칸, `4 × 16 + 0 = 64`가 된다. 같은 request의 token이라도 block 경계를 넘으면 KV cache에서 멀리 떨어진 곳에 쓰인다. 이것이 paged KV cache다. 이번 step의 `slot_mapping`은 아래와 같고, padding token은 `-1`로 채워 아무 데도 쓰지 않는다.

```text
slot_mapping = [192, 48, 49, 158, 159, 64, -1, -1]
```

다음 step에 decode할 때도 같은 계산을 한다. A가 position 17의 token을 계산하면 그 KV는 block 12의 1번째 칸(`12 × 16 + 1 = 193`)에 쓰인다. block이 꽉 차면 scheduler가 `allocate_slots()`로 새 block을 받아 block table에 한 칸을 더한다.

### scheduler의 block 소유와 재사용

block의 주인은 scheduler다. worker는 받은 block table대로 읽고 쓸 뿐, block을 할당하거나 반납하지 않는다. 할당, 반납, prefix cache 재사용 규칙은 request 처리 4번의 [KVCacheManager 소제목](#kvcachemanager-block을-나눠-주고-돌려받는-방식)에서 다뤘다. 여기서는 그 규칙이 위 자료구조에서 어떻게 보이는지만 정리한다.

- 할당: `free_block_queue`에서 `KVCacheBlock`을 꺼내 `ref_cnt`를 1로 만들고, `req_to_blocks[request_id]`에 붙인다. worker에는 다음 `SchedulerOutput`으로 block ID가 전달된다.
- 공유: prefix cache가 맞으면 같은 `KVCacheBlock`이 두 request의 `req_to_blocks`에 함께 들어가고, `ref_cnt`가 2가 된다. 두 request의 block table 행에 같은 block ID가 들어가므로, GPU의 같은 KV를 함께 읽는다.
- 반납: request가 끝나면 그 request의 block마다 `ref_cnt`를 1씩 내린다. 0이 된 block만 `free_block_queue`로 돌아간다. GPU 메모리는 그대로이고, 다음에 이 block을 받는 request가 그 자리를 덮어쓴다.

### padding이 남는 곳: CUDA graph

padding은 한 군데에 남아 있다. CUDA graph는 capture한 batch 크기로만 재생할 수 있어서, 이번 step의 token 수를 가장 가까운 capture 크기로 올린다. 그림의 step은 실제 token이 6개(`num_tokens`)지만, 크기 8의 graph를 쓰려고 2개를 padding해 8개(`num_tokens_after_padding`)로 만든다. padding token의 slot은 `-1`이라 KV cache에 쓰이지 않고, 그 출력은 버린다. 이 padding은 request마다 생기는 것이 아니라 batch 끝에 한 번만 생기므로, 낭비는 batch 크기를 맞추는 몇 token에 그친다.
