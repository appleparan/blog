## Introduction

예전에 Inside vLLM: Anatomy of a High-Throughput LLM Inference System을 읽고는 '아, 그렇구나' 하고 넘어간 적이 있다. 그런데 막상 누군가에게 설명하려니 말이 제대로 나오지 않았다. 분명 읽을 때는 이해했다고 생각했는데, 정작 내 언어로 설명할 수 없다는 사실이 꽤 부끄러웠다.

## 큰 그림

코드를 따라가기 전에 전체 구조부터 보고 가자.

### step: vLLM이 요청을 처리하는 단위

그 전에 vLLM이 요청을 어떻게 처리하는지부터 알아야 한다. vLLM은 요청 단위가 아니라 step이라는 시간 단위로 일한다. 요청을 하나씩 끝까지 처리하지 않고, step을 돌리면서 step 한 번에 살아 있는 요청 전부를 한꺼번에 조금씩 진행시킨다. prefill 중인 요청은 prompt token을 한 조각 더 계산하고, decode 중인 요청은 다음 token을 하나 더 만든다.

/>

풀어 쓰면 이렇다.

1. **Step은 엔진의 기본 실행 단위다.** CPU의 clock과 비슷하게 엔진의 실행 주기를 나타내며, 이하 모든 step은 이 단위를 의미한다.
2. **매 step마다 엔진은 처리할 요청과 token을 선택한다.** 선택된 token들을 하나의 GPU forward pass로 처리하고, 요청마다 다음 token을 하나씩 생성한다.
3. **하나의 요청은 여러 step에 걸쳐 처리된다.** 먼저 입력 token들을 처리하는 prefill을 수행하고, 이후 매 step에서 decode를 반복하며 출력 token을 생성한다.
4. **한 step에는 여러 요청이 함께 처리될 수 있다.** 수백 개의 요청이 하나의 batch에 포함될 수 있으며, 긴 요청 하나가 GPU를 독점하지 않고 다른 요청들과 연산 자원을 공유한다.

### vLLM 컴포넌트

이 step을 돌리는 vLLM 서버는 크게 세 컴포넌트로 나뉜다.

- **API frontend**는 HTTP를 받고, chat template을 렌더링하고 token화하며, 결과 token ID를 text와 HTTP 응답으로 바꾼다. 
    - 원래는 Python이었지만, Rust Frontend로 전환하기 위해 현재 구현되고 있다. 아직 몇 가지 기능들이 구현이 안된게 있으므로 이 글에서는 Python Frontend로 설명할 예정이다.
- **EngineCore**는 request의 priority, token budget, KV cache block을 관리하고, 이번 step에 실행할 일을 scheduler가 고른다.
- **Worker와 model runner**는 scheduler가 고른 일을 GPU forward와 sampling으로 처리한다. 실행 token은 요청별 가변 길이를 한 batch로 pack하지만, KV state는 별도 page/block으로 관리한다.

아래 그림은 API server 하나와 EngineCore 하나를 쓰는 uni executor 경로다. 화살표는 요청과 결과가 이동하는 방향이고, GPU는 프로세스 밖의 장치로 표시했다.

그림에서 Scheduler와 Worker 사이를 도는 화살표가 앞서 말한 step이다. 한 step을 조금 더 자세히 보면 세 단계다.

1. scheduler가 지금 살아 있는 요청들을 보고, 이번 step에 계산할 token을 고른다. 한 번에 쓸 수 있는 token 수(token budget)와 KV cache 자리가 한도다.
2. worker가 고른 token들을 GPU에서 forward 한 번으로 계산하고, 요청마다 다음 token을 하나씩 뽑는다(sampling).
    - 이때의 batch는 요청별로 길이를 맞춰 padding한 [요청 수 x 길이] 격자가 아니다. 요청마다 길이가 다른 token 조각을 그대로 한 줄로 이어 붙인 것이다. 예를 들어 A의 prefill 512개, B의 prefill 10개, C의 decode 1개면 523개짜리 token 줄 하나가 forward에 들어간다.
    - 각 요청의 조각이 어디서 시작하고 끝나는지, 그 요청의 지난 KV cache가 어느 block에 있는지는 따로 넘겨주므로 attention은 요청을 섞지 않는다. sampling도 요청마다 자기 조각의 마지막 위치에서 한다.
3. scheduler가 뽑힌 token을 각 요청에 기록하고, 끝난 요청은 내보낸다.

prefill은 보통 한 step에 끝나지만, prompt가 길면 token budget에 맞춰 여러 step에 나눠서 한다(chunked prefill). 그래서 한 step의 batch에는 prefill 중인 요청과 decode 중인 요청이 섞여 있고, 위 예시의 A, B, C가 바로 그 모습이다.

step마다 나온 token ID는 frontend로 돌아간다. streaming 요청이면 그때그때 SSE event가 되고, non-streaming 요청이면 완료된 뒤에 최종 JSON으로 만들어진다.

이후 글은 두 부분으로 나뉜다. 서버 초기화에서는 이 그림의 상자들이 만들어지는 순서를 따라가고, 요청 처리에서는 화살표를 따라간다.

### 1. `vllm serve`와 서버 모드 선택

`vllm serve`를 한다고 하자. `vllm/entrypoints/cli/main.py`를 통해 `vllm/entrypoints/cli/serve.py`로 실행하게 된다.
외부 LB라던가 Multiport같은 특수한 옵션을 주지 않는다면, Single API Server가 올라오게 된다.

```python
args.api_server_count = None
uvloop.run(run_server(args))
```

API server 수와 EngineCore 수는 따로 정한다. API server를 늘리면(예: `--api-server-count 2`) tokenize와 응답 직렬화 같은 frontend의 CPU 작업을 여러 프로세스가 나눠 지고, engine은 하나를 공유한다. data parallelism은 반대로 engine과 model replica를 늘린다. 이 글은 둘 다 하나인 구성만 다룬다.

### 2. 소켓 bind와 `run_server_worker`

Single API 서버는 `setup_server` 후 `run_server_worker`를 실행한다. [`vllm/entrypoints/launchers/api_server/entry.py`](https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/launchers/api_server/entry.py#L164)

`setup_server`는 로깅 셋업, parser plugin 로드, argument 검증 후 포트(소켓)을 열게 된다.
실질적으로 메인역할을 하는건 `run_server_worker`이다.
`run_server_worker`: `setup_server`로 연 소켓을 받아서 엔진 클라이언트(`AsyncLLM`)를 만들고, FastAPI 앱을 구성한 뒤 `uvicorn`으로 서빙한다. 물론 종료 처리도 이 함수가 처리한다.
