## Introduction

예전에 [Inside vLLM: Anatomy of a High-Throughput LLM Inference System](https://www.aleksagordic.com/blog/vllm)을 읽고는 '아, 그렇구나' 하고 넘어간 적이 있다. 그런데 막상 누군가에게 설명하려니 말이 제대로 나오지 않았다. 예전에 비슷한 내용을 [코드](https://github.com/appleparan/nano-vllm-rs)를 통해서도 공부하고 작동원리를 이해했다고 생각했지만, 정작 내가 설명할 때는 기억도 잘 나지 않고, 코드도 다 안뜯어봐서 디테일도 없었고 많이 부끄러웠다.

이럴 때 가장 좋은 방법은 역시 직접 글로 정리해 보는 것이다. 코드를 따라가며 이해한 내용을 내 방식대로 풀어 쓰다 보면, 적어도 쉽게 잊어버리지는 않는다.

게다가 위 글은 2025년 가을의 글이고, 그사이 vLLM에는 큰 변화가 많았다. V0 engine이 완전히 제거되어 V1만 남았고, async scheduling이 기본으로 켜졌으며, Model Runner V2가 모든 model의 기본 실행 경로가 되었다. Python API server를 대신할 Rust frontend도 실험 기능으로 들어왔다. 따라서 이번에는 2026년 10월, vLLM v0.32.0을 기준으로 내부 아키텍처를 다시 살펴보려 한다.

이번 글은 설명을 요약하는 대신, vLLM 소스 코드를 직접 열어 보며 따라간다. 기준은 text 생성 model 하나를 GPU 하나에 띄우고 `/v1/chat/completions` request를 보내는 경우다. 순서는 이렇다.

1. 큰 그림: vLLM이 request를 step으로 쪼개는 방식과, 그 step을 돌리는 두 process(API server, EngineCore)
2. 서버 초기화: `vllm serve` 한 줄이 config를 만들고, EngineCore를 띄우고, model과 KV cache를 GPU에 올리는 순서
3. request 처리: chat request 하나가 tokenize, schedule, forward, detokenize를 거쳐 응답이 되고 정리되는 경로
4. 실행 batch와 KV cache: 위 과정을 받치는 batch와 KV block 자료구조. chunked prefill, speculative decoding, 멀티턴, disaggregated prefill/decode, 여러 종류의 attention을 섞은 model에서 이 자료구조가 어떻게 쓰이는지도 본다

1과 2는 서버라는 상자가 만들어지는 순서이고, 3은 그 상자 사이를 오가는 화살표다. 4는 3에서 반복해서 등장하는 KV block을 따로 모아 자세히 본다.

## 큰 그림

LLM은 token을 하나씩 만든다. request(요청)는 이 token 생성을 묶은 단위다. prompt를 받아 output token을 끝까지 만들어 내는 일 전체가 request 하나다. vLLM은 이 request를 한꺼번에 처리하지 않고 step으로 다시 쪼갠다. step은 GPU forward 한 번이고, step 한 번에 각 request는 자기 token을 몇 개씩만 계산한다. 그래서 request 하나는 여러 step에 걸쳐 끝나고, step 하나에는 여러 request의 token이 함께 들어간다.

request는 두 단계로 진행된다. prefill은 prompt token을 계산하는 단계이고, decode는 output token을 하나씩 만드는 단계다. token을 계산하면 그 token의 K, V 값이 나온다. vLLM은 이 값을 다음 token 계산에 다시 쓰려고 GPU 메모리에 보관한다. 이 저장소가 KV cache다.

코드를 따라가기 전에 이 관계와, 이것을 돌리는 전체 구조부터 보고 가자.

### step: LLM request를 쪼개는 단위

vLLM 구조를 이해하는 출발점은 LLM request 하나를 여러 step으로 쪼갠다는 점이다. vLLM은 request 단위가 아니라 step이라는 시간 단위로 일한다. request를 하나씩 끝까지 처리하지 않고, step을 돌리면서 step 한 번에 살아 있는 request 전부를 한꺼번에 조금씩 진행시킨다. prefill 중인 request는 prompt token을 계산하고(긴 prompt를 여러 step에 나누는 chunked prefill은 아래에서 본다), decode 중인 request는 다음 token을 하나 더 만든다.

풀어 쓰면 이렇다.

1. **Step은 엔진의 기본 실행 단위다.** CPU의 clock과 비슷하게 엔진의 실행 주기를 나타내며, 이하 모든 step은 이 단위를 의미한다.
2. **매 step마다 엔진은 처리할 request와 token을 선택한다.** 선택된 token들을 하나의 GPU forward pass로 처리하고, request마다 다음 token을 하나씩 생성한다.
3. **하나의 request는 여러 step에 걸쳐 처리된다.** 먼저 입력 token들을 처리하는 prefill을 수행하고, 이후 매 step에서 decode를 반복하며 출력 token을 생성한다.
4. **한 step에는 여러 request가 함께 처리될 수 있다.** 수백 개의 request가 하나의 batch에 포함될 수 있으며, 긴 request 하나가 GPU를 독점하지 않고 다른 request들과 연산 자원을 공유한다.

### vLLM 컴포넌트

이 step을 돌리는 vLLM 서버는 아래 그림처럼 두 process와 GPU로 나뉜다. 그림은 API server 하나와 EngineCore 하나를 쓰는 uni executor 구성이다.

그림의 상자를 위에서부터 차례로 보면 이렇다.

- **API server process**는 HTTP request를 엔진 request로, 엔진 출력을 HTTP 응답으로 바꾼다.
    - **FastAPI app**: FastAPI router가 HTTP request를 받는다. chat template과 tokenizer로 prompt를 token ID로 바꿔 AsyncLLM에 넘기고, 돌아온 결과를 JSON이나 SSE로 응답한다.
    - **AsyncLLM**: EngineCore를 호출하는 engine client다. request를 ZMQ로 EngineCore에 보내고, 돌아온 출력을 FastAPI app에 넘긴다.
    - 지금은 Python 구현이다. Rust frontend로 전환하는 작업이 진행 중이지만 아직 빠진 기능이 있어서, 이 글은 Python frontend로 설명한다.
- **EngineCore process**는 busy loop를 돌며 ZMQ로 받은 request를 Scheduler에 넣고, step을 실행하고, 결과를 AsyncLLM으로 보낸다.
    - **Scheduler**: 대기 중인 request와 실행 중인 request를 보고, token budget과 priority에 따라 이번 step에 request마다 계산할 token 수를 정한다. 안에 있는 KV cache manager가 KV cache block을 request에 할당하고, 끝난 request의 block을 회수한다.
    - **Executor · Worker · ModelRunner**: Scheduler가 정한 일을 GPU에서 실행한다. Executor는 EngineCore가 worker를 호출하는 창구이고, GPU가 하나면 같은 process 안의 [`UniProcExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/uniproc_executor.py#L51)가 쓰인다. Worker는 GPU 장치를 초기화하고 model을 load한다. ModelRunner는 이번 step의 token을 1차원 배열 하나로 이어 붙여 batch를 만들고 forward와 sampling을 실행한다.
- **GPU**는 process 밖의 장치다. ModelRunner가 보낸 forward와 sampling을 계산하고 token ID를 돌려준다.

그림의 주황색 STEP LOOP가 앞서 말한 step이다. 한 step을 조금 더 자세히 보면 세 단계다.

1. scheduler가 지금 살아 있는 request들을 보고, 이번 step에 계산할 token을 고른다. 한 번에 쓸 수 있는 token 수(token budget)와 KV cache 자리가 한도다.
2. worker가 고른 token들을 GPU에서 forward 한 번으로 계산하고, request마다 다음 token을 하나씩 고른다(sampling).
    - 이때의 batch는 request별로 길이를 맞춰 padding한 [request 수 x 길이] 격자가 아니다. request마다 길이가 다른 token 조각을 그대로 1차원 배열 하나로 이어 붙인 것이다. 예를 들어 A의 decode 1개, B의 prefill 2개, C의 prefill 조각 3개면 6개짜리 token 줄 하나가 forward에 들어간다. 이 A, B, C는 뒤의 "실행 batch와 KV cache" 파트에서 다시 쓰는 예시다.
    - 각 request의 조각이 어디서 시작하고 끝나는지, 그 request의 지난 KV cache가 어느 block에 있는지는 따로 넘겨주므로 attention은 request를 섞지 않는다. sampling도 request마다 자기 조각의 마지막 위치에서 한다.
3. scheduler가 sampling한 token을 각 request에 기록하고, 끝난 request는 내보낸다.

prefill은 보통 한 step에 끝나지만, prompt가 길면 token budget에 맞춰 여러 step에 나눠서 한다(chunked prefill). 그래서 한 step의 batch에는 prefill 중인 request와 decode 중인 request가 섞여 있고, 위 예시의 A, B, C가 바로 그 모습이다.

step마다 나온 token ID는 frontend로 돌아간다. streaming request면 그때그때 SSE event가 되고, non-streaming request면 완료된 뒤에 최종 JSON으로 만들어진다.

이후 글은 두 부분으로 나뉜다. 서버 초기화에서는 이 그림의 상자들이 만들어지는 순서를 따라가고, request 처리에서는 화살표를 따라간다.

### 1. Server mode selection: `vllm serve`에서 `run_server()`까지

`vllm serve`를 실행하면 [`vllm/entrypoints/cli/main.py`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/main.py)가 subcommand를 찾아 [`vllm/entrypoints/cli/serve.py`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/serve.py)의 [`ServeSubcommand.cmd()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/serve.py#L54)를 호출한다. 이 함수가 옵션을 보고 서버를 어떤 모드로 띄울지 정한다. 외부 load balancer나 multi-port 같은 특수한 옵션을 주지 않으면, 지금 process에서 API server 하나가 [`run_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L165-L177)로 올라온다.

```python
# Single API server (this process).
args.api_server_count = None
uvloop.run(run_server(args))
```

다른 모드는 아래 세 가지다.

- [`run_dp_supervisor()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/dp_supervisor.py#L562): `--data-parallel-multi-port-external-lb`를 주면 쓰인다. `DPSupervisor`가 이 노드의 DP rank마다 vLLM 서버 process를 하나씩 띄우고, 각 서버는 자기 port로 request를 받는다.
- [`run_headless()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/serve.py#L181): `--headless`를 주면 쓰인다. API server 없이 EngineCore만 띄우고, request는 다른 노드의 frontend에서 받는다. 주로 vLLM을 여러 노드에 띄울 때 worker 노드에서 쓴다.
- [`run_multi_api_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/cli/serve.py#L269): API server가 둘 이상이거나 Rust frontend를 쓰면 쓰인다. DP(data parallelism)를 켜고 API server 수를 따로 정하지 않으면 그 기본값이 DP 크기가 되므로, 이 경로로 온다.

Rust frontend는 Python API server를 대신할 수 있는 실험 기능이다(`VLLM_USE_RUST_FRONTEND=1`). 처음 제안한 RFC는 당분간 Python frontend를 대체하지 않는다고 밝혔다([RFC #40846](https://github.com/vllm-project/vllm/issues/40846), [Roadmap #44280](https://github.com/vllm-project/vllm/issues/44280)). 이 글은 기본 경로인 [`run_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L165-L177)만 따라간다.

#### 설계 결정: API server와 EngineCore를 따로 늘린다

API server 수와 EngineCore 수는 따로 정한다. API server를 늘리면(예: `--api-server-count 2`) tokenize와 응답 직렬화 같은 frontend의 CPU 작업을 여러 process가 나눠 지고, engine은 하나를 공유한다. data parallelism은 반대로 engine과 model replica를 늘린다. 이 글은 둘 다 하나인 구성만 다룬다. 이 구조는 [#17546](https://github.com/vllm-project/vllm/pull/17546)에서 들어왔다. 이 PR은 `--api-server-count` 옵션을 추가했고, DP와 함께 쓰면 API server와 EngineCore가 ZMQ로 all-to-all 연결되게 했다. PR의 benchmark는 DP 크기를 키울 때 성능, 특히 TTFT가 이전보다 잘 확장되는 것을 보여 준다.

### 2. Socket bind: listen 전의 port 선점

API server 하나로 띄우는 [`run_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L165-L177)는 두 함수를 차례로 호출한다. [`setup_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L378)가 소켓을 만들어 주소에 bind하고, [`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)가 엔진 client를 만든 뒤 HTTP 서버를 띄운다.

[`setup_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L378)는 vLLM 버전과 기본값이 아닌 인자를 log로 남기고, tool parser와 reasoning parser plugin을 load하고, 인자를 검증한다. 그 다음 소켓을 만들어 bind한다. 기본은 [`create_server_socket()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L335)이 만드는 TCP 소켓이다. `--uds`로 경로를 주면 [`create_server_unix_socket()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L353)이 Unix domain socket을 만든다. 같은 호스트의 reverse proxy가 vLLM과 통신할 때 이 방식을 쓴다.

서버 소켓은 `socket() → bind() → listen() → accept()` 순서로 열린다. [`setup_server()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L378)는 `bind()`까지만 한다. 그래서 엔진을 준비하는 동안 port는 잡혀 있지만, request는 아직 받지 않는다. `listen()`과 `accept()`는 뒤에 나오는 [`serve_http()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L175)에서 일어난다.

[`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)도 tool parser와 reasoning parser plugin을 import한다. API server를 여러 개 띄우면 이 함수가 새 process마다 따로 시작되기 때문이다. 그 다음 [`build_async_engine_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L36)로 엔진 client인 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)을 만들고 [`build_and_serve()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L116)를 호출한다. 서버가 끝나면 엔진을 정리하고 소켓을 닫는 일도 이 함수가 한다.

엔진 초기화는 모두 [`build_async_engine_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L36) 안에서 일어난다. 이 함수가 반환되기 전에 설정 생성, EngineCore process 시작, model load와 KV cache 할당이 모두 끝난다. [3](#3-engine-config-cli-인자에서-vllmconfig까지)~[5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)이 이 과정을, [6번](#6-http-serving-route-등록과-uvicorn-실행)이 그 뒤의 [`build_and_serve()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L116)를 다룬다.

#### 설계 결정: 엔진보다 먼저 bind하는 이유

소켓을 엔진보다 먼저 bind하는 데는 이유가 있다. 코드 주석에 따르면, 엔진을 준비하기 전에 port를 잡아 두어 Ray와의 race condition을 피하려는 것이다([#8204](https://github.com/vllm-project/vllm/issues/8204)). port가 이미 쓰이고 있으면 무거운 엔진 초기화를 시작하기 전에 바로 실패하는 효과도 있다. [#8204](https://github.com/vllm-project/vllm/issues/8204)는 서버가 시작할 때 `address already in use` 오류로 bind에 실패하던 문제였다.

### 3. Engine config: CLI 인자에서 `VllmConfig`까지

3번은 [`build_async_engine_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L36)에서 시작한다. 이 단계는 CLI 인자를 엔진 전체가 공유하는 설정 객체 [`VllmConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2838)로 변환한다. 변환은 **필드 매핑**과 **기본값 결정**의 두 단계로 나뉜다. 단계를 나누는 이유는 설정값 하나를 정할 때 여러 정보를 조합해야 하기 때문이다. CLI 인자만으로는 값을 정할 수 없고, model, 하드웨어, 진입점을 함께 봐야 한다. 그래서 사용자가 정한 값은 그대로 쓰고, 정하지 않은 값만 vLLM이 이 정보들을 조합해 정한다.

[`__post_init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L1414)는 sub-config끼리 서로 어긋나지 않는지 검사하고, [compilation mode](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L1752) 같은 남은 값을 정한다. 이후 [4번](#4-engine-client-asyncllm-생성과-enginecore-연결)의 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)과 [5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)의 [EngineCore](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L115)는 모두 이 객체 하나를 받는다.


#### 설계 결정: 진입점마다 다른 batch 기본값

CUDA GPU에서 [`max_num_batched_tokens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/scheduler.py#L48)의 [기본값 표](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2900-L2952)는 아래와 같다. CPU와 TPU는 값이 따로 있다. GPU 메모리로 행을 고르고, 진입점으로 열을 고른다. 코드 주석은 H100급 GPU에 대해 "use larger offline defaults"라고 적어 두었다. 오프라인 batch 처리는 응답 지연보다 처리량이 중요하므로 한 step을 더 크게 잡는 것으로 보인다.

| GPU | `LLM` 클래스 | `vllm serve` |
| --- | --- | --- |
| 메모리 160GiB 이상 (B200 등) | 16384 | 16384 |
| 메모리 70GiB 이상, A100 제외 (H100, H200) | 16384 | 8192 |
| 그 외 | 8192 | 2048 |

[`UsageContext`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/usage/usage_lib.py#L111)는 CLI 인자가 아니다. 진입점이 코드에서 넘기는 값이다. `vllm serve`는 [`OPENAI_API_SERVER`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L39)를, `LLM` 클래스는 [`LLM_CLASS`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/llm.py#L343)를 넘긴다. 그래서 같은 인자를 줘도 진입점이 다르면 기본값이 달라질 수 있다.

A100은 메모리가 80GB여도 "그 외" 행으로 빠진다. A100에서는 `max_num_batched_tokens`를 크게 잡으면 오히려 처리량이 떨어졌기 때문이다([#17885](https://github.com/vllm-project/vllm/pull/17885)).

### 4. Engine client: `AsyncLLM` 생성과 EngineCore 연결

4번은 엔진 client를 만드는 단계다. 엔진 client는 API server가 엔진에 request를 넣고 결과를 받을 때 쓰는 객체이고, vLLM에서는 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)이다. [`VllmConfig`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2838)가 준비되면 [`AsyncLLM.from_vllm_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L95)가 이 객체를 만든다. [`AsyncLLM.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L87)에서 하는 일은 두 가지다. request 전처리와 결과 후처리를 맡을 객체를 만들고, EngineCore process를 띄워 ZMQ로 연결한다. 먼저 만드는 객체는 아래 세 개다.

- [`renderer`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L158): tokenizer와 chat template을 가지고, 사용자가 보낸 messages를 model 입력 형식(prompt 문자열과 token ID)으로 바꾼다. 이미지 같은 multimodal 입력 처리도 맡는다.
- [`InputProcessor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L161): renderer가 만든 입력과 sampling parameter를 검증하고, EngineCore로 보낼 [`EngineCoreRequest`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/__init__.py#L109)로 묶는다.
- [`OutputProcessor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L171): EngineCore가 돌려준 token ID를 request별로 모아 detokenize하고, logprobs를 붙여 [`RequestOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/outputs.py#L129)으로 바꾼다.

그 다음 [`EngineCoreClient.make_async_mp_client()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L137)를 [호출한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L184). DP를 쓰지 않으면 이 함수는 [`AsyncMPClient`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1106)를 반환한다. DP를 쓰면 외부 load balancer가 있을 때 [`DPAsyncMPClient`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1419)를, 없을 때 vLLM이 직접 분산하는 [`DPLBAsyncMPClient`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1603)를 반환한다. EngineCore process는 이 client의 부모 클래스 [`MPClient.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L595)에서 생긴다.

[`MPClient.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L595)은 먼저 ZMQ 소켓 두 개를 bind한다. request를 보내는 [ROUTER 소켓](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L660-L665)과 출력을 받는 [PULL 소켓](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L667-L669)이다. 그 다음 [`launch_core_engines()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L1198)가 handshake용 소켓을 열고, [`CoreEngineProcManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L237)가 [`EngineCoreProc.run_engine_core()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L282-L283)를 target으로 새 process를 시작한다. 이 함수가 EngineCore process의 진입점이고, process 안에서 일어나는 일은 [5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)에서 이어진다.

두 process는 아래 그림처럼 handshake로 연결된다.

EngineCore가 HELLO를 보내면 API server가 ZMQ 소켓 주소를 돌려준다. EngineCore는 [5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)의 startup을 마친 뒤 READY를 보낸다. [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84) 생성은 [5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)이 끝나야 반환된다.

#### 설계 결정: EngineCore process 분리와 ZMQ

EngineCore를 별도 process로 띄우는 이유는 두 가지다. API server와 엔진의 CPU 작업이 같은 자원을 두고 다투지 않게 하고, CPU 작업과 GPU 실행의 overlapping을 늘리기 위해서다. 처음에는 API server와 엔진이 같은 asyncio event loop를 썼다([RFC #6797](https://github.com/vllm-project/vllm/issues/6797)). [#6883](https://github.com/vllm-project/vllm/pull/6883)에서 API server를 별도 process로 분리했고, V1의 [#9826](https://github.com/vllm-project/vllm/pull/9826)에서 EngineCore를 분리했다. 두 process 사이의 통신에는 [ZeroMQ](https://zeromq.org/)(ZMQ)를 쓴다.

ZMQ는 TCP나 IPC 소켓 위에서 메시지 단위 통신을 제공하는 messaging library다. ZMQ에는 메시지를 중계하는 broker가 없어서, vLLM은 ZMQ용 서버를 따로 띄우지 않는다. API server와 EngineCore가 각자 ZMQ 라이브러리로 소켓을 만들고 서로 직접 연결한다. 메시지를 어떤 방식으로 주고받을지는 소켓 종류로 고르며, 앞에서 본 [ROUTER](https://zeromq.org/socket-api/#router-socket)와 [PULL](https://zeromq.org/socket-api/#pull-socket)이 그 예다. [#6883](https://github.com/vllm-project/vllm/pull/6883)은 gRPC와 benchmark로 비교해 ZMQ를 골랐고, 이 benchmark에서 ZMQ가 TTFT와 TPOT 모두 더 짧았다. API server 쪽은 [`zmq.asyncio`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L21) 소켓을 써서, EngineCore의 출력을 기다리는 동안에도 asyncio event loop가 다른 HTTP request를 처리한다.

이미지 같은 큰 multimodal tensor는 예외적으로 ZMQ를 거치지 않을 수 있다. [`mm_tensor_ipc`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/multimodal.py#L440)를 `"torch_shm"`으로 설정하면 tensor를 공유 메모리로 넘긴다. 이때 ZMQ 메시지에는 tensor 대신 참조만 들어간다. 기본값은 `"direct_rpc"`이고, 이 경우 tensor도 직렬화해 ZMQ로 보낸다.

### 5. EngineCore startup: model load, KV cache allocation, scheduler setup

5번은 EngineCore process가 시작해서 step loop에 들어가기까지의 과정이다. process 안에서 model을 GPU에 올리고, 남은 GPU 메모리로 KV cache를 할당하고, scheduler를 만든다. 이 셋이 갖춰지면 API server에 READY를 보내고 step loop에 들어간다.

[4번](#4-engine-client-asyncllm-생성과-enginecore-연결)에서 [`CoreEngineProcManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/utils.py#L237)가 target으로 넘긴 [`EngineCoreProc.run_engine_core()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1391)가 EngineCore process에서 처음 실행되는 함수다. 이 함수가 [`EngineCoreProc`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1128)를 만든다. [`EngineCoreProc.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1135)은 [`_perform_handshakes()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1250) context를 열어 HELLO를 보내고 ZMQ 주소를 받는다. 그리고 그 context 안에서 [`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)을 [호출한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1194).

[`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)은 model, KV cache, scheduler를 이 순서로 준비한다. 뒤 단계가 앞 단계의 결과를 쓰기 때문이다.

model은 [`executor_class(vllm_config)`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L144)에서 올라온다. GPU 하나로 띄우면 executor는 [`UniProcExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/uniproc_executor.py#L51)이고, 이 process 안에 Worker를 하나 만든다. Worker의 [`init_device()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L436)가 CUDA device와 분산 환경을 초기화하고, GPU 전체 메모리에 `gpu_memory_utilization`을 [곱해](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L535) vLLM이 쓸 메모리 예산을 정한다. 이어서 [`load_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L587)이 model runner를 통해 weight를 GPU에 올린다. GPU를 여러 개 쓰면 [`MultiprocExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/multiproc_executor.py#L111)가 GPU마다 worker process를 따로 띄운다. worker 수는 tensor, pipeline, prefill context parallelism 크기를 곱한 [`world_size`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/parallel.py#L945-L949)다. data parallelism은 EngineCore 자체를 늘리므로, EngineCore 하나에 속한 worker 수에는 들어가지 않는다. 이후 EngineCore가 worker에 시키는 일은 모두 executor의 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)를 거친다. 이 함수는 [5번 끝](#collective_rpc-enginecore가-worker에-일을-시키는-방식)에서 따로 설명한다.

KV cache는 [`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)이 [호출하는](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L157) [`_initialize_kv_caches()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L261)가 준비한다. 먼저 worker에서 layer별 [`KVCacheSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L165)을 모은다. spec에는 KV cache의 shape(block 크기, KV head 수, head 크기)와 dtype, 그리고 full attention, sliding window, MLA 같은 attention 종류가 들어 있다. vLLM은 KV cache를 고정 크기 block으로 나눠 request에 나눠 준다. block 하나는 기본 16 token의 KV를 담는다. 이 값으로 block 하나의 byte 크기가 정해진다. 그 다음 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)로 각 Worker에서 실행되는 [`determine_available_memory()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L634)가 KV cache에 쓸 수 있는 메모리를 잰다. 측정은 두 번이다. 먼저 [`profile_run()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_model_runner.py#L6133)이 한 step의 최대 token 수로 만든 dummy 입력으로 forward를 한 번 돌려, 실행 중에 잠깐 생기는 activation 메모리의 최고치(그림의 PEAK)를 잰다. CUDA graph는 forward 한 번의 GPU 작업을 기록해 두고 통째로 재생하는 기능이다. 자세한 것은 아래에서 본다. 다음으로 [`profile_cudagraph_memory()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_model_runner.py#L6333)가 CUDA graph가 차지할 메모리를 추정한다. 메모리 예산에서 weight, activation 최고치, CUDA graph 추정치를 뺀 나머지가 KV cache 몫이다. 이 크기로 block 수를 정하고, [`initialize_from_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L377)가 KV cache tensor를 할당한다.

마지막으로 [`compile_or_warm_up_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L379)이 model을 warm up하고 CUDA graph를 capture한다. 추정치로 비워 둔 자리를 실제 graph가 채운다. [CUDA graph](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)는 kernel 실행, 데이터 복사 같은 GPU 작업을 의존 관계로 이어 놓은 것이다. CUDA graph capture는 forward 한 번에 실행되는 작업을 이 graph로 기록해 두는 일이다. vLLM은 batch 크기 몇 개([`cudagraph_capture_sizes`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/compilation.py#L651))를 골라 각각 기록해 두고, 실행할 때는 batch를 가장 가까운 크기로 [padding해](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/cudagraph_dispatcher.py#L71) 그 graph를 통째로 재생한다. 고정 크기 몇 개에 입력을 맞추는 이런 방식을 흔히 bucketing이라고 부른다.

scheduler는 step마다 어떤 request의 token을 몇 개 계산할지 정하는 컴포넌트다. 개념은 바로 아래 [Scheduler 소제목](#scheduler-step마다-계산할-token을-고르는-컴포넌트)에서 설명한다. scheduler 객체는 [`Scheduler(...)`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L174)로 만든다. 앞에서 정한 KV cache 설정을 받아 [`KVCacheManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L328)를 만든다. request에 KV block을 나눠 주려면 전체 block 수를 알아야 하므로, scheduler는 KV cache 다음에 생긴다.

[`EngineCore.__init__()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L118)이 끝나면 [`EngineCoreProc`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1128)은 ZMQ 입출력 thread를 띄운다. 그 다음 [`_perform_handshakes()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1250) context를 빠져나가면서 [READY를 보낸다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1338-L1350). 마지막으로 [`run_busy_loop()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1547)에 들어가 request를 기다린다. 이 loop가 뒤에서 볼 step loop다.

#### `collective_rpc()`: EngineCore가 worker에 일을 시키는 방식

EngineCore는 worker가 몇 개인지, 같은 process에 있는지 신경 쓰지 않는다. executor의 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)에 메서드 이름만 넘기면, executor가 그 메서드를 모든 worker에서 실행하고 결과를 리스트로 모아 돌려준다. 실행 방식은 executor마다 다르다. [`UniProcExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/uniproc_executor.py#L51)는 같은 process에 있는 worker의 메서드를 바로 호출한다. [`MultiprocExecutor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/multiproc_executor.py#L111)는 공유 메모리 기반 [`MessageQueue`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/multiproc_executor.py#L164)로 모든 worker process에 호출을 broadcast하고, worker별 응답 queue에서 결과를 받는다.

5번의 [`determine_available_memory()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_worker.py#L634), [`initialize_from_config()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L377), [`compile_or_warm_up_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L379)이 모두 [이 경로로](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L137-L163) worker에서 실행된다. 그래서 EngineCore 코드에는 `self.model_executor.xxx()`만 보이고, 실제 일은 worker에서 일어난다.

#### Scheduler: step마다 계산할 token을 고르는 컴포넌트

scheduler는 step마다 어떤 request의 token을 몇 개 계산할지 정한다. 기준은 두 가지다. 하나는 한 step에 계산할 수 있는 token 수(token budget)다. [3번](#3-engine-config-cli-인자에서-vllmconfig까지)에서 본 `max_num_batched_tokens`가 이 상한을 [정한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L137-L141). 다른 하나는 KV cache block이다. request가 새 token을 계산하려면 그 token의 KV를 저장할 block이 있어야 한다. [`KVCacheManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L328)는 GPU의 KV block 전체를 관리하는 객체로, request에 block을 [나눠 주고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L778) 끝난 request의 block을 [돌려받는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L620). block이 모자라면 scheduler는 실행 중인 request 하나를 [preempt해](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L795-L802) block을 확보한다.

step마다 실제로 어떻게 고르는지는 [request 처리의 4번](#4-schedule-step마다-계산할-token-배정)에서 다룬다.

#### 설계 결정: KV cache 크기를 profiling으로 정한다

vLLM은 KV cache를 시작할 때 한 번에 할당하고, 이후에는 고정 크기 block 단위로 request에 나눠 준다. 이 block 방식은 PagedAttention 논문에서 왔다. 논문은 request마다 KV cache를 연속 공간으로 미리 잡으면 단편화와 과잉 예약으로 메모리가 낭비된다고 보고, OS의 paging처럼 KV cache를 block으로 나눠 이 낭비를 줄였다([Kwon et al., SOSP 2023](https://arxiv.org/abs/2309.06180)).

block pool을 시작할 때 한 번에 잡으므로, 그 크기를 정하려면 KV cache 말고 다른 것이 쓸 메모리를 먼저 알아야 한다. activation 최고치와 CUDA graph 메모리는 model, attention kernel, batch 크기에 따라 달라서 식으로 미리 계산하기 어렵다. 그래서 vLLM은 dummy 입력으로 실제로 한 번 돌려서 잰다. KV cache 크기를 자동으로 정하는 기능은 초기 [PR #6](https://github.com/vllm-project/vllm/pull/6)에서 들어왔다.

CUDA graph 메모리는 이 방식에서 따로 다뤄야 했다. CUDA graph는 KV cache에 의존하므로 KV cache를 할당한 뒤에 capture한다. 그래서 profiling 때는 그 크기가 빠졌고, KV cache를 너무 크게 잡아 OOM이 나기도 했다. [PR #30515](https://github.com/vllm-project/vllm/pull/30515)는 profiling 중에 작은 dummy KV cache로 CUDA graph를 한 번 capture해 그 크기를 추정하게 했다. 이 PR에서는 기본으로 꺼져 있었지만, v0.32.0에서는 [기본으로 켜져 있다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/envs.py#L2221-L2223)(`VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS`).

### 6. HTTP serving: route 등록과 Uvicorn 실행

다시 [2번](#2-socket-bind-listen-전의-port-선점)의 [`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)로 돌아온다. [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)이 반환되면 [`run_server_worker()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L180)는 [`build_and_serve()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/entry.py#L116)를 호출한다. 이 함수는 먼저 엔진에게 지원하는 task 목록([`SupportedTask`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/tasks.py#L43))과 `model_config`를 받아 온다. task 목록에는 `generate` 같은 생성 task와 `embed` 같은 pooling task가 들어 있다.

[`build_app()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/app.py#L19)은 FastAPI app을 만들고, [`register_api_routers()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/routers.py#L12)로 이 목록에 맞는 route만 등록한다. 예를 들어 `generate`가 있으면 `/v1/chat/completions` 같은 생성 route를 붙인다. [`init_app_state()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/api_server/app_state.py#L24)는 route가 쓸 handler를 `app.state`에 만들어 둔다. chat request를 처리하는 [`OpenAIServingChat`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L118)도 여기서 생긴다. 마지막으로 [`serve_http()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L175)를 호출한다.

[`serve_http()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L175)는 Uvicorn 설정을 만들고, [`server.serve()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L236) coroutine을 event loop에 task로 올린다. event loop가 이 task를 실행하면 Uvicorn이 시작하면서 소켓에 `listen()`을 호출한다. `accept()`는 그 뒤 연결이 들어올 때마다 일어난다. Uvicorn 서버로는 signal handler를 설치하지 않는 [`NoSignalServer`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L45)를 쓴다.

#### 설계 결정: Uvicorn의 signal handler를 끈다

[`NoSignalServer`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/launchers/launcher.py#L45)는 SIGINT와 SIGTERM handler를 설치하지 않는다. vLLM은 종료할 때 HTTP 서버뿐 아니라 엔진도 정리해야 해서, 종료 handler를 event loop에 직접 등록한다. Uvicorn이 자기 handler를 설치하면 이 handler와 경쟁하다가 덮어쓴다. [#49668](https://github.com/vllm-project/vllm/pull/49668)이 이 문제를 고치면서 지금 구조가 되었다.

## request 처리

이 파트는 request 하나가 들어와서 응답이 나갈 때까지를 따라간다. 기준은 앞과 같다. text 생성 model, API server 하나, EngineCore 하나, GPU 하나에 `/v1/chat/completions` request를 보내는 경우다. 다른 API나 multimodal 입력, streaming 입력처럼 이 가정에서 벗어나는 경로는 필요한 곳에서 따로 설명한다. 서버 초기화가 상자를 만드는 순서였다면, 여기서는 그 상자 사이의 화살표를 따라간다.

### 1. HTTP POST: FastAPI router의 request 수신

1번은 HTTP request가 vLLM 코드에 처음 들어오는 단계다. router는 request 형식을 검증하고 handler에 넘길 뿐, model을 직접 실행하지 않는다. 예를 들어 client가 다음 request를 보낸다고 하자.

```console
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"<model>","messages":[{"role":"user","content":"hi"}]}'
```

이 request는 [`create_chat_completion()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/api_router.py#L41-L80) route로 들어온다. FastAPI가 이 함수를 호출하기 전에 JSON body를 [`ChatCompletionRequest`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/protocol.py#L220)로 검증한다. 함수는 [서버 초기화 6번](#6-http-serving-route-등록과-uvicorn-실행)에서 `app.state`에 만들어 둔 [`OpenAIServingChat`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L118)을 꺼내, 그 [`create_chat_completion()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L281)을 호출한다.

chat completions만 있는 것은 아니다. model이 `generate` task를 지원하면, [서버 초기화 6번](#6-http-serving-route-등록과-uvicorn-실행)의 [`register_generate_api_routers()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/generate/api_router.py#L21)가 다른 생성 API의 route도 함께 등록한다. 모두 같은 방식으로 동작한다. FastAPI가 JSON body를 API마다 정의된 Pydantic model로 검증하고, route는 검증된 request를 그 API의 handler에 넘긴다.

handler는 API마다 다르지만, 결국 모두 [2번](#2-tokenize-chat-request를-model-입력으로)부터의 경로를 탄다. 입력을 token ID로 바꾸고 `AsyncLLM`의 [`generate()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L698)를 호출한다. 이 글은 chat completions를 예로 따라간다.

handler가 돌려준 값에 따라 응답 형식이 갈린다. [`ErrorResponse`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/serve/engine/protocol.py#L86)면 오류 JSON을, [`ChatCompletionResponse`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/protocol.py#L134)면 완성된 JSON을 보낸다. 그 밖의 경우는 streaming이므로 `StreamingResponse`로 감싸 `text/event-stream`(SSE)으로 보낸다. route에 붙은 [`with_cancellation`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/serve/utils/api_utils.py#L51) decorator는 client 연결이 끊기면 handler task를 취소한다. 이 취소가 [7번](#7-free-blocks-request-종료와-kv-block-정리)의 정리로 이어진다.

#### SSE: 응답을 조금씩 보내는 방식

SSE(Server-Sent Events)는 HTTP 응답 하나를 열어 둔 채, server가 event를 하나씩 이어서 보내는 방식이다. 표준은 [HTML Living Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html)에 있다. 응답의 `Content-Type`은 `text/event-stream`이고, event 하나는 `data: ...` 줄과 빈 줄 하나로 끝난다.

```text
data: {"choices":[{"delta":{"content":"Hel"}}]}

data: {"choices":[{"delta":{"content":"lo"}}]}

data: [DONE]
```

LLM 서버가 SSE를 쓰는 이유는 token이 step마다 하나씩 나오기 때문이다. 응답을 다 만들 때까지 기다리지 않고, 만든 부분부터 client에 보낼 수 있다. 통신은 server에서 client로 한 방향뿐이다. WebSocket처럼 양방향 연결이 필요 없어서, 평범한 HTTP 위에서 그대로 동작한다. 마지막 `data: [DONE]`은 SSE 표준이 아니라 OpenAI API가 정한 종료 표시이고, vLLM도 이를 따른다.

vLLM에서는 route가 handler의 async generator를 Starlette의 [`StreamingResponse`](https://starlette.dev/responses/#streamingresponse)로 [감싼다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/api_router.py#L77-L80). generator가 `data: ...` 문자열을 하나 yield할 때마다 Starlette가 그것을 HTTP chunk로 보낸다. 이 문자열을 만드는 쪽은 [6번](#6-detokenize-token-id에서-응답까지)의 `chat_completion_stream_generator()`다. 그 사이에는 [`with_sse_keep_alive()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/serve/utils/sse_keep_alive.py#L21)가 끼어 있다. 이 함수는 keep-alive 간격이 설정되어 있으면, 그 시간 동안 새 chunk가 없을 때 연결 유지용 SSE comment를 보낸다. 간격이 0 이하면 아무것도 하지 않는다.

### 2. Tokenize: chat request를 model 입력으로

2번은 chat 형식의 request를 엔진에 넘길 형태로 바꾸는 단계다. 하는 일은 세 가지다. messages를 token ID로 바꾸고, 생성할 token 수의 한도를 정하고, sampling parameter를 만든다. 이 일은 모두 API server process에서 일어나고, EngineCore는 이미 token화된 입력만 받는다.

[`OpenAIServingChat`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L118)의 [`_create_chat_completion()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L296-L415)이 실제 일을 한다. 먼저 [`render_chat_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L258-L279)가 model 이름을 확인하고, renderer의 [`render_chat()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/renderers/online_renderer.py#L224-L317)을 호출한다. 여기서 messages, system prompt, tools를 model의 chat template에 넣어 prompt 문자열을 만들고, tokenizer로 token ID로 바꾼다. 결과가 [`EngineInput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/inputs/engine.py#L266)이다. [서버 초기화 4번](#4-engine-client-asyncllm-생성과-enginecore-연결)에서 본 renderer가 바로 이 일을 한다.

생성 한도는 [`get_max_tokens()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/serve/utils/api_utils.py#L169-L205)가 정한다. 규칙의 핵심은 하나다. prompt와 생성 token을 합친 길이는 `max_model_len`을 넘을 수 없다. 그래서 prompt를 넣고 남은 공간이 상한이 되고, request나 서버 설정이 그보다 작은 값을 주면 그 값이 한도가 된다. 각 값의 정의와 관계는 2번 끝의 [생성 한도를 정하는 값들](#생성-한도를-정하는-값들)에서 자세히 다룬다.

  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/03-2-max-tokens-dark.svg"

sampling parameter는 [`to_sampling_params()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/protocol.py#L715)가 만든다. 이 함수는 temperature, top-p, stop 같은 request 필드로 [`SamplingParams`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/sampling_params.py#L268)를 만든다. 마지막으로 [`engine_client.generate()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L698)를 호출한다. 이 서버에서 `engine_client`는 [서버 초기화 4번](#4-engine-client-asyncllm-생성과-enginecore-연결)에서 만든 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)이다.

#### 생성 한도를 정하는 값들

`max_tokens`는 request가 원하는 값과 서버의 강제 상한 중 작은 값이다. 어느 값도 prompt를 넣고 남은 공간(`model_max_tokens`)을 넘지 못한다. 아래 값은 모두 token 단위다.

- context length: model이 한 번에 다룰 수 있는 최대 token 수다. model의 HF `config.json`에 적혀 있다.
- `max_model_len`: 이 서버가 허용하는 sequence 길이의 상한이다. sequence는 prompt와 생성 token을 합친 것이다.
- `input_length`: prompt 길이(prompt_len). chat template을 적용해 token화한 prompt의 token 수다.
- `model_max_tokens`: prompt를 넣고 남은 공간, 즉 `max_model_len - input_length`다.
- `fallback_max_tokens`: request가 요청한 한도다. `max_completion_tokens`, 없으면 `max_tokens`, 그것도 없으면 model의 기본 sampling 설정 값을 쓴다.
- `override_max_tokens`: 서버 운영자가 `--override-generation-config`의 `max_new_tokens`로 건 강제 상한이다.
- `platform_max_tokens`: 외부 플랫폼 plugin을 위한 상한이다. CUDA를 포함한 기본 플랫폼에서는 [제한이 없다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/platforms/interface.py#L224-L225).

먼저 `max_model_len`이 정해진다. `max_model_len`은 context length를 넘지 못한다. 사용자가 `--max-model-len`을 주면 그 값을, 주지 않으면 context length를 쓰고, context length보다 큰 값을 주면 기본적으로 [오류가 난다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/model.py#L2639-L2664).

$$
\text{max\_model\_len} = \min\big(\texttt{--max-model-len},\ \text{context length}\big)
$$

context length는 model마다 키 이름이 달라서, vLLM은 `max_position_embeddings`, `n_positions`, `max_seq_len`, `seq_length` 같은 후보 키 중 config에 있는 값의 [최솟값을 쓴다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/transformers_utils/model_arch_config_convertor.py#L394-L427). Llama나 Qwen 같은 대부분의 model은 `max_position_embeddings`다. tokenizer config에 `model_max_length`가 있으면 그 값으로 더 줄어들 수 있다.

그 다음 `max_tokens`가 정해진다. 기본 형태는 아래 식처럼 네 값 중 가장 작은 값이다.

$$
\begin{aligned}
\text{model\_max\_tokens} &= \text{max\_model\_len} - \text{input\_length} \\
\text{max\_tokens} &= \min\big(\text{model\_max\_tokens},\ \text{fallback\_max\_tokens},\ \text{override\_max\_tokens},\ \text{platform\_max\_tokens}\big)
\end{aligned}
$$

값이 없는(`None`) 항은 `min`에서 빠진다. 그래서 request가 한도를 주지 않으면 `model_max_tokens`가 그대로 한도가 되고, request가 큰 값을 줘도 context 길이를 넘지는 못한다. 다만 서버 쪽 값은 설정에 따라 상한이 아니라 기본값으로만 쓰인다. 아래에서 그 규칙을 본다.

`max_new_tokens`는 `max_tokens`와 같은 값의 다른 이름이다. Hugging Face의 `generation_config.json`과 `--override-generation-config`는 이 값을 `max_new_tokens`라고 적고, vLLM은 읽을 때 `max_tokens`로 [매핑한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/model.py#L1883-L1888). 아래에서 HF는 `generation_config.json`의 `max_new_tokens`를, override는 `--override-generation-config`의 `max_new_tokens`를 뜻한다.

HF 파일을 어디서 읽는지는 `--generation-config` 값이 [정한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/model.py#L1824-L1837). `auto`(기본값)면 `--model`로 준 곳에서 읽는다. `--model`은 HF Hub repo id일 수도, local 폴더일 수도 있다. 폴더 경로를 주면 그 폴더에서 읽고, `vllm`이면 읽지 않는다.

이 값들은 두 가지 역할 중 하나를 맡는다. 차이는 request가 값을 줬을 때 드러난다.

- 기본값: request가 값을 주지 않았을 때만 그 자리를 채운다. request가 값을 주면 그 값이 더 커도 request 값을 쓴다.
- 강제 상한: request가 무엇을 주든 그 값을 위에서 자른다. `min`에 항상 들어간다.

`get_max_tokens()`는 세 단계로 `max_tokens`를 정한다.

1. 원하는 값(requested)을 고른다. request의 `max_completion_tokens`, `max_tokens`, 서버 기본값 순서로 보고 처음 있는 값을 쓴다. 서버 기본값은 override가 있으면 override, 없으면 HF다.
2. 강제 상한(cap)을 고른다. `--generation-config`가 폴더 경로면 서버 기본값이, 아니면 override가 [상한이 된다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L175-L181). 둘 다 없으면 상한도 없다.
3. `model_max_tokens`, requested, cap 중 가장 작은 값을 고른다. 값이 없는 항은 빠진다.

<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/03-2-max-tokens-flow-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/03-2-max-tokens-flow-dark.svg"
  caption="get_max_tokens()가 max_tokens를 정하는 순서."

그림의 "override > HF"는 둘 다 있으면 override를 쓴다는 뜻이다.

예를 들어 `model_max_tokens`가 4000이고, model의 `generation_config.json`에 `max_new_tokens: 512`가 있다고 하자. 아래 표에서 열은 서버를 띄운 설정이고(`<dir>`은 `generation_config.json`이 있는 폴더 경로), 행은 client가 보낸 request 하나다. 칸의 값은 그 request에 실제로 적용되는 `max_tokens`다. 셋째 열은 `auto`에 `--override-generation-config '{"max_new_tokens": 1000}'`을 더한 설정이다.

| client request의 `max_tokens` | `--generation-config auto` | `--generation-config <dir>` | `auto` + override 1000 |
| --- | --- | --- | --- |
| 없음 | 512 | 512 | 1000 |
| 100 | 100 | 100 | 100 |
| 2000 | 2000 | 512 | 1000 |

`auto`에서 512는 기본값이라 request의 2000을 막지 않는다. 폴더 경로에서는 512가 강제 상한이라 2000이 512로 잘린다. override를 주면 1000이 강제 상한이 되고, 파일 값 위에 덮어써지므로 기본값 자리도 1000이 차지한다. `vllm`이면 파일을 읽지 않으므로 override만 적용된다.

헷갈리기 쉬운 점을 정리하면 아래와 같다.

- `input_length`는 prompt 길이(prompt_len)다. 이름에 input이 들어가지만 생성 token은 포함하지 않는다.
- `max_model_len`은 context length와 같은 값이 아니다. 둘 중 작은 값이고, 대개 사용자가 `--max-model-len`으로 줄인 값이다.
- `max_new_tokens`와 `max_tokens`는 같은 값이다. HF와 `--override-generation-config`는 앞의 이름을, vLLM 내부와 OpenAI API는 뒤의 이름을 쓴다.
- HF 파일은 local 경로를 뜻하지 않는다. `auto`면 `--model`이 가리키는 곳(HF Hub 또는 local)의 파일이다.
- `auto`에서 HF 값은 기본값일 뿐이다. request가 더 큰 값을 주면 막지 않는다.
- override는 강제 상한이면서 기본값 자리도 덮어쓴다. 그래서 request가 비어 있으면 HF 값이 아니라 override 값이 쓰인다.

### 3. ZMQ ADD: `AsyncLLM`에서 EngineCore로

3번은 request를 엔진에 등록하고, 결과를 받을 자리를 마련하는 단계다. 등록은 API server와 EngineCore 양쪽에서 일어난다.

[`AsyncLLM.generate()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L698-L809)는 먼저 [`add_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L388)를 호출한다. 여기서 [`InputProcessor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L161)가 [`EngineInput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/inputs/engine.py#L266)과 [`SamplingParams`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/sampling_params.py#L268)를 검증하고 [`EngineCoreRequest`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/__init__.py#L109)로 묶는다. 그 다음 두 줄이 순서대로 실행된다.

```python
self.output_processor.add_request(request, prompt, parent_req, index, queue)
await self.engine_core.add_request_async(request)
```

[첫 줄](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L572)은 API server 쪽에 이 request의 detokenizer, logprob 처리기, 결과 queue를 등록한다. [둘째 줄](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L575)은 EngineCore에 ADD message를 보낸다. 결과 queue를 먼저 만들어 두므로, 엔진 출력이 아무리 빨리 와도 받을 자리가 이미 있다. `generate()`는 이후 이 queue([`RequestOutputCollector`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/output_processor.py#L53))를 async generator로 읽으며 결과를 기다린다.

ADD message는 [서버 초기화 4번](#4-engine-client-asyncllm-생성과-enginecore-연결)에서 bind한 ROUTER 소켓으로 간다. [`AsyncMPClient.add_request_async()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core_client.py#L1296)가 request를 msgspec으로 직렬화해 ZMQ로 보낸다. EngineCore 쪽에서는 입력 thread가 이 message를 받아 [`preprocess_add_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1089)로 [`Request`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L60) 객체로 바꾼다. busy loop는 이 객체를 [`_handle_client_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1674)로 넘기고, [`add_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L508)가 scheduler의 waiting queue에 넣는다.

ADD를 보내기 전에 `add_request()`는 [`check_admission()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L316-L374)으로 admission을 검사한다. 끝나지 않은 request 수가 `--max-num-queued-reqs`를, prefill 중인 prompt token 합이 `--max-num-queued-tokens`를 넘으면 request를 거절하고 HTTP 503으로 응답한다. 503은 load balancer나 client SDK가 다른 instance로 retry하게 하려는 선택이다. 다만 두 값의 [기본값은 `None`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/scheduler.py#L92-L105)이라, 설정하지 않으면 API server는 request를 거절하지 않는다. ZMQ도 막지 않는다. vLLM은 ZMQ 소켓의 [high-water mark를 0](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/utils/network_utils.py#L372-L376)(무제한)으로 두므로, ZMQ는 메시지를 버리거나 막지 않는다. 그래서 기본 설정에서 몰린 request는 EngineCore의 입력 queue를 거쳐 scheduler의 waiting queue에 쌓이고, 그만큼 TTFT가 늘어난다. 이 waiting queue를 어떻게 비우는지는 [4번](#4-schedule-step마다-계산할-token-배정)에서 본다.

입력 자체가 stream으로 들어오는 경우는 경로가 조금 다르다. 실시간 음성 인식 API는 오디오 조각이 도착할 때마다 [`StreamingInput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/speech_to_text/realtime/serving.py#L59-L89)을 yield한다. `add_request()`는 이런 입력을 [`_add_streaming_input_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L580-L673)로 넘긴다. 이 함수는 결과 queue를 먼저 만들어 바로 반환하고, 입력을 읽는 task를 따로 띄운다. 그 task가 입력 조각마다 request를 만들어 같은 queue로 EngineCore에 이어 붙인다. admission은 첫 조각을 보낼 때 한 번만 검사한다. 거절되면 그 오류가 queue를 통해 `generate()`로 전달된다. SSE는 출력을 조금씩 보내는 방식이라 이 경로와 관계가 없다. chat completions는 `stream: true`여도 위의 일반 경로를 탄다.

### 4. Schedule: step마다 계산할 token 배정

4번은 scheduler가 이번 step에 어떤 request의 token을 몇 개 계산할지 정하는 단계다. 기준은 [서버 초기화 5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)의 Scheduler 소제목에서 본 두 가지, token budget과 KV block 여유다. 앞의 step timeline 그림이 보여 준 "step마다 여러 request가 함께 진행된다"는 동작이 여기서 만들어진다.

EngineCore는 이 일을 queue 몇 개로 처리한다. [`run_busy_loop()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1547-L1556)는 step마다 두 가지를 반복한다. 먼저 [`_process_input_queue()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1573-L1602)가 input thread가 채운 [`input_queue`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1147)를 비워, 새 request를 scheduler의 `waiting` queue에 넣는다. 그 다음 `step_fn`이 schedule, forward, 결과 처리를 한 번 실행한다. 결과는 [`output_queue`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1148)로 가고, output thread가 이를 API server로 보낸다.

[`Scheduler.schedule()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L591)은 두 queue를 정해진 순서로 본다.

1. `running`부터 본다. 이미 실행 중인 request마다 이번 step에 계산할 token 수를 정한다. prompt를 다 계산한 request는 보통 1개(decode), prompt가 남은 request는 남은 만큼이나 budget이 허락하는 만큼(chunked prefill)이다. 그만큼의 KV block을 `allocate_slots()`로 받고, token budget에서 뺀다.
2. 그 다음 `waiting`을 앞에서부터 본다. 이번 step에 preempt가 없었고 budget이 남았을 때만 본다. 새 request는 먼저 [`get_computed_blocks()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L264)로 prefix cache에서 이미 계산된 block을 찾고, 나머지 token에 필요한 block을 `allocate_slots()`로 받는다. block을 받으면 `waiting`에서 꺼내 `running`에 넣는다. `running`의 request 수가 `max_num_seqs`에 닿으면 멈춘다.

running을 먼저 보는 이유는 이미 시작한 request를 끝까지 진행시키기 위해서다. 새 request는 남은 budget과 block 안에서만 들어온다.

배정 결과가 [`SchedulerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L232)이다. 여기에는 request별 계산할 token 수, 새로 받은 KV block, encoder 작업, structured output 정보가 들어 있다. 결국 한 step의 batch는 `{request_id: num_tokens}` 하나로 표현되고, 여기에 prefill 조각과 decode token이 섞여 들어간다.

여러 request의 token을 padding 없이 한 forward로 묶는 방법은 뒤의 [prefill과 decode를 한 step에 섞는 continuous batching](#12-scheduler-출력-prefill과-decode를-한-step에-섞는다)에서 다룬다.

#### KVCacheManager: block을 나눠 주고 돌려받는 방식

[`KVCacheManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L328)는 [서버 초기화 5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)에서 할당한 KV cache를 고정 크기 block 단위로 관리한다. block 하나는 기본 [16 token](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/cache.py#L72)의 KV를 담는다. 일반 attention layer에서 block 하나의 byte 크기는 `2(K, V) * block_size * num_kv_heads * head_size * dtype 크기`다.

KVCacheManager는 빈 block queue에서 block을 꺼내 request에 나눠 주고, 끝난 request의 block을 다시 queue에 넣는다. hash가 있는 block은 queue에 있는 동안 prefix cache로 다시 쓸 수 있다. 빈 block은 [`BlockPool`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L136)의 [`free_block_queue`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L178)에 있다. 아래 그림은 block이 이 queue를 오가는 네 경로이고, 각 경로는 그림 뒤에서 차례로 설명한다.

[`allocate_slots()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L371)는 세 단계로 block을 나눠 준다.

1. 필요한 block 수를 계산한다. 새 token이 17개면 `ceil(17 / 16) = 2`개다.
2. `free_block_queue`에 block이 충분한지 확인한다. 모자라면 실패를 돌려준다.
3. queue 앞에서 block을 꺼내 request에 붙이고, request별 block 목록(`req_to_blocks`)에 기록한다.

실패하면 scheduler가 처리한다. running request라면 우선순위가 가장 낮은 running request를 [preempt](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L795-L802)한다. FCFS에서는 `running`의 마지막 request다. preempt된 request는 block을 모두 돌려주고, 계산한 token 수를 0으로 되돌린 채 [`waiting` 맨 앞](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L1612-L1613)으로 간다. 다시 들어오면 prompt부터 다시 계산한다(recompute). waiting request라면 이번 step에는 더 들이지 않는다.

request가 끝나거나 preempt되면 block은 `free_block_queue`로 [돌아간다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L774-L804). 돌아가는 자리는 block에 hash가 있는지에 따라 다르다. hash가 없는 block은 queue 앞에 넣어 가장 먼저 재사용한다. 코드 주석은 그 이유를 GPU locality라고 적는다. hash가 있는 block, 즉 prefix cache로 다시 쓸 수 있는 block은 queue 뒤에 넣는다. 새 block은 앞에서부터 꺼내므로, cache된 block은 가장 오래 쓰지 않은 것부터 덮어써진다(LRU).

prefix caching은 이 구조 위에서 동작한다. scheduler는 prompt를 16 token씩 잘라 block마다 hash를 계산한다. hash에는 앞 block의 hash가 들어가므로, 같은 hash는 "처음부터 그 block까지 token이 모두 같다"는 뜻이다. [`cached_block_hash_to_block`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L181)은 이 hash에서 block으로 가는 표다. 새 request가 오면 `get_computed_blocks()`가 이 표에서 가장 긴 일치를 찾는다. 찾은 block이 다른 request에서 쓰는 중이면 참조 수([`ref_cnt`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L182))만 올린다. 이미 반납되어 `free_block_queue`에 있으면 queue 중간에서 빼내 다시 쓴다. 그래서 queue는 중간의 block을 O(1)에 빼낼 수 있어야 하고, vLLM은 Python `deque` 대신 [이중 연결 리스트](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L246-L262)를 직접 만들어 쓴다. 꽉 차지 않은 마지막 block은 hash가 없으므로 공유되지 않는다.

#### 설계 결정: prefill과 decode를 나누지 않는다

V1 scheduler에는 prefill phase와 decode phase가 따로 없다. [코드 주석](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L594)도 "There's no 'decoding phase' nor 'prefill phase' in the scheduler"라고 적어 둔다. prompt token과 생성된 token을 똑같이 "아직 계산하지 않은 token"으로 보고, 결정은 `{request_id: num_tokens}` 같은 dictionary 하나로 표현한다. V1 소개 글은 이 표현이 chunked prefill, prefix caching, speculative decoding까지 담을 만큼 일반적이라고 설명한다([vLLM V1 소개 글](https://blog.vllm.ai/2025/01/27/v1-alpha-release.html)). 앞의 step timeline 그림에서 prefill과 decode가 한 step에 섞이는 것도 이 덕분이다. V1을 다시 설계하며 정리한 [#8779](https://github.com/vllm-project/vllm/issues/8779)는 그 배경으로 "scheduling is not cheap"을 든다. 이전 scheduler는 step마다 `running` 전체를 Python으로 훑었고, 그 CPU 시간이 GPU를 놀게 했다. 표현을 하나로 줄인 것은 이 비용을 줄이는 방향과 맞닿아 있다.


#### 설계 결정: free block queue는 직접 만든 이중 연결 리스트다

`free_block_queue`는 Python `deque` 대신 vLLM이 직접 만든 이중 연결 리스트다. 이 구조는 V1에 prefix caching을 넣은 [#9972](https://github.com/vllm-project/vllm/pull/9972)에서 들어왔다. PR은 `deque`보다 나은 점을 두 가지로 든다. 중간의 block을 O(1)에 뺄 수 있고, 새 Python 객체를 만들지 않고 block 객체의 포인터만 바꾼다. 앞의 prefix caching에서 반납된 block을 queue 중간에서 다시 꺼내는 일이 바로 첫째 이유다. 같은 PR의 benchmark는 prefix cache 적중률 49%인 offline batch에서 입력 처리량이 약 1.8배(17,916에서 32,258 tok/s)로 늘었다고 보고한다.

#### 설계 결정: prefix caching은 기본으로 켠다

V1은 prefix caching을 처음부터 기본 기능으로 설계했다. [#8779](https://github.com/vllm-project/vllm/issues/8779)는 V1의 방향 중 하나로 "Prefix-caching as a first-class feature"를 들고, 그 overhead를 줄이는 것을 목표로 삼았다. v0.32.0에서도 model이 지원하면 prefix caching이 [기본으로 켜진다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L3021-L3027). 같은 system prompt나 대화 기록을 공유하는 request가 많을수록 prefill에서 아끼는 계산이 커진다.

### 5. Forward: GPU forward와 sampling

5번은 worker가 [`SchedulerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L232)대로 GPU에서 forward를 한 번 돌리고, request마다 다음 token을 sampling하는 단계다.

EngineCore의 busy loop는 step마다 [`step_fn`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L242-L246)을 호출한다. 가장 단순한 [`step()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L657-L687)은 아래 순서로 한 step을 처리한다.

```python
scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
future = self.model_executor.execute_model(scheduler_output, non_block=True)
grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
model_output = future.result()
if model_output is None:
    model_output = self.model_executor.sample_tokens(grammar_output)
engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)
```

executor는 [서버 초기화 5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)에서 본 [`collective_rpc()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/executor/abstract.py#L199)로 worker의 model runner를 호출한다. model runner의 [`execute_model()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1719-L2087)은 forward를 네 단계로 처리한다.

1. request 상태를 갱신한다. [`finish_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1733), [`add_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1181), [`update_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1236)가 끝난 request를 빼고, 새 request를 넣고, 새로 받은 KV block을 block table에 더한다. worker는 request 상태를 step 사이에 계속 들고 있으므로, scheduler는 매 step 바뀐 부분만 보낸다.
2. 입력을 준비한다. [`prepare_inputs()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1812)가 `input_ids`, `positions`, `query_start_loc`, `seq_lens`를 만들고, [`prepare_attn()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1815)이 block table과 [`slot_mapping`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/block_table.py#L341-L348)을 만든다. 이 값으로 attention metadata를 조립한다.
3. forward를 실행한다. CUDA graph 모드와 batch 크기에 따라 [full graph를 재생하거나](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L2006), piecewise graph를 쓰거나, [model을 직접 호출한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L2044).
4. 결과를 저장하고 `None`을 반환한다. hidden state는 [`ExecuteModelState`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L2403)에 넣어 두고, sampling은 다음 호출에서 한다.

forward에 들어가는 입력은 세 가지다.

- `input_ids`: 이번 step에 계산할 token ID를 request 순서대로 이어 붙인 1차원 배열이다. request마다 행을 나누지 않으므로 request 사이에 padding이 없다.
- `positions`: `input_ids`의 각 token이 자기 request 안에서 몇 번째 token인지 담은 배열이다. 길이는 `input_ids`와 같고, RoPE 같은 position encoding이 이 값을 쓴다.
- attention metadata: 한 줄로 이어 붙인 배열을 attention layer가 request별로 나눠 계산하는 데 필요한 batch 구조 정보다.

attention metadata에는 네 가지 값이 들어 있다.

- `query_start_loc`: `input_ids`에서 각 request의 token이 시작하는 위치다. 어디서 어디까지가 같은 request인지 알려 준다.
- `seq_lens`: request마다 KV cache에 있는 token까지 합친 전체 길이다.
- block table: request마다 이전 KV가 들어 있는 block ID 목록이다.
- `slot_mapping`: 이번 step에 만든 새 KV를 KV cache의 어느 칸에 쓸지 token마다 담은 배열이다.

v0.32.0에서는 [`CommonAttentionMetadata`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/attention/backend.py#L387)가 이 값을 담고, attention backend마다 [builder](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/attention/backend.py#L683)가 자기 kernel에 맞는 형태로 바꾼다.

attention metadata는 model의 `forward()` 인자로 넘기지 않는다. model runner가 [`set_forward_context()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L2015)로 전역 context에 올려 두면, 각 attention layer가 [`get_forward_context()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/layers/attention/attention.py#L704)로 꺼내 쓴다. 그래서 model 코드는 `forward(input_ids, positions)` 형태를 그대로 유지할 수 있다. 각 배열의 실제 값은 뒤의 [step 안의 token packing](#13-step-안의-token-packing)과 [block table](#14-block-table-token-위치에서-kv-cache-주소로)에서 예시로 본다.

sampling은 [`sample_tokens()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L2088-L2175)가 따로 한다. 먼저 hidden state 중 [`logits_indices`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L968)가 가리키는 위치만 고른다. request마다 이번 step의 마지막 token 위치다. 고른 hidden state로 [`compute_logits()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1615)가 vocabulary 크기의 logits를 만들고, [`sample()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1592-L1660)이 penalty, `logit_bias`, temperature, top-k, top-p, min-p를 적용한 뒤 request마다 token을 sampling한다. MRV2는 이 sampler를 [Triton kernel](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/sample)로 다시 구현했다. 결과가 [`ModelRunnerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/outputs.py#L267)이다.

#### structured output: grammar bitmask로 출력 형식을 강제하는 방식

structured output은 sampling 직전에 형식에 맞지 않는 token을 지우는 방식으로 동작한다. model은 형식을 모른 채 평소처럼 logits를 만들고, 형식은 sampler가 지킨다. 기준이 되는 것은 grammar다. grammar는 지금까지 나온 token 다음에 어떤 token이 올 수 있는지 알려 주는 상태 기계(state machine)다. 예를 들어 schema가 `age`를 정수로 정했다면, `{"age": ` 다음에는 숫자 token만 올 수 있다.

- grammar compile: request가 JSON schema나 정규식 같은 형식을 주면, EngineCore의 [`StructuredOutputManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/structured_output/__init__.py#L47)가 backend로 grammar를 [compile한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/structured_output/__init__.py#L126). backend는 기본값 `auto`에서 xgrammar, guidance, outlines, lm-format-enforcer 중 하나를 [고른다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/structured_outputs.py#L12-L20). compile은 thread pool에서 돌고, 그동안 request는 [`WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L374) 상태로 기다린다.
- bitmask 생성: step마다 [`get_grammar_bitmask()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L1995)가 request마다 grammar의 현재 상태에서 허용되는 token을 bit로 표시한다. vocabulary의 token 32개를 int32 하나에 담으므로, request 하나의 bitmask는 [`(vocab_size + 31) // 32`개의 int32](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/warmup.py#L373-L376)다. 형식이 없는 request의 bitmask는 [모든 bit를 켠다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/structured_output/__init__.py#L217-L224).
- logits masking: `sample_tokens()`가 logits를 만든 직후 [`apply_grammar_bitmask()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1621-L1625)를 호출한다. kernel이 bit가 꺼진 token의 logits를 [`-inf`로 바꾸므로](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/structured_outputs.py#L189-L198), temperature나 top-p 값과 상관없이 그 token은 sampling 결과로 나올 수 없다.
- grammar 상태 갱신: sampling이 끝나면 [`update_from_output()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2026)이 [`accept_tokens()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2186)로 새 token을 grammar에 넣어 상태를 다음으로 넘긴다.

forward와 sampling을 두 번의 호출로 나눈 이유가 이 bitmask다. bitmask는 CPU에서 계산한다. 위의 `step()`을 보면 `execute_model(non_block=True)`로 forward를 시작한 뒤, GPU가 도는 동안 CPU가 `get_grammar_bitmask()`를 계산하고, 그 결과를 `sample_tokens()`에 넘긴다. 호출을 나눠야 bitmask 계산이 forward와 겹친다.

#### 설계 결정: async scheduling으로 scheduling과 실행을 겹친다

async scheduling은 step N의 결과를 기다리지 않고 step N+1을 미리 짠다. 아직 모르는 다음 token 자리는 placeholder로 잡아 둔다. 왜 이것이 필요한지부터 보자.

async scheduling이 꺼져 있으면 EngineCore는 `step()`으로 schedule, forward, 결과 처리를 차례로 한다. GPU가 step N을 마치면 CPU가 결과를 받아 상태를 갱신하고 step N+1을 짜는데, 그동안 GPU는 다음 일을 받지 못하고 기다린다. 순서대로 할 수밖에 없었던 이유는 step N+1을 짜려면 step N에서 sampling한 token을 알아야 하기 때문이다.

v0.32.0은 조건이 맞으면 [async scheduling을 자동으로 켠다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L1585). 이때 EngineCore는 [`step()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L657-L687) 대신 [`step_with_batch_queue()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L698)를 쓴다. 새 batch의 실행을 먼저 시작하고, 그 실행이 GPU에서 도는 동안 다음 step을 schedule한다. 앞선 batch의 결과는 queue가 차거나 더 넣을 수 없을 때 받는다. 동시에 진행하는 batch 수는 [`max_concurrent_batches`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L577)가 정한다.

이 구조는 [#19970](https://github.com/vllm-project/vllm/pull/19970)에서 들어왔다. 목표는 scheduler를 실행보다 한 step 앞서 돌게 해서, scheduling에 드는 CPU 시간을 GPU 실행 뒤에 숨기는 것이다. PR은 이 방식이 [NanoFlow](https://arxiv.org/abs/2408.12757) 논문의 접근과 비슷하다고 밝힌다. 처음에는 `--async-scheduling`으로 켜는 실험 기능이었다. [`AsyncScheduler`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/async_scheduler.py)는 이 의존성을 placeholder로 푼다. step N의 결과를 기다리지 않고 request마다 다음 token이 하나 나온다고 가정해 [`num_output_placeholders`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L162)를 올려 두고 step N+1을 짠다. 실제 token ID는 GPU에 남아 있는 step N의 sampling 결과를 worker가 바로 이어 붙이고, 결과가 CPU에 도착하면 placeholder를 실제 token으로 바꾼다. EOS로 끝난 request처럼 가정이 틀린 경우에는 미리 계산한 결과를 버린다. 이 기능은 v0.14.0부터 기본으로 켜졌다.

#### 설계 결정: Model Runner V2를 처음부터 다시 만들었다

위에서 본 `execute_model()`과 `sample_tokens()`는 Model Runner V2(MRV2)의 코드다. MRV2는 v0.12.0에서 실험 기능으로 들어와 v0.29.0부터 모든 model의 기본 실행 경로가 되었다([PR #25266](https://github.com/vllm-project/vllm/pull/25266)). [설계 문서](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/design/model_runner_v2.md)는 V1 model runner를 다시 만든 이유로 "fundamental design mistakes"와 쌓인 기술 부채를 든다. 이 글의 흐름과 닿는 변경은 세 가지다.

- persistent batch와 입력의 분리: 연속된 step의 batch는 거의 같으므로, V1부터 request 상태를 step 사이에 계속 들고 있었다(persistent batch). V1은 이 상태 tensor를 그대로 model 입력으로 써서, request가 들고 날 때마다 tensor 전체를 다시 정렬해야 했다. MRV2는 request마다 고정된 행을 주고, step마다 필요한 행을 GPU에서 모아 입력을 만든다. 위 1단계의 `add_requests()`와 `finish_requests()`가 이 행을 관리한다.
- async-first: V1은 async scheduling을 나중에 덧붙였다. MRV2는 실행 loop를 CPU 동기화가 없는 CUDA stream으로 가정하고 처음부터 설계했다.
- GPU에서 입력 준비: `input_ids`, `positions`, `query_start_loc`, `seq_lens`를 Python이 아니라 Triton kernel로 만든다. CPU 부담이 줄고, async scheduling에서 CPU가 아직 모르는 값(예: 직전 step의 token)을 GPU가 바로 쓸 수 있다.

설계 문서는 MRV2가 아직 기능이 완전하지 않고 열린 설계 결정도 남아 있다고 적는다. 그래서 Triton이 없거나 MRV2가 아직 지원하지 않는 기능을 쓰면 [V1 runner로 돌아간다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L703-L738).

### 6. Detokenize: token ID에서 응답까지

6번은 sampling한 token ID를 request별 출력으로 되돌리고, text로 바꿔 client에 보내는 단계다. 이 일은 EngineCore와 API server에 나뉘어 있다.

EngineCore에서는 [`Scheduler.update_from_output()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2026)이 [`ModelRunnerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/outputs.py#L267)의 token ID와 logprob을 request별로 나누고, request 상태를 갱신한다. EOS token이나 `max_tokens`에 닿은 request는 여기서 끝난다. 결과는 client별 [`EngineCoreOutputs`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/__init__.py#L259)로 묶이고, [`_process_engine_step()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L1603)이 이를 output queue에 넣는다. output thread가 queue에서 꺼내 PULL 소켓으로 보낸다.

API server에서는 [`AsyncLLM`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L84)의 background loop인 [`output_handler()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L845)가 이 출력을 받아 [`OutputProcessor.process_outputs()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/output_processor.py#L681)에 넘긴다. 여기서 request별 [`IncrementalDetokenizer`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/detokenizer.py#L31)가 새 token ID를 text로 바꾼다. token을 하나씩 따로 decode하지 않고 request마다 상태를 들고 이어서 decode하는데, BPE token 하나가 UTF-8 문자의 일부일 수 있기 때문이다. 한 글자가 여러 token에 걸치면 마지막 token이 와야 그 글자가 나온다. fast tokenizer면 tokenizers 라이브러리의 [`DecodeStream`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/detokenizer.py#L179-L195)을 쓴다. 이어서 stop string을 확인하고, [`RequestOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/outputs.py#L129)을 만들어 [3번](#3-zmq-add-asyncllm에서-enginecore로)에서 등록한 queue에 넣는다. queue를 기다리던 `generate()`가 깨어나 이 값을 handler에 넘긴다. streaming request는 [`DELTA`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/protocol.py#L774)로 만들어져 `RequestOutput`에 새로 생긴 부분만 담기고, non-streaming request는 `FINAL_ONLY`라 끝났을 때 한 번만 나온다. DELTA에서 handler가 queue를 늦게 읽으면, 그사이에 쌓인 delta는 하나로 합쳐진다.

handler는 응답 형식에 맞게 마무리한다. 그 전에 reasoning parser와 tool parser가 [설정되어 있으면](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L131-L163), text에서 `reasoning_content`와 `tool_calls`를 따로 떼어 낸다. streaming이면 [`chat_completion_stream_generator()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L466)가 [`RequestOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/outputs.py#L129)마다 chat chunk를 만들어 `data: ...` 형식으로 보내고, 끝에 `data: [DONE]`을 보낸다. non-streaming이면 [`chat_completion_full_generator()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/serving.py#L935)가 generator를 끝까지 읽은 뒤 최종 text와 usage를 `ChatCompletionResponse` JSON 하나로 만든다. SSE chunk 수와 생성 token 수는 일대일이 아니다. 첫 role chunk와 마지막 usage chunk가 따로 있고, detokenizer가 문자를 다 만들 때까지 text를 미루기도 한다.

#### 설계 결정: detokenize와 stop string은 API server에서 한다

EOS token과 `max_tokens`는 token ID만 보면 되므로 EngineCore가 판단한다. 반면 detokenize와 stop string 검사는 API server process에서 한다. 이 분담은 [서버 초기화 4번의 process 분리](#설계-결정-enginecore-process-분리와-zmq)와 같은 RFC에서 나왔다. [RFC #6797](https://github.com/vllm-project/vllm/issues/6797)은 후속 과제로 "Decouple incremental detokenization logic so that it can also be used in the API server process"와 "The API server process can also intercept/process any stop strings, and just abort the request as needed"를 적었다. V1 `AsyncLLM`을 만든 [#9826](https://github.com/vllm-project/vllm/pull/9826)도 "stop strings are detected in the detokenizer and we send an abort message"라고 적는다. V1 설계를 정리한 [#8779](https://github.com/vllm-project/vllm/issues/8779)도 "De-tokenization is expensive"라며 batch가 클수록 이 비용이 커진다고 적는다. detokenize를 EngineCore loop 밖으로 빼면 이 CPU 작업이 GPU 실행과 겹친다.

stop string을 만나면 API server는 [`abort_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/output_processor.py#L552)로 frontend 상태를 정리하고, EngineCore에 abort를 보내 아직 실행 중인 request를 멈춘다. 이 abort가 [7번](#7-free-blocks-request-종료와-kv-block-정리)의 정리로 이어진다.

### 7. Free blocks: request 종료와 KV block 정리

7번은 끝난 request의 자원을 scheduler, worker, API server 세 곳에서 돌려주는 단계다. request는 정상 완료, stop string, client 취소, 오류 중 하나로 끝나고, 어느 경우든 같은 정리를 거친다. [6번](#6-detokenize-token-id에서-응답까지) 그림의 아래쪽이 이 정리를 보여 준다.

끝나는 경로는 누가 끝을 알아차리는지에 따라 둘로 나뉜다. EOS token이나 `max_tokens`는 EngineCore가 token ID만 보고 알 수 있으므로, scheduler가 abort 없이 바로 request를 끝낸다. 반면 stop string과 client 연결 끊김은 API server만 알 수 있다. 이때만 API server가 EngineCore에 abort를 보내 request를 멈춘다. 즉 abort는 모든 종료가 아니라, EngineCore 밖에서 끝을 정한 경우에만 쓰는 경로다. 6번 그림에서 왼쪽의 긴 화살표가 정상 종료이고, 주황색 점선이 abort다.

- scheduler: 정상 완료는 [6번](#6-detokenize-token-id에서-응답까지)의 `update_from_output()`에서, abort는 [`finish_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2649)에서 request를 queue에서 빼낸다. 두 경로 모두 [`_free_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2714)로 모인다. 이 함수는 multimodal request의 [encoder cache를 비우고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2734), [`KVCacheManager.free()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L620)로 KV block을 돌려준다.
- worker: scheduler는 끝난 request ID를 다음 step의 [`SchedulerOutput.finished_req_ids`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L260)에 실어 보낸다. worker는 [5번](#5-forward-gpu-forward와-sampling) ①의 [`finish_requests()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1152-L1160)에서 이 request가 쓰던 persistent batch의 행을 비운다. preempt된 request도 같은 방식으로 빠진다.
- API server: `OutputProcessor`가 [request 상태와 detokenizer를 지운다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/output_processor.py#L855-L857). `generate()`는 마지막 출력을 handler에 넘기고 끝난다.

여기서 free는 GPU 메모리를 CUDA allocator에 돌려주는 것이 아니다. block pool에서 참조를 풀어, 다음 request가 이 block을 다시 쓸 수 있게 하는 것이다. 반납이 늦춰지는 경우도 두 가지 있다. async scheduling에서는 GPU가 아직 그 block을 쓰는 step이 진행 중일 수 있어서, scheduler가 안전한 step까지 반납을 미룬다. disaggregated prefill이나 KV offloading처럼 KV connector가 block을 다른 곳으로 보내는 중이면, `_free_request()`가 [전송이 끝날 때까지](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2723-L2742) 반납을 미룬다.

client가 연결을 끊으면 [1번](#1-http-post-fastapi-router의-request-수신)의 cancellation이 [`AsyncLLM.generate()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L698-L809)까지 전달된다. `generate()`는 [`asyncio.CancelledError`를 받아](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L779) [`abort()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/async_llm.py#L911)를 호출하고, 이 함수가 API server의 출력 상태와 EngineCore 양쪽에서 request를 지운다. 그래서 끊긴 request가 GPU에서 계속 token을 만들지 않는다.

## 실행 batch와 KV cache

이 파트는 request 처리 [4번](#4-schedule-step마다-계산할-token-배정)과 [5번](#5-forward-gpu-forward와-sampling)에서 미뤄 둔 내용을 다룬다. [1번](#1-전체-구조-한-step의-실행-batch)에서 한 step의 batch가 만들어지는 전체 구조를 보고 그 세부를 차례로 설명한 뒤, [2번](#2-chunked-prefill-긴-prompt를-여러-step에-나누기)부터 그 구조 위에서 동작하는 기능을 본다. 예시에서 A, B, C는 서로 다른 request 세 개다. 사용자 세 명이 각자 보낸 chat request라고 보면 된다. 세 request는 한꺼번에 들어오지 않았다. A가 가장 먼저 들어왔고, C는 몇 step 전에, B는 이번 step 직전에 들어왔다. 예시는 도착 시각이 다른 셋이 같은 step에서 함께 계산되는 순간이다. A는 이미 16 token을 계산하고 다음 token을 decode하는 중이고, B는 2 token짜리 prompt를 처음 prefill하고, C는 긴 prompt를 position 14부터 이어서 prefill한다. position은 request 안에서 token의 순서 번호다. 이 글의 position, index, 번호는 모두 zero-based indexing이다. block 크기는 기본값인 16 token이다.

#### 1.1 request와 KV block의 자료구조

request와 KV block은 따로 관리된다. request 객체는 KV block을 직접 들고 있지 않고, KV block 쪽도 request를 가리키지 않는다. 둘은 request ID로만 이어진다. EngineCore process의 CPU 쪽에는 세 가지 자료구조가 있고, 앞 그림 1번의 상자 세 개가 이것이다.

- [`Request`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L60): scheduler가 관리하는 request 상태다. `prompt_token_ids`, 지금까지 만든 output token, 계산을 마친 token 수(`num_computed_tokens`), 상태(`status`), `sampling_params`, prefix caching용 block hash 목록([`block_hashes`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L225))을 담는다. `waiting`, `running` queue에 들어가는 것이 이 객체다.
- [`KVCacheBlock`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L176-L200): KV block 하나의 metadata다. `block_id`, 참조 수(`ref_cnt`), block hash, 그리고 `free_block_queue`의 이중 연결 리스트용 `prev_free_block`과 `next_free_block`만 들고 있다. KV 값 자체는 들고 있지 않다.
- [`req_to_blocks`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L122-L125): request ID에서 그 request가 쓰는 `KVCacheBlock` 목록으로 가는 dictionary다. `KVCacheManager` 안에 있고, request가 끝나면 이 목록으로 block을 돌려준다.

실제 KV 값은 GPU에 있다. [서버 초기화 5번](#5-enginecore-startup-model-load-kv-cache-allocation-scheduler-setup)에서 layer마다 할당한 KV cache tensor를 block 단위로 나눈 것이고, `block_id`는 그 tensor 안의 block 위치다. 모든 `KVCacheBlock`은 [`BlockPool.blocks`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L172)에 미리 만들어져 있고, block 0은 [null block](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/block_pool.py#L184-L188)으로 따로 잡아 둔다. 그래서 실제로 나눠 주는 block ID는 1부터 시작한다.

**block과 slot: KV cache의 칸 번호**

slot은 KV cache 안에서 token 하나의 K와 V가 들어가는 칸 하나에 붙인 번호다. block 하나는 token 16개를 담으므로, KV cache 전체는 `num_blocks * 16`개의 칸이 한 줄로 늘어선 것으로 볼 수 있다. 이 칸에 앞에서부터 0, 1, 2, … 번호를 붙인 것이 slot이다. 번호는 `slot = block ID * 16 + offset`으로 정해진다. offset은 block 안에서의 위치다. 예를 들어 request C의 position 14 token(이 글에서는 C14로 쓴다)은 block 9의 offset 14에 들어가므로 slot 158이고, C16은 block 4의 offset 0이라 slot 64다.

<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/04-slot-layout-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/04-slot-layout-dark.svg"
  caption="slot의 세 가지 모습. block을 칸 단위로 센 번호이고, 칸 하나에는 token 하나의 K와 V가 들어가며, 모든 layer가 같은 번호를 쓴다."
/>

칸 하나에 들어가는 것은 한 layer에서 그 token의 K 벡터와 V 벡터다. KV head가 여러 개면 slot은 head별로 나뉘지 않고, 모든 head의 K와 V를 한 slot이 함께 가리킨다. FlashAttention backend 기준으로 layer마다 KV cache tensor의 shape은 [`[num_blocks, num_kv_heads, block_size, 2 * head_size]`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/attention/backends/flash_attn.py#L1196-L1197)이다. KV를 쓰는 kernel은 slot을 [`slot // block_size`(block)와 `slot % block_size`(offset)로 다시 나눠](https://github.com/vllm-project/vllm/blob/v0.32.0/csrc/cache_kernels.cu#L343-L344) 이 tensor의 index로 쓴다. 그래서 slot 158은 `kv_cache[9, :, 14]` 자리다. 여기서 `:`가 모든 head를 뜻한다.

이때 slot은 논리적인 주소다. 물리 메모리에서는 head 축이 offset 축보다 앞에 있으므로, 한 slot에 속한 head 0의 값과 head 1의 값은 메모리에서 붙어 있지 않다. slot은 "block 9, offset 14에 있는 모든 head의 K와 V"를 한 번에 가리키는 번호이고, 실제 byte 위치는 kernel이 tensor의 stride로 계산한다.

KV cache tensor는 layer마다 따로 있지만 slot 번호는 모든 layer가 같이 쓴다. 한 step의 `slot_mapping` 하나를 [모든 layer가 같이 쓰므로](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/attn_utils.py#L446-L454), C14의 KV는 어느 layer에서든 각자 tensor의 같은 자리, 즉 slot 158에 쓰인다. 그래서 slot은 특정 layer의 메모리 주소가 아니라, token 하나가 KV cache 전체에서 차지하는 위치다.

layer마다 같은 번호를 써도 충돌하지 않는다. layer마다 tensor가 따로 있어서, 같은 번호라도 서로 다른 메모리를 가리키기 때문이다. request 사이에서도 slot은 겹치지 않는다. block pool은 block 하나를 한 번에 한 request에게만 나눠 주고, slot은 block에서 나오므로 그 block의 slot 16개도 그 request만 쓴다. 예외는 prefix caching이다. 여러 request가 같은 prefix의 꽉 찬 block을 `ref_cnt`를 올려 함께 쓰는데, 이 block은 내용이 같고 읽기만 하므로 문제가 없다. 새 KV는 각 request가 따로 받은 block의 slot에 쓴다.

worker도 같은 정보를 따로 들고 있다. scheduler는 step마다 새로 할당한 block ID를 [`SchedulerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L232)에 실어 보내고, worker는 이를 [`BlockTables`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/block_table.py#L17)에 request별로 이어 붙인다. 그래서 `BlockTables`에는 request마다 block ID 목록이 하나씩 있고, 목록의 n번째 값은 그 request의 n번째 block이 KV cache의 몇 번 block인지 나타낸다. 위 그림에서 request A의 목록은 `[7, 12]`다. A의 position 0-15 token의 KV는 block 7에, position 16-31 token의 KV는 block 12에 있다는 뜻이다. B와 C의 목록은 [전체 구조 그림](#1-전체-구조-한-step의-실행-batch)의 4번 상자에 있고, 각각 `[3]`과 `[9, 4]`다.

#### 1.2 scheduler 출력: prefill과 decode를 한 step에 섞는다

scheduler는 1.1의 두 자료구조로 [`SchedulerOutput`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L232)을 만들어 worker에 보낸다. 담기는 값은 둘이다.

- 이번 step에 계산할 token 수(`num_scheduled_tokens`): `Request`에서 나온다. request의 전체 token 수에서 `num_computed_tokens`를 뺀 값이 아직 계산하지 않은 token 수다. scheduler는 이 수를 token budget 안에서 잘라 배정한다. 예시에서는 `{A: 1, B: 2, C: 3}`이다.
- block ID: `req_to_blocks`에서 나온다. 이번 step에 처음 들어온 request는 [`NewRequestData`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L41)에 block ID 목록 전체와 `num_computed_tokens`를 담는다. 이미 돌고 있는 request는 [`CachedRequestData`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L138)에 이번 step에 새로 붙은 block ID(`new_block_ids`)만 담는다. worker가 앞의 목록을 이미 들고 있기 때문이다. 예시에서 B는 새 request라 목록 `[3]` 전체를 보낸다. A는 position 16이 block 12의 첫 칸이고, C는 position 16이 block 4의 첫 칸이다. 그래서 두 block은 이번 step에 할당되고, A는 `[12]`, C는 `[4]`만 보낸다.

이 배정 하나에 A의 decode와 B, C의 prefill이 함께 들어간다. 이렇게 섞을 수 있는 이유를 batching 방식의 차이로 보자.

vLLM의 batching은 batch를 step마다 다시 짜는 continuous batching이고, 여기에 prefill token과 decode token을 한 step에 섞는다. 그림은 같은 request 네 개를 세 방식으로 처리한다. 이 그림의 A-D는 1.3 예시와 다른 request다.

- static batching: A, B, C를 한 batch로 묶으면 가장 긴 A가 끝날 때까지 batch가 유지된다. 먼저 끝난 B와 C의 자리는 padding으로 채우고, step 2에 도착한 D는 batch가 끝난 step 7에야 시작한다.
- continuous batching: batch를 step마다 다시 짜므로 B와 C는 끝나는 대로 빠지고 D는 바로 들어온다. Orca 논문의 iteration-level scheduling에서 온 방식이다([Yu et al., OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/yu)). 다만 한 step이 prefill과 decode 중 하나만 돌리면, D가 prefill하는 step 3에 A, B, C의 decode는 한 step 쉰다. vLLM V0의 기본 scheduler가 이렇게 동작했다. prefill을 배정한 step에는 [decode를 배정하지 않았다](https://github.com/vllm-project/vllm/blob/v0.6.0/vllm/core/scheduler.py#L917).
- vLLM의 continuous batching: V1 scheduler에는 [prefill 단계도 decode 단계도 없다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L594-L600). request마다 아직 계산하지 않은 token 수만 보고 token budget 안에서 배정한다. 그래서 step 3에는 A, B, C의 decode token과 D의 prefill token이 함께 들어가고, 아무도 쉬지 않는다.

vLLM에는 batch 슬롯도 없다. 흔히 보는 continuous batching 그림은 슬롯 몇 개를 고정해 두고 빈 슬롯을 다음 request로 채운다. vLLM은 step마다 `running` request 중 token budget과 KV block이 허락하는 만큼의 token을 골라 1차원 배열 하나로 이어 붙인다. request를 `[request 수 * 최대 길이]` 격자로 맞추지 않으므로 request별 padding도 없다. request 경계는 position과 attention metadata로 따로 넘긴다. 이 배열이 실제로 어떻게 생겼는지는 아래에서 차례로 본다. padding이 완전히 사라진 것은 아니다. CUDA graph를 쓸 때는 batch 크기를 capture한 크기로 맞추느라 끝에 약간 남는다.

#### 1.3 step 안의 token packing

먼저 이 step 직전에 세 request가 어디까지 와 있는지 보자. token 이름은 1.1의 C14처럼 request 이름 뒤에 position을 붙인다. `A16`은 request A의 position 16 token이다.

<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/04-request-history-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/04-request-history-dark.svg"

- A는 오래전에 들어온 request다. 이전 step들에서 prompt를 prefill하고 token을 몇 개 생성했다. 그래서 A0-A15의 KV는 이미 KV cache에 있다. A16은 바로 앞 step에서 sampling으로 뽑은 token이고, 아직 KV가 없다. 이번 step은 A16의 KV를 계산하고, 그 결과로 다음 token A17을 뽑는다. 이것이 decode다.
- B는 방금 들어온 request다. prompt가 2 token이라 B0, B1을 한 번에 prefill한다.
- C는 prompt가 긴 request다. 앞 step에서 prompt의 첫 조각 C0-C13을 prefill했다. 이번 step은 다음 조각 C14-C16을 계산하고, C17부터는 다음 step으로 넘긴다(chunked prefill).

그래서 세 request는 이번 step에 계산하는 token 수도, 지금까지의 길이도 다르다. 이번 step에 들어가는 것은 주황색 token 6개뿐이다. 회색 token은 다시 계산하지 않고, attention이 KV cache에서 그 KV를 읽기만 한다.

한 step에 계산할 token은 request별로 따로 담지 않고, 1차원 배열 하나에 이어 붙인다. 이 배열을 packed batch라고 부르자. 아래 그림의 step에서 A는 decode token 1개, B는 prefill token 2개, C는 prefill 조각 3개를 계산하므로, 6 token이 차례로 배열의 index 0-5에 들어간다. 끝의 index 6-7은 CUDA graph 크기를 맞추는 padding이다. worker의 [`InputBatch`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/input_batch.py#L39-L100)는 이 배열과 함께 request 경계를 알려 주는 배열을 만든다.

<Figure
  src="/assets/images/post/2026-10-12-Inside-vLLM/04-batch-kv-cache-light.svg"
  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/04-batch-kv-cache-dark.svg"

token마다 값이 있는 배열은 index를 기준으로 읽으면 된다. 아래 표의 한 열이 packed batch의 칸 하나다.

| packed batch index | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 이 칸의 request | A | B | B | C | C | C | PAD | PAD |
| `input_ids` | A16 | B0 | B1 | C14 | C15 | C16 | PAD | PAD |
| `positions` | 16 | 0 | 1 | 14 | 15 | 16 | - | - |

<small>참고: A16, B0 같은 token 이름은 편의상 붙인 이름이다. 실제 배열에는 tokenizer의 정수 token ID가 들어간다.</small>

request마다 값이 있는 배열은 request 순서(A, B, C)로 읽는다.

| request | A | B | C |
| --- | --- | --- | --- |
| `query_start_loc` (시작 index) | 0 | 1 | 3 |
| 이번 step의 token 수 | 1 | 2 | 3 |
| `seq_lens` | 17 | 2 | 17 |

`query_start_loc`은 실제로는 `[0, 1, 3, 6]`이다. 마지막 6은 C가 끝나는 index다.

- [`input_ids`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/input_batch.py#L88): 각 칸에서 계산할 token의 ID다. 실제 배열에는 tokenizer vocabulary의 정수 ID가 들어간다. 이미 KV를 계산한 token은 넣지 않는다. 그래서 A는 앞의 16 token(A0-A15)을 건너뛰고 A16 하나만 들어간다.
- [`positions`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/input_batch.py#L90): 각 칸의 token이 자기 request의 문장 안에서 몇 번째 token인지를 담는다. packed batch의 index와는 다르다. 예를 들어 C15는 packed batch의 index 4에 있지만, request C 안에서는 15번째 위치이므로 position은 15다. 여러 request를 이어 붙였기 때문에 index만 보면 원래 위치를 알 수 없고, 그래서 이 배열이 따로 필요하다. model은 RoPE 같은 위치 encoding에 이 값을 쓰고, [1.4](#14-block-table-token-위치에서-kv-cache-주소로)의 slot 계산도 이 값을 쓴다.
- [`query_start_loc`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/input_batch.py#L66): 각 request의 token이 packed batch의 어느 index에서 시작하는지를 담는다. 길이는 request 수 + 1이다. request i의 token은 index `query_start_loc[i]`부터 `query_start_loc[i+1]` 바로 앞까지다. A는 index 0, B는 1-2, C는 3-5다.
- [`seq_lens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/input_batch.py#L69): request마다 이번 step이 끝났을 때의 전체 길이다. KV cache에 이미 있는 token도 센다. A는 cache의 16 token과 새 token 1개를 더해 17이다. attention은 새 token이 이 길이만큼의 KV를 보게 한다.

그림 아래쪽의 `slot_mapping`은 token마다 KV를 쓸 slot 번호다. slot은 [1.1](#11-request와-kv-block의-자료구조)에서 본 KV cache의 칸 번호이고, 이 번호를 구하는 방법은 [1.4](#14-block-table-token-위치에서-kv-cache-주소로)에서 본다.

attention kernel은 `query_start_loc`으로 request 경계를 알고, `seq_lens`로 각 request가 읽을 KV 길이를 안다. 그래서 각 token은 자기 request의 KV만 보고, 길이가 다른 request도 request별 padding 없이 한 forward에 들어간다.

**자료구조에서 배열로**

이 배열들은 앞에서 본 자료구조로 만든다. 재료는 세 가지다.

| 재료 | 출처 | A | B | C |
| --- | --- | --- | --- | --- |
| 이미 계산한 token 수 | [`Request.num_computed_tokens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L184) | 16 | 0 | 14 |
| 이번 step에 계산할 token 수 | [`SchedulerOutput.num_scheduled_tokens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L244) | 1 | 2 | 3 |
| block ID 목록 | `req_to_blocks`의 사본(worker의 `BlockTables`) | `[7, 12]` | `[3]` | `[9, 4]` |

worker는 이 재료로 배열을 계산한다. `query_start_loc`은 `num_scheduled_tokens`의 [누적합이고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1430), `positions`와 `seq_lens`는 [`num_computed_tokens`에서 나온다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1460-L1466).

| 배열 | 계산식 | A | B | C |
| --- | --- | --- | --- | --- |
| `input_ids` | token 목록의 `num_computed_tokens`번째부터 `num_scheduled_tokens`개 | A16 | B0, B1 | C14-C16 |
| `positions` | `num_computed_tokens`부터 1씩 증가 | 16 | 0, 1 | 14-16 |
| `query_start_loc` | `num_scheduled_tokens`의 누적합 | 0 | 1 | 3 (끝은 6) |
| `seq_lens` | `num_computed_tokens` + `num_scheduled_tokens` | 17 | 2 | 17 |
| `slot_mapping` | position과 block ID 목록으로 계산(1.4) | 192 | 48, 49 | 158, 159, 64 |

<small>참고: A16, B0 같은 token 이름은 편의상 붙인 이름이다. 실제 배열에는 tokenizer의 정수 token ID가 들어간다.</small>

정리하면, request 상태는 어떤 token을 넣을지 정하고, block table은 그 token의 KV를 어디에 쓸지 정한다. `slot_mapping` 계산은 1.4에서 본다.

#### 1.4 block table: token 위치에서 KV cache 주소로

block table은 "request의 몇 번째 token의 KV가 KV cache의 어디에 있는가"에 답하는 표다. KV cache는 16 token짜리 block으로 나뉘어 있고, 한 request의 block은 KV cache 안에서 연속으로 놓이지 않는다. 그래서 token의 position만으로는 KV의 위치를 알 수 없고, request마다 block ID 목록을 따로 들고 있어야 한다. OS가 page table로 가상 주소를 물리 메모리 주소로 바꾸는 것과 같은 구조이고, vLLM의 [PagedAttention 논문](https://arxiv.org/abs/2309.06180)이 이 비유로 설계를 설명한다.

attention layer는 forward 중에 KV cache를 두 번 쓴다.

- 쓰기: 이번 step에 계산한 token의 새 K, V를 KV cache에 저장한다. 저장할 위치는 `slot_mapping`이 token마다 알려 준다. FlashAttention backend에서는 [`reshape_and_cache_flash()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/attention/backends/flash_attn.py#L1452-L1460)가 이 일을 한다.
- 읽기: 각 token이 같은 request의 앞 token을 보려면, 그 token들의 K, V를 KV cache에서 읽어야 한다. attention kernel은 [block table과 `seq_lens`를 받아](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/attention/backends/flash_attn.py#L1399-L1413) 직접 읽는다.

두 경로 모두 block table로 위치를 찾는다. 쓰기 경로에서는 [slot mapping kernel](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/block_table.py#L341-L348)이 미리 block table로 `slot_mapping`을 만들어 두고, 읽기 경로에서는 attention kernel이 block table을 직접 본다.

**position에서 slot까지**

<FigureSteps
  base="/assets/images/post/2026-10-12-Inside-vLLM/04-block-table-lookup"
  caption="request C의 position이 block table을 거쳐 KV cache slot이 되는 과정."
  labels={[
    'C14: 14 // 16 = 0이므로 block 9, offset은 14이므로 slot 158이다.',
    'C15: 같은 block 9의 offset 15, slot 159다.',
    'C16: 16 // 16 = 1이므로 block 4로 넘어가고, offset은 0이므로 slot 64다.',
    '세 token 전체. 실제 forward에서는 세 token의 KV를 한 번에 쓴다.',
  ]}
/>

request C의 token C14가 KV를 쓸 위치를 찾는 과정은 세 단계다. C의 block ID 목록은 `[9, 4]`다.

1. block: position 14를 block 크기 16으로 나눈 몫은 0이다. C의 목록에서 0번째 값은 block 9다.
2. offset: 14를 16으로 나눈 나머지는 14다.
3. slot: block 9의 offset 14이므로 `9 * 16 + 14 = 158`이다.

C16은 position 16이라 몫이 1이다. C의 목록에서 1번째 값인 block 4로 넘어가고, offset은 0이므로 slot은 `4 * 16 + 0 = 64`다. C14와 C16은 position으로는 두 칸 차이지만, KV cache 안에서는 block 9와 block 4로 멀리 떨어져 있다. 이것이 paged KV cache다. 세 단계를 한 식으로 쓰면 아래와 같다.

$$
\text{slot} = \text{block\_table}\big[\lfloor \text{position} / \text{block\_size} \rfloor\big] \times \text{block\_size} + (\text{position} \bmod \text{block\_size})
$$

이번 step의 `slot_mapping`은 아래와 같다. `input_ids`와 같은 순서로 token마다 slot 하나를 담고, CUDA graph padding token은 `-1`로 채워 아무 데도 쓰지 않는다.

```text
token        = [A16, B0, B1, C14, C15, C16, PAD, PAD]
slot_mapping = [192, 48, 49, 158, 159,  64,  -1,  -1]
```

**다음 step**

다음 step도 같은 계산을 한다. A가 position 17의 token을 계산하면, 몫은 1이므로 A의 목록 `[7, 12]`에서 block 12를 고르고, offset 1을 더해 slot `12 * 16 + 1 = 193`에 쓴다. A가 position 32에 이르러 block 12가 꽉 차면, scheduler가 `allocate_slots()`로 새 block을 받아 A의 목록 끝에 붙인다.

### 2. chunked prefill: 긴 prompt를 여러 step에 나누기

prompt가 한 step의 token budget보다 길면 scheduler는 prompt를 여러 step에 나눠 계산한다. 위 예시의 C가 바로 이런 조각이다. C는 이번 step에 position 14부터 16까지 3 token만 계산하고, 나머지는 다음 step으로 넘긴다.

나누는 방법은 단순하다. scheduler는 request마다 남은 token 수를 계산한 뒤, 이를 [남은 token budget으로 자른다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L704-L712). 남은 부분은 request의 `num_computed_tokens`에 기록되어, 다음 step에 이어서 배정된다. `enable_chunked_prefill`은 [기본으로 켜져 있다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/scheduler.py#L134). 끄면 budget보다 긴 새 request는 [그 step에 넣지 않는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L1158-L1167).

긴 prompt 하나가 budget을 다 차지하면 다른 request의 decode가 밀린다. `--long-prefill-token-threshold`는 이를 막는 상한이다. request 하나가 한 step에 계산할 prefill token 수를 이 값으로 자른다. 기본값은 0(끔)이고, request가 하나뿐이면 밀릴 request가 없으므로 [적용하지 않는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L640-L649). encoder-decoder model은 chunked prefill을 지원하지 않아서 [자동으로 끈다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/scheduler.py#L294-L302).

#### 전체 구조에서 보면

예시의 C로 [전체 구조](#1-전체-구조-한-step의-실행-batch)의 각 단계가 어떻게 바뀌는지 보면 아래와 같다.

- [1.1](#11-request와-kv-block의-자료구조) 자료구조: 이번 step 전 C의 `num_computed_tokens`는 14다. position 16은 첫 block(0-15)을 넘으므로, `allocate_slots()`가 block 4를 새로 꺼내 `req_to_blocks`의 C 목록에 붙인다.
- [1.2](#12-scheduler-출력-prefill과-decode를-한-step에-섞는다) scheduler 출력: `num_scheduled_tokens`에서 C는 budget으로 잘린 3이다. 새 block ID는 [`CachedRequestData.new_block_ids`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L150)로 가고, worker는 이를 [C의 기존 block ID 목록 뒤에 붙인다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L140-L150). 그래서 C의 목록은 `[9]`에서 `[9, 4]`가 된다.
- [1.3](#13-step-안의-token-packing) 배열: `positions`는 14-16이고, `seq_lens`는 14 + 3 = 17이다. 나머지 prompt는 배열에 없다.
- [1.4](#14-block-table-token-위치에서-kv-cache-주소로) slot: 158, 159, 64다. step이 끝나면 `num_computed_tokens`는 17이 되고, 다음 step의 C는 position 17(slot 65)부터 같은 목록으로 이어 간다.

### 3. speculative decoding: draft token이 batch와 KV에 들어가는 방식

speculative decoding은 작은 drafter가 다음 token 몇 개를 미리 추측하고, 본 model이 한 forward에서 이를 한꺼번에 검증하는 방식이다. 추측이 맞으면 한 step에 token 여러 개를 얻는다. drafter의 종류는 다양하다. v0.32.0의 MRV2에는 n-gram, EAGLE, MTP, DFlash 등이 [들어 있다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode). 여기서는 알고리즘이 아니라, draft token이 지금까지 본 batch와 KV 구조에 어떻게 들어가는지만 본다.

- request: draft token은 [`Request.spec_token_ids`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L183)에 붙는다. scheduler가 보는 길이 [`num_tokens_with_spec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L299-L300)에는 draft token이 포함된다. 그래서 decode request도 이번 step에 1 token이 아니라 `1 + draft 수`만큼 배정된다.
- batch: 배정된 draft token은 [`SchedulerOutput.scheduled_spec_decode_tokens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L251)로 worker에 간다. worker는 이를 다른 token과 함께 [packed batch](#13-step-안의-token-packing)에 넣어 forward 한 번으로 계산하고, rejection sampler가 어디까지 맞았는지 판정한다.
- KV: draft token도 일반 token처럼 KV cache에 KV를 쓴다. 자세한 처리는 아래에서 본다.

#### draft token의 KV cache 처리

draft token의 KV는 일반 token과 같은 block, 같은 slot 계산으로 쓰이고, 틀린 draft의 KV는 지우지 않고 다음 step에 덮어쓴다. 예시의 A가 draft 2개(d17, d18)를 받았다고 하자. d는 draft token이라는 표시이고, d17은 drafter가 position 17에 추측한 token이다.

1. Schedule: A는 이번 step에 3 token(A16, d17, d18)을 배정받는다. `allocate_slots()`의 `num_new_tokens`에는 [검증 전 draft token도 포함된다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L450). position 16-18은 모두 block 12 안이므로 새 block은 필요 없다.
2. Forward: 세 token은 [1.3](#13-step-안의-token-packing)의 배열에 함께 들어간다. `positions`는 16, 17, 18이고, [1.4](#14-block-table-token-위치에서-kv-cache-주소로)와 같은 계산으로 `slot_mapping`은 192, 193, 194다. 본 model은 forward 한 번으로 세 token의 KV를 모두 쓰고, 각 위치의 다음 token을 예측한다. 세 token을 계산했으므로 `num_computed_tokens`는 16 + 3 = 19가 된다.
3. Verify: rejection sampler가 d17은 맞고 d18은 틀렸다고 판정하면, d17을 받고 position 18에는 본 model이 sampling한 token을 쓴다. scheduler는 `num_computed_tokens`를 19에서 틀린 draft 수만큼 [되돌려 18로 만든다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2113-L2127).
4. Overwrite: slot 194에는 틀린 d18의 KV가 남아 있다. 하지만 `num_computed_tokens`가 18이므로 다음 step은 position 18부터 다시 계산하고, 새 token의 KV가 slot 194를 덮어쓴다. block을 반납하거나 KV를 지우는 작업은 없다.

prefix cache에는 검증된 token만 올라간다. block hash를 등록할 token 수를 [`request.num_tokens`로 자르므로](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L455-L456), 검증 전 draft가 든 block은 hash가 붙지 않는다. 그래서 다른 request가 틀린 draft의 KV를 prefix cache로 재사용하는 일은 없다.

#### drafter별 KV cache

drafter가 model이면 그 attention layer도 KV를 쓰고, 이 KV는 본 model과 같은 자료구조에 들어간다. draft layer는 본 model과 같은 `vllm_config`에 등록되고, [`get_kv_cache_spec()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/attn_utils.py#L142-L151)이 모든 attention layer의 spec을 한 dictionary에 모은다. 그래서 [1.1](#11-request와-kv-block의-자료구조)의 `KVCacheManager`와 block pool이 draft KV까지 관리한다. layer의 spec이 모두 같은 일반적인 경우 [한 KV cache group으로 묶이므로](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L2189-L2193), block ID 하나가 본 model layer와 draft layer의 KV tensor에서 같은 자리를 가리킨다. worker의 drafter도 본 model의 [`BlockTables`를 그대로 쓰고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/speculator.py#L298), [1.4](#14-block-table-token-위치에서-kv-cache-주소로)와 같은 방식으로 `slot_mapping`을 계산한다.

[`num_lookahead_tokens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L615-L641)는 이와 별개다. EAGLE처럼 자기 KV cache를 쓰는 drafter를 위한 값이다([docstring](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L395-L397)). drafter는 다음 step에 쓸 draft를 만들면서 그 위치의 KV를 쓴다. 그래서 `allocate_slots()`는 본 model이 쓸 slot에 이 수를 더한 만큼 [block을 미리 잡는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L542-L544).

drafter마다 다른 점은 자기 KV가 있는지, 틀린 draft의 KV를 어떻게 처리하는지, lookahead slot이 몇 개 필요한지다. 아래 표에서 K는 `num_speculative_tokens`이고, lookahead 값은 [`VllmConfig.num_lookahead_tokens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L615-L641)에서 정한다.

| drafter | 자기 KV | 틀린 draft 자리의 drafter KV | lookahead |
| --- | --- | --- | --- |
| n-gram, suffix | 없음. 이미 나온 token에서 같은 패턴을 찾는다 | 해당 없음 | 0 |
| EAGLE, EAGLE3, MTP | 있음. 본 model의 hidden state를 받는 draft layer | 본 model과 같은 query 길이로 [틀린 위치까지 계산하고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/target_dependent_ar/speculator.py#L204-L209), 다음 step에 덮어쓴다 | K |
| multi-module MTP | 있음. MTP module 여러 개 | 다음 step에 입력을 다시 넣어 [뒤쪽 module의 오래된 slot을 갱신한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/multi_module_mtp/speculator.py#L52-L54) | K |
| DFlash (dflash2, LiLiCorr 포함) | 있음. bonus 1개와 mask K개 query를 [한 번에 계산한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/dflash/speculator.py#L60-L62) | 틀린 행은 [PAD slot을 받아 KV를 쓰지 않는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/dflash/speculator.py#L628-L632) | K + 1 |
| DSpark | 있음. DFlash를 확장한 block drafter | DFlash와 같다 | 기본(anchor sampling) K, 그 외 K + 1 |
| draft model | 있음. 별도의 작은 LM | [임시 KV를 쓰고 나중에 덮어쓴다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/standalone_ar/speculator.py#L477-L479) | K |
| Gemma4 MTP | 없음. 본 model layer의 [KV를 공유한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/gemma4/speculator.py#L5-L7) | 해당 없음 | K |

정리하면, drafter KV도 본 model KV와 같은 규칙을 따른다. block은 scheduler가 `req_to_blocks`로 나눠 주고, worker는 같은 block table로 slot을 찾으며, 틀린 자리는 지우지 않고 다시 쓴다. 다른 점은 drafter가 본 model보다 앞선 position에 KV를 쓴다는 것뿐이고, 그 자리를 lookahead slot이 미리 확보한다.

#### 설계 결정: drafter의 KV를 본 model과 같은 pool에 둔다

v0.32.0은 drafter의 KV를 본 model과 같은 KV cache pool에 둔다. 이렇게 하면 drafter가 본 model의 block table과 `slot_mapping`을 그대로 쓸 수 있다. 코드 주석도 batch 모양과 KV cache 배치가 같아서 draft prefill에 본 model의 attention metadata와 slot mapping을 [바로 쓸 수 있다고 적는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/target_dependent_ar/speculator.py#L282-L284).

이 결정은 hybrid model에서 비용이 드러난다. hybrid model은 linear attention과 full attention처럼 서로 다른 layer를 섞은 model이다. [RFC #59117](https://github.com/vllm-project/vllm/issues/59117)은 GDN과 full attention을 섞은 27B model에 DFlash drafter를 붙인 사례를 vLLM 0.30 기준으로 보고한다. drafter의 sliding window layer가 새 KV cache spec을 더하면서 KV cache group이 4개에서 16개로 늘었다. 그 결과 쓸 수 있는 KV cache가 369,121 token에서 33,530 token으로 줄었다. 이 RFC는 drafter에 전용 pool을 주자고 제안한다. [RFC #58638](https://github.com/vllm-project/vllm/issues/58638)은 같은 문제를 group을 나누는 방식을 고쳐서 풀자고 제안한다. 두 RFC 모두 아직 open 상태이고, v0.32.0은 공유 pool을 유지한다.

#### 설계 결정: drafter가 쓸 자리를 미리 잡는다

scheduler는 본 model이 계산할 token 외에 lookahead slot까지 [block을 잡는다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L542-L544). drafter는 본 model의 query 범위 뒤쪽 position에 KV를 쓰는데, block table이 그 position을 덮지 않으면 엉뚱한 block에 쓰게 된다. [PR #42971](https://github.com/vllm-project/vllm/pull/42971)은 이 문제를 실제로 겪은 사례다. 새 request의 첫 step에 lookahead block을 잡지 않아서, DFlash drafter가 마지막 prefill block에 KV를 덮어썼다. prefix caching을 켜고 동시 request가 많으면 그 block은 여러 request가 공유하는 block이라, 정상이던 request의 KV까지 망가졌다. scheduler 쪽 수정은 [PR #43733](https://github.com/vllm-project/vllm/pull/43733)에서 들어갔다. 지금은 lookahead 값을 [`num_lookahead_tokens` 한 곳에서만 계산하고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L616-L623), scheduler와 worker warmup이 같은 값을 읽는다.

#### 설계 결정: 틀린 draft의 KV는 지우지 않고 덮어쓴다

틀린 draft의 KV는 지우지 않는다. scheduler는 `num_computed_tokens`만 되돌리고, 다음 step이 같은 slot에 올바른 KV를 쓴다. EAGLE 계열 drafter는 한발 더 나아가 틀린 위치까지 포함해 본 model과 같은 query 길이로 계산한다. 코드 주석에 따르면 이유는 두 가지다. 틀린 token 수를 CPU가 알려면 CPU와 GPU를 동기화해야 하는데, 이를 피할 수 있다. 그리고 본 model의 `query_start_loc`, `seq_lens` 같은 attention metadata를 [그대로 다시 쓸 수 있다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/spec_decode/target_dependent_ar/speculator.py#L204-L209). 이는 Model Runner V2의 설계 원칙과도 맞는다. MRV2 설계 문서는 speculative decoding처럼 CPU가 아직 모르는 값을 [GPU가 직접 계산하게 한다](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/design/model_runner_v2.md#L136-L138)고 적는다. MRV2를 도입한 [PR #25266](https://github.com/vllm-project/vllm/pull/25266)도 같은 방향이다.

#### 설계 결정: draft를 위한 자리도 token budget에서 뺀다

drafter가 본 model의 batch 안에서 draft query를 계산하면, 그 query도 한 step의 token budget을 쓴다. 그래서 scheduler는 drafter 방식에 따라 request마다 [추가 slot 수를 budget에서 미리 뺀다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/speculative.py#L1887-L1925). EAGLE3와 MTP는 0, draft model은 1, DFlash는 K다. 이 표는 v0.32.0 기준이다. 그 직후 [PR #59468](https://github.com/vllm-project/vllm/pull/59468)은 DFlash와 DSpark가 draft를 본 model batch 밖에서 계산한다는 점을 들어 이 값을 0으로 바꿨다. 이 PR은 v0.32.0 tag에는 들어 있지 않다.

### 4. block 소유: scheduler가 할당하고 worker는 쓰기만 한다

block의 주인은 scheduler다. worker는 받은 block table대로 읽고 쓸 뿐, block을 할당하거나 반납하지 않는다. 할당, 반납, prefix cache 재사용 규칙은 [request 처리 4번](#4-schedule-step마다-계산할-token-배정)의 [KVCacheManager 소제목](#kvcachemanager-block을-나눠-주고-돌려받는-방식)에서 다뤘다. 여기서는 그 규칙이 위 자료구조에서 어떻게 보이는지만 정리한다.

- 할당: `free_block_queue`에서 `KVCacheBlock`을 꺼내 `ref_cnt`를 1로 만들고, `req_to_blocks[request_id]`에 붙인다. worker에는 다음 `SchedulerOutput`으로 block ID가 전달된다.
- 공유: prefix cache가 맞으면 같은 `KVCacheBlock`이 두 request의 `req_to_blocks`에 함께 들어가고, `ref_cnt`가 2가 된다. 두 request의 block ID 목록에 같은 block ID가 들어가므로, GPU의 같은 KV를 함께 읽는다.
- 반납: request가 끝나면 그 request의 block마다 `ref_cnt`를 1씩 내린다. 0이 된 block만 `free_block_queue`로 돌아간다. GPU 메모리는 그대로이고, 다음에 이 block을 받는 request가 그 자리를 덮어쓴다.

### 5. 멀티턴 대화: prefix caching으로 이전 턴의 KV를 다시 쓴다

멀티턴 대화는 이전 턴의 KV를 대부분 다시 쓴다. vLLM에는 대화 세션이라는 개념이 없지만, prefix caching이 같은 효과를 낸다.

  caption="두 번째 턴이 첫 번째 턴의 KV block을 다시 쓰는 과정."
/>

서버 입장에서 멀티턴 대화는 턴마다 새 request다. client가 이전 대화 전체를 `messages`에 다시 담아 보내고, 서버는 이를 처음 보는 request처럼 처리한다. 첫 번째 턴이 끝나면, 정상 종료든 stop string이나 연결 끊김에 따른 abort든 그 request의 block은 반납된다. 하지만 꽉 찬 block은 hash를 가진 채 `free_block_queue` 뒤에 들어가고, GPU의 KV 값도 그대로 남는다. 다른 request가 그 block을 받아 덮어쓰기 전까지는 다시 쓸 수 있다.

두 번째 턴이 오면 renderer가 대화 전체를 다시 token화하고, scheduler가 block hash를 계산한다. 앞부분은 첫 번째 턴과 token이 같으므로 hash도 같고, `get_computed_blocks()`가 그 block을 찾아 다시 쓴다. 첫 번째 턴의 답변도 대부분 포함된다. 생성된 token도 block이 꽉 찰 때마다 [hash가 붙고](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/request.py#L272-L288), `allocate_slots()`가 계산을 마친 token까지 [cache에 등록하기](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_manager.py#L607-L615) 때문이다. 결국 새로 prefill하는 것은 처음으로 hash가 어긋나는 block부터다.

다만 다시 계산되는 부분이 생기는 경우가 세 가지 있다.

- 마지막 block: 꽉 차지 않은 block은 hash가 없어서 공유되지 않는다. 그래서 첫 번째 턴 끝의 최대 15 token은 다시 계산한다.
- token이 달라지는 경우: 첫 번째 턴의 답변은 다음 턴에서 text로 돌아와 다시 token화된다. 이때 생성할 때와 다른 token이 될 수 있고, chat template이 턴 끝에 특수 token을 넣기도 한다. token이 처음 달라지는 block부터는 다시 계산한다.
- eviction: 턴 사이에 다른 request가 많이 들어와 block이 모자라면, 오래 쓰지 않은 cache block부터 덮어써진다. 그 부분은 다시 prefill한다. KV offloading을 켜면 밀려난 block을 CPU 메모리나 디스크에서 다시 불러올 수 있다.

여러 사용자가 한 서버를 쓸 때는 prefix cache가 사용자 사이에서도 공유된다는 점에 주의해야 한다. chat completions request의 [`cache_salt`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/chat_completion/protocol.py#L485-L492)를 사용자마다 다르게 주면, 첫 block의 hash에 salt가 섞여 다른 사용자의 cache와 맞지 않게 된다. 같은 이유로, system prompt를 턴마다 바꾸지 않아야 앞부분 block이 계속 재사용된다.

#### 생성 중에 새 입력이 들어올 때

생성 중에 들어온 입력은 일반 request와 streaming 입력 세션에서 다르게 처리된다. 일반 request는 새 request로 함께 돌고, streaming 세션은 현재 턴이 끝날 때까지 다음 조각을 기다리게 한다.

  darkSrc="/assets/images/post/2026-10-12-Inside-vLLM/05-input-during-gen-dark.svg"
  caption="생성 중에 들어온 입력: 새 request와 streaming 입력 세션."
/>

일반 chat이나 agent request는 이미 돌고 있는 생성에 입력을 끼워 넣을 수 없다. 생성 중에 새 메시지가 오면 vLLM은 이를 새 HTTP request로 처리한다. 앞 request는 그대로 생성을 이어 가고, 두 request는 같은 step의 batch에 함께 들어간다. 앞 request를 멈추려면 client가 연결을 끊어야 하고, 그러면 [request 처리 7번](#7-free-blocks-request-종료와-kv-block-정리)의 abort 경로를 탄다.

새 request는 보통 대화 전체를 다시 담아 오므로 prefix cache 효과를 본다. 앞 request가 계산을 마친 꽉 찬 block에는 이미 hash가 붙어 있다. 그래서 앞 request가 아직 생성 중이어도, 새 request는 그 block을 `ref_cnt` 2로 공유한다. agent의 tool 호출도 같은 구조다. model이 tool 호출을 출력하면 그 request는 정상 종료되고, tool 결과를 붙인 다음 턴은 새 request로 들어와 이전 턴의 KV를 prefix cache로 다시 쓴다.

[request 처리 3번](#3-zmq-add-asyncllm에서-enginecore로)의 streaming 입력 세션은 다르게 동작한다. 이 세션은 같은 request ID로 입력 조각을 이어 붙인다(`resumable=True`). 생성 중에 다음 조각이 오면 scheduler는 끼어들지 않고 그 조각을 [`streaming_queue`에 쌓아 둔다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2615-L2623). 현재 턴의 생성이 끝나면 [`_handle_stopped_request()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L2464-L2490)가 request를 끝내지 않고, queue에서 다음 조각을 꺼내 같은 request로 이어 간다. queue가 비어 있으면 request는 `WAITING_FOR_STREAMING_REQ` 상태로 다음 입력을 기다린다. 어느 경우든 request가 끝나지 않으므로 KV block도 반납하지 않는다. 그래서 다음 조각은 prefix cache를 찾을 필요 없이 이전 KV 위에서 바로 이어 계산된다.

#### 전체 구조에서 보면

첫 번째 턴이 block 7, 12, 5에 KV를 남기고 끝났다고 하자. 두 번째 턴의 앞 48 token은 첫 번째 턴과 같으므로, 이 3 block(16 * 3 = 48 token)이 prefix cache에 맞는다.

- [1.1](#11-request와-kv-block의-자료구조) 자료구조: `get_computed_blocks()`가 찾은 block 7, 12, 5가 새 request의 `req_to_blocks` 목록 앞에 그대로 들어가고, 각 block의 `ref_cnt`가 1 오른다. request의 `num_computed_tokens`는 0이 아니라 48에서 시작한다.
- [1.2](#12-scheduler-출력-prefill과-decode를-한-step에-섞는다) scheduler 출력: 새 request는 [`NewRequestData`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L41)로 worker에 간다. 여기에는 cache에 맞은 block을 포함한 [전체 block ID와 `num_computed_tokens`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/output.py#L47-L48)가 들어 있다.
- [1.3](#13-step-안의-token-packing) 배열: `input_ids`와 `positions`는 position 48부터 시작한다. `seq_lens`는 48에 이번에 계산할 token 수를 더한 값이다.
- [1.4](#14-block-table-token-위치에서-kv-cache-주소로) slot: `slot_mapping`은 새 token의 slot만 담는다. attention은 block ID 목록의 앞쪽 block 7, 12, 5에서 앞 48 token의 KV를 읽는다. 계산은 건너뛰고, 읽기만 하는 것이다.

### 6. disaggregated prefill/decode: KV block이 instance 밖으로 나갈 때

prefill은 계산이 많고, decode는 메모리 대역폭을 많이 쓴다. 두 일을 서로 다른 instance에 나누면 각각에 맞게 GPU를 쓸 수 있다. 이를 disaggregated prefill/decode(P/D)라고 한다. 이때 prefill instance가 만든 KV block을 decode instance로 옮겨야 하고, vLLM은 이 일을 KV connector에 맡긴다.

KV connector는 [`--kv-transfer-config`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/kv_transfer.py#L60-L73)의 `kv_connector`로 고르고, `kv_role`로 이 instance가 KV를 보내는 쪽(`kv_producer`)인지 받는 쪽(`kv_consumer`)인지 정한다. NIXL 기반 [`NixlConnector`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/distributed/kv_transfer/kv_connector/factory.py#L178) 등이 있다. [connector](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/distributed/kv_transfer/kv_connector/v1/base.py#L180)는 scheduler 쪽과 worker 쪽으로 나뉜다. scheduler 쪽은 block 할당과 반납 시점을 정하고, worker 쪽은 실제로 KV를 layer마다 보내고 받는다.

- prefill instance: request는 prefill을 마치면 끝난다. 이때 scheduler가 connector의 [`request_finished()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/distributed/kv_transfer/kv_connector/v1/base.py#L616-L636)를 호출하고, connector가 "아직 보내는 중"이라고 답하면 block 반납을 미룬다. [request 처리 7번](#7-free-blocks-request-종료와-kv-block-정리)에서 본 "KV connector가 block을 보내는 중이면 반납을 미룬다"가 이 경우다.
- decode instance: 새 request가 오면 scheduler가 [`get_num_new_matched_tokens()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/distributed/kv_transfer/kv_connector/v1/base.py#L501-L534)로 원격에서 받아올 수 있는 token 수를 묻는다. 그만큼 block을 할당하고, request를 [`WAITING_FOR_REMOTE_KVS`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L1320-L1323) 상태로 둔다. KV가 다 도착하면 받아 온 부분은 다시 계산하지 않고, 남은 token만 계산한 뒤 decode로 넘어간다.

같은 connector 구조가 KV offloading에도 쓰인다. offloading connector는 GPU에서 밀려난 block을 CPU 메모리나 디스크에 보내 두고, 같은 prefix의 request가 오면 `get_num_new_matched_tokens()`로 다시 불러온다. 멀티턴 대화에서 eviction으로 사라진 block을 되살리는 것도 이 경로다.

#### 전체 구조에서 보면

decode instance에서 받아 오는 KV도 같은 자료구조를 거친다.

- [1.1](#11-request와-kv-block의-자료구조) 자료구조: scheduler는 받아 올 token 수만큼 block을 할당해 `req_to_blocks`에 붙이고, request를 `WAITING_FOR_REMOTE_KVS` 상태로 둔다. 이때 KV가 아직 오지 않았는데도 [`num_computed_tokens`를 받아 올 token 수로 먼저 맞춘다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/sched/scheduler.py#L1324-L1336). 전송이 실패하면 나중에 다시 고친다.
- worker: connector의 worker 쪽이 받은 KV를 할당된 block ID 자리에 직접 쓴다. [`start_load_kv()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/distributed/kv_transfer/kv_connector/v1/base.py#L318-L320)는 KV를 vLLM의 paged KV buffer, 즉 [1.4](#14-block-table-token-위치에서-kv-cache-주소로)의 KV cache tensor로 불러온다.
- [1.2](#12-scheduler-출력-prefill과-decode를-한-step에-섞는다)-[1.4](#14-block-table-token-위치에서-kv-cache-주소로): 전송이 끝나면 request는 다시 scheduling 대상이 된다. 남은 token만 배정되고, `positions`는 받아 온 token 다음부터 시작한다. 받아 온 KV는 prefix cache에 맞은 block처럼 block table을 통해 읽힌다.

### 7. CUDA graph: padding이 남는 유일한 곳

padding은 한 군데에 남아 있다. CUDA graph는 capture한 batch 크기로만 재생할 수 있어서, 이번 step의 token 수를 가장 가까운 capture 크기로 올린다. [1.3](#13-step-안의-token-packing) 그림의 step은 실제 token이 6개(`num_tokens`)지만, 크기 8의 graph를 쓰려고 2개를 padding해 8개(`num_tokens_after_padding`)로 만든다. padding token의 slot은 `-1`이라 KV cache에 쓰이지 않고, 그 출력은 버린다. 이 padding은 request마다 생기는 것이 아니라 batch 끝에 한 번만 생기므로, 낭비는 batch 크기를 맞추는 몇 token에 그친다.

padding token도 [1.3](#13-step-안의-token-packing)의 배열에 자리를 차지한다. `input_ids` 끝에 PAD token이 붙고, `slot_mapping`의 해당 자리는 `-1`이다. full CUDA graph 모드에서는 request 수도 capture 크기에 맞춰 늘린다. 이때 늘어난 request 자리의 `query_start_loc`은 [모두 전체 token 수로 채운다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu/model_runner.py#L1431-L1433). 그래서 이 가짜 request의 query 길이는 0이 되고, `query_start_loc`은 줄어들지 않는 순서를 유지한다. FA3 같은 attention backend는 이 순서를 요구한다.

### 8. 여러 종류의 attention: KV cache group과 타입별 manager

지금까지는 모든 layer가 같은 full attention을 쓴다고 가정했다. 2026년의 주요 open model은 대부분 그렇지 않다. 긴 context에서 KV cache와 attention 비용을 줄이려고, full attention layer는 일부만 남기고 나머지를 더 가벼운 layer로 바꾸기 때문이다. v0.32.0이 지원하는 model 중 몇 가지를 보면 이렇다.

- [Gemma 4](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/models/gemma4.py), [MiMo-V2-Flash](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/models/mimo_v2.py): full attention layer 사이에 sliding window attention layer를 섞는다. sliding window attention은 최근 window 크기만큼의 token만 보는 attention이다.
- [DeepSeek-V4.1](https://github.com/vllm-project/vllm/tree/v0.32.0/vllm/models/deepseek_v41): KV를 세 종류로 나눠 쓴다. 여러 token을 하나로 압축한 MLA KV([`MLAAttentionSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/models/deepseek_v41/attention.py#L1138-L1160)), 최근 token을 압축하지 않고 두는 sliding window KV([`SlidingWindowMLASpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/attention/backends/mla/sparse_swa.py#L116-L125)), 압축기가 쓰는 작은 ring buffer([`CircularBufferSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/models/deepseek_v41/compressor.py#L159-L167))다. DeepSeek-V4도 압축 KV와 sliding window KV를 함께 쓴다.
- [Qwen 3.8](https://github.com/vllm-project/vllm/tree/v0.32.0/vllm/models/qwen4_exp) 계열: full attention layer와 Gated DeltaNet이라는 linear attention layer를 섞는다. 코드에서 class 이름은 `Qwen4Exp`다.
- [Kimi K3](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/models/kimi_k3/nvidia/model.py#L889-L930): Kimi Delta Attention(KDA)이라는 linear attention layer와 MLA layer를 섞는다.
- [GLM-5.3-Flash](https://github.com/vllm-project/vllm/tree/v0.32.0/vllm/models/glm5next): KDA 방식의 linear attention layer와 sparse attention layer를 섞는다. 코드에서 class 이름은 `Glm5Next`다. 이름은 비슷하지만 GLM-5.3-Flash는 GLM-5.2·GLM-5.3과 구조가 다른 model이다. GLM-5.2·GLM-5.3은 DSA(sparse attention) 하나만 쓰는 계열이고, vLLM에서는 [DeepSeek-V3.2 code](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/models/deepseek_v32/__init__.py#L7)가 GLM-5.2(`glm_moe_dsa`)를 함께 돌린다.
- [Nemotron-H](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/models/nemotron_h.py) 계열: full attention과 Mamba2를 섞는다.

linear attention과 Mamba 같은 state space layer는 token마다 KV를 쌓지 않고, request마다 고정 크기 state 하나를 들고 간다. vLLM은 이런 layer를 KV cache 쪽에서 모두 같은 종류로 다룬다. Gated DeltaNet layer는 Mamba layer와 같은 [`MambaBase`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/layers/mamba/gdn/base.py#L22)를 상속하고, Kimi K3의 KDA layer도 [`MambaSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/models/kimi_k3/nvidia/kda.py#L829-L831)을 돌려준다. 이 글에서는 이런 layer를 묶어 Mamba 계열이라고 부른다.

layer 종류마다 KV에 필요한 것이 다르다. full attention은 모든 token의 KV가 필요하고, sliding window는 마지막 window 안의 token만 필요하고, Mamba 계열은 마지막 state 하나만 필요하다. 모든 layer에 full attention처럼 KV를 잡으면, sliding window layer와 Mamba 계열 layer에서 쓰지 않을 메모리를 잡게 된다. vLLM은 이 문제를 hybrid KV cache manager로 푼다. 기본으로 켜져 있다. 핵심은 layer를 종류별 group으로 나누고, 메모리는 하나의 block pool로 함께 쓰는 것이다.

아래 그림은 이 설계의 결과를 먼저 보여 준다. 예시를 작게 하려고 block 크기는 2 token, window는 4 token으로 잡았다. group, buffer, pos는 그림 뒤의 소제목에서 차례로 설명한다.

#### KVCacheSpec: layer가 자기 KV 형식을 밝힌다

layer마다 [`get_kv_cache_spec()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/layers/attention/attention.py#L606-L690)으로 자기 KV 형식을 [`KVCacheSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L164)으로 밝힌다. model runner가 이것을 [모은다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/gpu_model_runner.py#L7146-L7175). spec은 block 크기, block 하나의 byte 크기(page size), request 하나가 최대로 쓸 메모리를 정한다.

| spec | 쓰는 layer | request 하나가 쓰는 메모리 |
| --- | --- | --- |
| [`FullAttentionSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L577) | 일반 attention. MLA도 이것의 하위 클래스다 | `max_model_len`까지 |
| [`SlidingWindowSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L849) | sliding window attention | window 크기까지 |
| [`ChunkedLocalAttentionSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L809) | chunked local attention | chunk 크기까지 |
| [`MambaSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L1034) | Mamba, Gated DeltaNet, KDA 같은 state 기반 layer | state 하나(block 1개)와 약간의 여유 |
| [`CrossAttentionSpec`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L1156) | encoder-decoder의 cross attention | encoder 출력 길이까지 |

#### KV cache group: 같은 종류의 layer를 묶는다

[`get_kv_cache_groups()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L2159)가 layer들을 group으로 나눈다. 모든 layer의 spec이 같으면 group은 하나다. 대부분의 model이 이 경우이고, 앞 절까지 본 구조가 그대로 쓰인다. 종류가 섞여 있으면 아래 두 단계를 거친다.

1. page size를 맞춘다. [`unify_kv_cache_spec_page_size()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L1292-L1354)가 가장 큰 page size를 기준으로, 작은 layer는 block 크기를 배수로 키운다. Mamba의 state는 block 크기와 관계없이 크기가 정해지므로, page를 [padding해](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L1331-L1340) 맞춘다.
2. layer 수가 같은 group으로 나눈다. [`_get_kv_cache_groups_uniform_page_size()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L1362-L1502)는 layer를 종류별로 모은 뒤, 가장 적은 종류의 layer 수를 group 크기로 삼아 [나눈다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L1478-L1502). 그림에서는 full attention이 2개라서 group 크기가 2이고, sliding window 4개는 group 2개가 된다. 나누어떨어지지 않으면 빈 layer를 채우고 경고를 남긴다.

group 크기를 맞추는 이유는 메모리를 함께 쓰기 위해서다. [`get_kv_cache_config_from_groups()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L1620-L1640)는 group마다 메모리를 따로 잡지 않는다. buffer k를 만들고, 각 group의 k번째 layer가 그 buffer를 함께 쓰게 한다. 코드 주석은 이것을 "Groups alias from byte 0"이라고 적는다. 그림에서 buffer 0은 F0, S0, S1이 함께 쓴다. 같은 bytes를 여러 group이 쓰는데도 충돌하지 않는 것은 block ID 하나가 한 번에 한 group에만 할당되기 때문이다. [`KVCacheTensor`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/kv_cache_interface.py#L1408-L1430) docstring도 "a block ID is owned by one group at a time"이라고 밝힌다. 그래서 block 3이 group 0에 가 있으면, buffer 0과 buffer 1의 block 3 자리는 F0과 F1의 KV가 쓴다.

#### 타입별 manager: 할당과 반납 규칙은 group마다 다르다

KV cache coordinator는 하나의 [`BlockPool`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_coordinator.py#L119)을 만들고, group마다 spec에 맞는 manager를 [하나씩 만든다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_coordinator.py#L154-L170). manager는 모두 [`SingleTypeKVCacheManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L48)의 하위 클래스이고, 같은 block pool에서 block을 받는다. 차이는 "이미 필요 없어진 token이 몇 개인가"를 답하는 `get_num_skipped_tokens()`에서 난다. 그만큼의 앞쪽 block은 null block으로 바꾸고 pool에 돌려준다.

- [`FullAttentionManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L729): 건너뛰는 token이 없다. request가 끝날 때까지 모든 block을 들고 있다. MLA도 이 manager를 쓴다.
- [`SlidingWindowManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L933): window 뒤로 밀려난 token을 [건너뛴다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L1135-L1170). 그림의 request R은 8 token을 계산했고 window가 4이므로, 앞 5 token은 다시 볼 일이 없다. 그래서 앞 block 2개가 null이 된다.
- [`ChunkedLocalAttentionManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L1263): 현재 chunk 앞의 token을 건너뛴다.
- [`MambaManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L1415): 마지막 state만 [남긴다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L1954-L1959)(`num_computed_tokens - 1`).
- [`CrossAttentionManager`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/single_type_kv_cache_manager.py#L2115): encoder 출력은 request마다 다르므로 prefix caching을 하지 않는다.

worker 쪽도 group 단위로 나뉜다. request는 group마다 block table을 하나씩 가지고([`MultiGroupBlockTable`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/block_table.py#L208)), attention metadata도 group별로 만든다. [1.4](#14-block-table-token-위치에서-kv-cache-주소로)에서 본 block table과 `slot_mapping`이 group 수만큼 있는 셈이다.

#### prefix caching: 모든 group이 동의하는 길이를 찾는다

group이 여럿이면 prefix cache hit도 group마다 다르다. full attention은 앞에서부터 모든 block이 있어야 맞는다. sliding window는 hit 끝 앞의 window 안 block만 있으면 된다. Mamba는 hit 끝 위치의 state가 있어야 한다. 그래서 같은 token 열이라도 group마다 hit 길이가 다르고, 실제로 쓸 수 있는 것은 모든 group이 동의하는 길이다. block hash에도 group ID가 [섞여서](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L74), 같은 token의 block도 group마다 따로 cache되고 따로 지워진다.

[`HybridKVCacheCoordinator`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_coordinator.py#L609)의 [`find_longest_cache_hit()`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_coordinator.py#L796-L806)는 이 길이를 반복으로 찾는다. docstring은 "Each attention type either accepts the current candidate length or reduces it. If any type reduces the length, restart checks over all types"라고 설명한다. full attention이 먼저 앞에서부터 가장 긴 hit를 찾고, 다른 종류는 그 길이 안에서 뒤에서부터 자기 조건이 맞는 곳을 찾는다. 누군가 길이를 줄이면 모든 종류가 다시 확인한다. 길이는 줄어들기만 하므로 반드시 멈춘다. full attention 하나와 다른 종류 하나뿐이면 한 번으로 끝난다.

hybrid manager는 `--disable-hybrid-kv-cache-manager`로 끌 수 있다. 꺼지면 sliding window와 chunked local layer도 [full attention처럼 할당한다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L2173). 계산은 여전히 window만 하지만 메모리는 아끼지 못한다. hybrid manager를 지원하지 않는 KV connector를 쓰거나, GPU가 아닌 platform이면 [자동으로 꺼진다](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py#L2135-L2192). 설계 문서는 [`docs/design/hybrid_kv_cache_manager.md`](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/design/hybrid_kv_cache_manager.md)에 있다. 다만 문서가 "exactly two KV cache groups"라고 쓴 부분은 v0.32.0 코드보다 오래되었다. 지금 coordinator는 group 종류가 셋 이상이어도 처리한다.

#### 설계 결정: 메모리는 하나로, 규칙은 group마다

이 설계는 두 요구를 함께 맞춘다. 하나는 메모리 낭비를 줄이는 것이다. sliding window layer가 window 밖 block을 바로 돌려주면, 그 block을 full attention layer나 다른 request가 쓸 수 있다. group마다 pool을 따로 잡았다면 종류별 비율을 미리 정해야 하고, workload에 따라 한쪽이 남고 다른 쪽이 모자란다. vLLM은 block ID 공간을 하나로 두어 이 비율을 정하지 않는다. 다른 하나는 기존 구조를 그대로 쓰는 것이다. group 하나는 앞에서 본 block table, block pool, prefix caching을 그대로 쓴다. 종류별로 다른 것은 manager의 몇 가지 메서드뿐이다.

대가는 제약이다. 모든 group의 page size가 같아야 하므로 block 크기를 키우거나 page를 padding해야 하고, group 크기를 맞추려고 빈 layer를 넣기도 한다. MLA처럼 padding할 수 없는 spec은 page size가 맞지 않으면 [`NotImplementedError`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L1341-L1354)를 낸다.

SGLang은 같은 문제를 반대 방향으로 푼다. 종류마다 물리적인 pool을 따로 두고, 하나의 radix tree의 node에 종류별 데이터를 붙인다. 이 차이는 SGLang을 다루는 다음 글에서 비교한다.

## 마치며

이 글은 `vllm serve` 한 줄이 서버를 띄우고, chat request 하나가 token이 되어 돌아오기까지의 경로를 v0.32.0 소스 코드로 따라갔다. 서버 초기화에서는 process와 config, KV cache가 준비되는 순서를 봤다. request 처리에서는 HTTP request가 tokenize, schedule, forward, detokenize를 거쳐 정리되는 과정을 봤다. 실행 batch와 KV cache에서는 그 과정을 받치는 batch와 KV block 구조를 봤다.

글이 너무 길어져서 아래 주제는 이번 글에서 뺐다. 각 주제는 별도 포스트에서 다룰 예정이다.

- SGLang의 구조: 같은 문제를 푸는 다른 serving engine인 SGLang이 server, scheduler, KV cache를 어떻게 나누는지 vLLM과 비교한다.
- NCCL 초기화: 이 글은 GPU 하나를 가정했다. GPU 여러 개로 model을 나눠 띄울 때 worker process가 NCCL 통신을 언제, 어떻게 초기화하는지 본다.
- FlashInfer 같은 attention backend의 결합: [1.4](#14-block-table-token-위치에서-kv-cache-주소로)에서 본 `slot_mapping`과 attention metadata가 FlashAttention, FlashInfer 같은 backend로 어떻게 넘어가고, backend를 어떻게 고르는지 본다.
